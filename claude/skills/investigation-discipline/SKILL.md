# 調査と変更の規律

技術的な罠そのものは個人記憶の個別トピックにある。ここに置くのは**判断の順序**。
どれも「気をつける」では守れないので手順の形にしてある。

## 0. 「残す・隠す・後回し」を安全側と決めつけない

「消す / やめる / 失敗させる」は不可逆で危険に見え、「残す / 隠す / 後回しにする」は
可逆で安全に見える。だが**残したものが何を提供しているかを測らない**と、何も守らずに
ノイズと矛盾だけが残る。

- **「残す」と決めたら、それが今何を提供しているかを 1 つ実測する。**
  提供していなければ残す理由は無い。「手で入れたものだから」は提供物ではない。
- **「隠す・skip する」と決めたら、隠した後に残る状態を書き出す。**
  「緑だが残骸がある」が答えになるなら、それは対処ではなく事故の準備。
  次の処理がその残骸を正常な状態と誤認する。
- **「残置・後回し」と決めたら、その状態で成立するかを実行して確かめる。**
  常に赤・常に警告なら残置は選択肢ではない。**常に赤いテストは本当の回帰を隠す**ので、
  skip でも残置でもなく廃止する。
- 「統合テストには価値がある」のような一般論を、価値が実際に生まれているかを
  確かめずに適用しない。
- ユーザーへの確認も同じ構造で判断の回避になりうる。**測れば決まることは測る。**
  確認を求めてよいのは主観・好みが要る場合だけ(個人記憶 autonomous-execution-preference)。

## 1. コードに書かれた制約を要件と混同しない

制約に見えるものが**過去の実装都合**であることがある。制約の枠内で仮説を潰し続けると、
枠自体が誤りだった場合に全部無駄になる。

**先に打つ手:** 調査対象の制約を見つけたら、仮説を立てる前に出自を確認する。

```bash
git log --oneline -S '<制約の文字列>' -- <path>   # 入った commit
git log -1 --format=%B <sha>                      # その理由
```

commit message が「実装を簡単にするため」「中途半端にやるより」なら**要件ではない**。
ユーザーが明示的に要求していない制約は、外す選択肢を検討対象に入れる。
「ユーザーがそう指示したのか」を確認するのが最短。

## 2. 同じ問題を解いている先行実装を最初に見る

`superpowers:systematic-debugging` の Phase 2「Find Working Examples」を飛ばさない。

**先に打つ手:** 「自分の環境固有の問題」と考える前に、

1. 同じことをしている実績あるプロジェクトの実装を読む
2. ベンダの公式ドキュメントで**その API の保証範囲**を確認する
3. 同じ症状の既知 issue を検索する

広く使われている仕組みが自分だけ壊れているなら、前提の理解が違っている可能性が高い。

## 3. 前提を変えたら、その前提が効いている場所を全部列挙する

**先に打つ手:** 変更した前提を grep して、参照している箇所を機械的に全部出す。
コードだけでなく**テスト・ドキュメント・運用手順**も対象。各箇所について
「新しい前提でも成立するか」を 1 つずつ書き出す。レビューは実行結果を見ないので
この種の見落としは捕まらない。

## 4. 因果を説明できない回避策は当てない

**先に打つ手:** 回避策を入れる前に「何が起きているか」「この対策がどう効くか」
「影響範囲はどこまでか」を言葉にする。説明できないなら回避策を重ねるのではなく、
**その構成を使うのをやめる**。環境変数のような広く伝播する手段はとくに、
副作用の範囲を確かめてから使う(実例は個人記憶 windows-claude-code-env)。

## 5. 環境の異常を報告する前に測定手段を検証する

**先に打つ手:** 破壊や異常を報告する前に、同じ事実を**別の手段で**測って一致を確認する。
とくに「数が減った」「消えた」は測定漏れと区別が付かない。
`catch { continue }` で例外を飲む集計コードは書かない(飲むなら件数を数えて報告する)。
PowerShell の具体的な測定バグは個人記憶 windows-claude-code-env にある。

## 6. 注入された記憶は、行動原則なら本文まで開く

`type: feedback` / `type: user` のもの(振る舞いの指示)は、作業を始める前に本文を開く。
索引の 1 行だけ見て「知っている」と扱わない。
記憶を「書き足す」ことで解決しようとする前に、既存の記述を守れていたかを確認する。

## 7. 既存ファイルを入力として消費したら、拾わなかった行を必ず出す

抽出・変換を書いたら、同じ入力に対して**補集合**(拾わなかった行)を出力させて目で見る。
0 件になるか「意図的に捨てた」と言えるまでは完成と呼ばない。
**捨てた行が、拾った行の前提条件であることがある。**

## 8. 「無視した」を出力の選択肢にしない — 扱うか、止まる

報告して続行は人間の作業を増やすだけで、扱うより止まるより悪い。

**先に打つ手:** 「例外は報告します」と書きたくなったら、その報告を読んだ人間が
何をするのかを 1 行で書く。書けないなら扱うか、その場で止める。
「無視」というカテゴリが要らなくなるよう対象の指定方法を変える(明示マーカー方式など)。

## 9. 設計を変えたら、その設計を根拠にした過去の判断を棚卸しする

セクション 3 はコードの参照箇所を grep する話だが、**判断そのものにも同じ棚卸しが要る。**
根拠が消えても配分だけが残る。

**先に打つ手:** 設計を変えたら「この設計を前提に決めたこと」を列挙して、
根拠が生きているか 1 件ずつ確認する。残っている判断を現状の理由で再説明できなければ外す。

## 10. 観測のために足した仕組みが被験体を壊す

**セクション 5 の「測定手段を疑う」の上位版。**測定コードが間違った数字を出すだけでなく、
**測定のために足した仕組みが対象そのものを壊す。**

| 足したもの | 何が起きたか |
|---|---|
| ストール検出ウォッチドッグ | winget の CPU で「停止」を判定したが、**MSI 中は winget は待つだけで働くのは msiexec**。正常動作中の MSI を kill し、Windows Installer のセッションが残って**後続 5 件が `1618` で連鎖失敗**した |
| 状態確認スクリプト(`winget list` を実行) | **最新の winget 診断ログが自分の探査になり、本命のログが隠れた** |
| 高頻度ポーリング | 1 vCPU のゲストで監視サービスが 3,700 秒 CPU を消費。**遅さの一因を自分で作った** |

**先に打つ手:**

- **介入を足す前に、その介入が誤爆したときの被害を書き出す。**「停止と判定したら kill」なら
  「正常なのに kill したら何が壊れるか」を先に言葉にする(例: MSI セッションが残る)。
- **判定に使う指標が対象の作業と同じ層かを確認する。**winget の CPU は winget の仕事量であって
  インストールの進捗ではない。**進捗は別の層(msiexec の有無・ディスク書き込み量・ログの更新時刻)で見る。**
- **観測が対象の資源を奪う環境では、観測頻度も変数として数える。**

## 11. 自分の経路が原因でないかを切り分けるまで「バグを見つけた」と言わない

「実害のあるバグ」に見えた異常の原因が**テスト経路**(対話デスクトップを持たない
プロセスから対象を起動していた)だったことがある。手がかりは対象自身が出していた
`Timeout creating winget window` の 1 行だけ。

**先に打つ手:** 異常を「対象の欠陥」と報告する前に、**条件を 1 つだけ変えた対比を取る。**
同一パッケージ・同一引数で起動元のデスクトップだけを変えると 2.5 時間ハング → 7 秒で決着した。
対比が取れないなら「自分の経路が原因である可能性を排除できていない」と明記して報告する。

## 12. 比較の「差分なし」と「取得失敗」を同じ枝に落とさない

`if ($d) { 差分を出す } else { 'IDENTICAL' }` と書くと、抽出が 0 件で `Compare-Object` が
エラーになったとき `$d` が null のまま **`else` に落ちて「完全一致」と報告する。**嘘を出力する。

**先に打つ手:** 比較の前に**両側の件数を検証して 0 なら止める。**
「一致」は差分が 0 件であることを確認して初めて言う。エラーと空を区別できない分岐を書かない。

## 13. 局面の違う観測を 1 つの設定へ畳み込まない

「壊れた既存 VM が vCPU 1 でだけ起動した」という観測を VM 作成スクリプトの既定値
`$CpuCount = 1` へ書き込むと、その既定で作った VM は Windows 11 セットアップの
要件チェック(2 コア以上)に落ち、インストールが始まらない。

**先に打つ手:** 回避策を成果物の既定値へ昇格させる前に、**その観測がどの局面のものかを書く。**
「インストール時」と「起動後」、「初回」と「復旧時」は別の局面で、要件が正反対になり得る。
局面を書けないなら既定値にせず、パラメータのままにして呼び出し側で選ばせる。

## 14. 引き継いだ「現在の状態」は、判断に使う前に測り直す

セクション 5 は測定手段を疑う話だが、**そもそも測っていない値**を根拠にしていることがある。
圧縮 state file・ハンドオフ・前セッションの報告に書かれた状態は**観測時点の値**で、
その後に別のセッションや別のワークフローが動かしている。

**先に打つ手:** 復旧・引き継ぎの直後に、**これから判断の根拠にする状態だけ**を再測定する。
全部測り直す必要はない。「未 push だから push する」のように、
書かれた状態がそのまま次の行動を決める項目に絞る。

### git の「push 済みか」を答えるコマンド

- `git status` / `git rev-list --count @{u}..HEAD` が見ているのは**ローカルの remote-tracking ref**。
  fetch していなければ古い値のまま答える。
- リモートの実際の位置は `git ls-remote origin refs/heads/main`。
- **いつ・どこから push されたかは `git reflog show origin/main --date=iso`** にしか無い。
  `update by push` の行と時刻が残る。HEAD 側の `git reflog --date=iso` も併せて見ると、
  自分が作っていないブランチ操作(`checkout` / `reset` / `merge`)の足跡が出る。

### 未レビューのコミットを main に積んだままにしない

flake input 更新のような**別作業の push が、下に積まれた未レビューのコミットを巻き添えで公開する。**
`git push` はブランチ全体を送るので、レビュー待ちかどうかは区別されない。
レビューゲートを通す前提のコミットは main に積まず、作業ブランチに載せる。

## 15. 環境差のあるコマンドは、OS 名で分岐せず能力で判定する

`uname -s` が `Darwin` でも、PATH の先頭が nix の GNU coreutils なら BSD 版のフラグは通らない。
**OS 判定はツール実装の判定にならない。** 非互換が出るのは in-place 編集と情報取得。

| 用途 | GNU | BSD |
|---|---|---|
| in-place 編集 | `sed -i`(suffix は `-i.bak` と密着必須) | `sed -i ''`(suffix は独立引数) |
| パーミッション取得 | `stat -c '%a'` | `stat -f '%Lp'` |

**先に打つ手:**

- **フラグは能力判定で選ぶ。** `stat -c '%a' "$f" 2>/dev/null || stat -f '%Lp' "$f" 2>/dev/null`。
  `case "$(uname -s)"` で分岐したコードは nix 環境で壊れる。
- **1 回限りの編集は shell に渡さずファイル編集ツールで書く。** 方言の問題が消える。
- **誤った側を渡した失敗は「編集されないまま成功に見える」形で出る。** GNU sed に `-i ''` を渡すと
  空スクリプト扱いになり、続く式が**ファイル名として**解釈される。編集後は必ず内容を検証する。
- **権限や到達性のプローブに冪等フラグを使わない。** `mkdir -p` は対象が既存なら
  何も書かずに 0 を返すので「書ける」証拠にならない。書き込み可否は新規パスの作成か
  `touch` で測る(→ セクション 5)。

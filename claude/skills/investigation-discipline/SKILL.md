# 判断前の事実確認と原因調査

不具合・テストの失敗・想定外の挙動を調べるときは、下の「根因を突き止めてから直す」の手順で進めます。単純に見える不具合や急ぎの場面でも省きません。ツールの出力の誤り (音声認識の聞き違い、文字変換の誤りなど) を見つけ、設定・運用の次の対処を提案する場面も含みます。

kata から調査を引き継いだときも、ほかの skill や作業の途中から調査を始めるときも「外部情報と現物を並行して調べる」に従います。設計・実装着手・高コスト処理・再試行の前には「次の操作を選ぶ前に確認する」も使います。調べる内容に応じて、対象・証拠・既存保証を扱う節を参照します。全範囲の完遂と変更判断は共通 `AGENTS.md` に従います。

## 根因を突き止めてから直す

根因を確かめる前に修正しません。症状だけを消す修正は、同じ原因から別の症状を生みます。「とりあえず直して後で調べる」「X を変えて様子を見る」「よく分からないが直るかもしれない」と考えたら、手順 1 へ戻ります。ユーザーから「それは起きていないのか」「推測をやめて」と問われた場合も、確かめていない前提が残っているので、観測へ戻ります。

1. **観測する:** エラーメッセージ・警告とスタックトレースを最後まで読み、行番号・パス・エラーコードを控えます。再現手順を確かめ、確実に再現できなければ推測で直さずに観測を増やします。直近の変更 (diff・commit・依存・設定・環境の差) を確かめます。複数の部品を通る処理 (CI → ビルド → 署名、API → サービス → DB など) では、部品の境界ごとに入ってきた値と出ていった値、環境変数・設定の伝わり方を記録して一度実行し、どこで壊れるかを特定してからその部品を調べます。
   誤った値が呼出しの深い所で見つかったら、その値を渡した呼び出し元を一段ずつたどり、誤った値が最初に生まれた箇所 (出所) を特定して、そこで直します。出所が承認された変更範囲の外 (上流のツール本体など) にある場合は、範囲の中で必要な保証を満たせる箇所を探し、無ければその事実と選択肢を利用者に示して判断を仰ぎます。手でたどれない場合は、危険な操作の直前に、引数・作業ディレクトリ・関係する環境変数・スタックトレースを標準エラーへ出す一時的な記録を入れて実行します。テスト中はロガーの出力が抑止されることがあるため、標準エラーを使います。不要なファイル・ディレクトリを作るテストを特定できない場合は [find-polluter.sh](scripts/find-polluter.sh) でテストファイルを一つずつ実行して特定します (テスト対象の repo の root で `bash <この skill のディレクトリ>/scripts/find-polluter.sh <検査するパス> '<テストファイルのパターン>' <テストコマンド...>`)。
2. **動く例と比べる:** 同じ repo の中で似た処理が動いている箇所を探し、壊れている箇所との違いを小さなものまで挙げます。参照する実装は最後まで読み、それが前提にする依存・設定・環境も確かめます。
3. **仮説を一つずつ試す:** 「原因は X、理由は Y」と一つの仮説に絞り、それを確かめる最小の変更や観測で試します。外れたら、試した変更だけを編集前に退避した複製か逆の編集で取り消し (`git checkout`・`git restore` は同じファイルの他の未コミット変更まで消すため使いません)、変更を重ねずに新しい証拠から仮説を立て直します。分からないことは分からないと示し、調べます。
4. **直す:** 修正の前に、元の不具合が再現することを確かめます。共通 `AGENTS.md`「変更の判断」のテストの規則でテストを書くと決めた場合は、再現する失敗テストを先に作り、[test-red-first](../test-red-first/SKILL.md) で赤を確かめます。テストを書かない場合は、その場の再現スクリプトか再現手順で失敗を確かめます。
   根因に対する修正を一つだけ、承認された範囲の中でその性質を担う箇所 (多くは出所) に入れ、ついでの改善や整理を混ぜません。事例や層ごとに対処を足さず、同じ原因が及ぶ範囲を一度に直すことは、共通 `AGENTS.md`「変更の判断」に従います。観測した一件がより広い原因 (モデルの癖・変換規則の誤りなど) の一例なら、同じ原因から出た実例を集め、修正の前後で比べてまとめて確かめます。テストで再現できない出力の誤りは、この比較を再現の代わりにします。原因がその項目の欠落そのもの (モデルが知り得ない固有名詞、新しい接続先など) と確かめた場合は、その一件を辞書や許可リストへ足すことが根因の修正です。
   修正後は、元の再現手順と実際の利用経路、修正した挙動に関係する既存テストで確かめます。完了を主張する前の確認は [kata-verify](../kata-verify/SKILL.md) に従います。
5. 修正するたびに別の場所で新しい共有状態・結合・症状が出る場合や、修正に大規模な作り直しが要る場合は、仮説の誤りではなく設計の誤りを疑います。個別の修正を重ねず、その設計を続ける根拠を確かめ、作り直す案と比べます。
6. 調べても根因がコードに無く、環境・タイミング・外部の要因と分かった場合は、調べた内容と根拠を残し、その要因に合う処理 (待ち方・再試行・エラー処理など) と、再発を観測できる記録を入れます。「根因が無い」という結論の多くは調査不足なので、手順 1〜3 の観測を尽くしたかを先に確かめます。再試行・経路の停止・別経路の判断は下の「検証と収束の条件」と共通 `AGENTS.md` に従います。

固定時間の待機 (`sleep`・`setTimeout` など) を含むテストが、負荷や並列実行で不安定になる場合は、待つ時間を推測せず、目的の状態 (イベントの発生・状態の遷移・件数・ファイルの出現) を条件にして待ちます。条件は待機ループの中で毎回取得し直し、短すぎない間隔で確かめ、上限を過ぎたら何を待っていたかを示して失敗させます。上限の値は共通 `AGENTS.md` の打ち切り上限の規則で決めます。debounce の間隔など時間そのものを確かめるテストに限り固定時間で待ちます。その場合も先に起点となる状態を条件で待ち、既知の周期から算出した値にして、その根拠をコメントに書きます。

## 次の操作を選ぶ前に確認する

最初に、利用者の環境で実際に起きていることと、製品の仕様・一般的な使い方のどちらが答えに必要かを確かめます。環境固有の事実は設定・ログ・実物で確認します。その事実を判定・解釈する場合は、外部の仕様や別事例とも照合します。機能や plugin が質問に登場しただけでは、その機能を実行する skill の適用条件になりません。利用者が明示的に指定した skill や、操作自体に必要な権限・安全確認は維持します。

判断に必要な照合を終えたら、結論とその証拠を伝えます。同じ対象・版・条件の確認済みの証拠が既に会話にあれば再利用します。照合で具体的な不足が見つかれば、判断を変え得る証拠を追加します。作業の途中で利用者から進捗を聞かれたら、その時点で確かめた結果と、今している作業をその場で返します。この返答のために新しい調査を始めたり、恒久対策の完了を待ったりしません。依頼への答えとなる結論は、共通 `AGENTS.md`「応答」に従い、分かるまで調べてから伝えます。

1. 目的と現在の制約を満たす、通常の直接的な方式から選びます。
   - 調査・手順の読込・委譲・検証・待機は、それが満たす依頼の要件か、守るべき既存保証へ結び付く場合だけ行います。適用条件を満たした手続の内容は省略・緩和せず、条件を満たさない手続は起動しません。単なる操作の実行を、成果物の実装・設計・レビューへ広げません。
   - 別の方式が必要なら、通常の方式では満たせない条件を具体的に示します。変更行数や job 数の少なさだけで、余分な実行層や既知の大きな処理負担を採用しません。たとえば ARM の通常ビルドには利用可能な ARM ネイティブ環境を使い、エミュレーターでの動作確認が目的ならエミュレーターを使います。
   - ツールや plugin 固有の確認条件は、その方式を使う場合に守る条件で、利用者の依頼全体に対する承認とは別です。確認待ちへ移る前に、その方式を使う必要性と、既に承認されている直接操作で目的・保持条件を満たせるかを確かめます。
   - 観測した制約から依頼への影響を推論し、高コストの追加試行、変更範囲を広げる承認依頼、または依頼全体の停止を選ぶ場合は、その判断をした担当とは別の担当に先に照合を頼みます。元の依頼の該当文、観測した事実、影響する普段の利用経路、承認済みの代替手段を渡します。試行を選ぶ場合は、結果によって次の操作がどう変わるかも渡します。既存の仕様・スコープ確認でこの照合が済んでいれば、その結果を使います。必要性を確認できるまで、その試行・承認依頼・全体停止を保留し、依存しない作業を続けます。利用者の中止指示と上位の権限制約には直ちに従います。
   - 上位指示・権限制約・実行前審査の拒否を避けるために経路を変えません。
2. 「外部情報と現物を並行して調べる」で得た証拠を使い、次の選択を変え得る不足を追加で調べます。案内・実行する手順は、現在の状態で各入口が使え、前提から最終結果まで進めるかを確かめます。前提の達成にその手順の完了が必要になる循環も、この確認に含めます。採用したい説明を否定できる条件も調べます。照合後の証拠で通常の方式と負担を判断できれば、所要時間の測定や全候補の比較を追加しません。証拠では選べない部分に、候補を区別する最小の実験を使います。前提が成立すれば必要な実装と通常経路の受入へ進み、成立しなければ機能・保証を保つ方式へ見直します。
   原因を断定できないときは、観測を説明する仮説を立て、支持する証拠・矛盾・未確認点から優先順位を付けます。優先する仮説を判別できる最小の確認を実行し、その結果で判断を更新します。仮説の列挙や次の調査の提案だけで止めません。
3. 対象版と前提が変わらない証拠は再利用します。資料や既存結果で不成立が確定した操作を、失敗をもう一度見るためだけに実行しません。新しい実装の回帰テストや観測経路の確認など、追加で確かめる性質がある場合は、その性質を検証します。高コスト処理でしか得られない証拠と、要求された全対象の通常受入は省略しません。
4. **費用の確認:** 利用者のアカウントに課金される処理 (有料 API、クラウドの推論・変換など) は、実行前に呼出し 1 回あたりの入力・出力・推論の使用量と単価から費用を見積もります。使用量が分からなければ、入力の規模・出力の上限・単価から保守的に見積もります。少数件の試行で使用量を測る場合も、その試行分を同じ見積もりと承認の判断に含めてから実行します。見積もりと承認の判断は、その依頼で既に使った額と予定額を合わせた累計で行います。見積額が依頼の目的の規模 (比較対象の利用費など) に比べて無視できない場合、または比べる規模が依頼から分からない場合は、見積額と得る結果を示して承認を得てから実行し、承認額を超える見込みになった時点で改めて承認を得ます。利用者が対象と方法 (件数・モデルなど) を明示して課金処理を依頼した場合は、その依頼を承認とし、依頼の範囲を超える件数・モデルや追加の課金だけを確認します。実行した課金は、結果の報告に用途と金額で含めます。
   エージェントが測定・採点・補助処理の手段として課金処理を選ぶ場合は、判断を変えない精度のために課金しません。エージェント自身ができる計算・比較・採点 (テキストどうしの照合、誤りの数え上げ、集計) は外部モデルに任せず自分で行い、同じ判断ができる無料の測り方 (ローカルで計算できる指標、取得済みの結果) があればそれを使います。外部モデルに頼むのは音声の聞き取りなど自分ではできない処理に限り、判断に足りる最小の件数、足りる中で最も安いモデル、推論量の指定で実行します。依頼の成果物そのものや、製品の通常経路・受入として課金される処理は、件数とモデルを依頼と仕様に従わせ、上の見積もりと承認だけを適用します。

AdGuard の通信ログ、DNS フィルタやモバイル広告の残存を調べる場合は、[ad-filter-investigation](../ad-filter-investigation/SKILL.md) を併用します。

エージェントの shell / sandbox によるファイル・認証・通信の食い違い、実行前審査の判断、Claude Code・Codex の sandbox 設定の照合・検証は、[実行環境の観測](references/agent-runtime.md) を読みます。Windows の文字コード・shell 間の入力や実レジストリは `windows-script-diagnostics` が担当します。

## 外部情報と現物を並行して調べる

調査の開始時に [precedent-research](../precedent-research/SKILL.md) を開きます。Claude Code では Skill ツールで呼び出し、Codex では `SKILL.md` の本文を読みます。両方の skill を読んだら、最初の調査操作として公開できる語で先例の Web 検索を始めます。対象に直接関係する外部資料の取得や現物の読み取りは、その検索と同時か、検索を始めた後に着手します。

公開情報で調べられる問いは、Web で開発元の資料の本文を開きます。インストール済みのマニュアルや同梱資料は、手元で使っている版の証拠として照合に使います。互いに依存しない検索・読取は並行して進めます。先例を比較し、対象の外部資料と現物を照合します。両方の結果を根拠にしてから、結論・提案・実行へ進みます。

1. **前提が成り立つかを確かめます。** 手元の資料・コード・設定どうしが整合していても、要件や外部仕様に照らして、それ自体が正しいか、必要かを調べます。何が前提ならその仕組みが必要になるか、その前提は今も成り立つかを確認します。最初に見つけた説明や、手元に列挙された候補の外も探します。
2. **対象に関わる仕様、反例、使える機能を探します。** 公式仕様・該当版の実装・原データなどの一次資料を優先し、問いに合う資料の本文を読みます。解決済みの issue、公開された運用例、解説や利用者の報告も、反例や実環境の手掛かりを探すのに使います。参照元をたどり、原資料を取得できない主張は独立した観測や再現で確かめます。検索結果の抜粋や、同じ原資料を写した複数の記事だけで裏付けを得たとは数えません。
3. **外部の説明を現物で検証します。** 資料の出典・版・日付・適用条件を、対象の版・設定・観測と突き合わせます。仕様と動作が食い違えば、再現条件と資料の更新状況を調べます。原因候補を区別できる確認を実行し、結果に合わせて仮説を更新します。方式は、既存例を取り入れた案と手元の方式を同じ要件で比べます。より少ない仕組みで要件を満たせるかを、対象環境での小さな実測や通常の利用経路で確かめてから選びます。結論には出典・実測と、判断に関わる反証や適用範囲を添えます。

公開検索や資料取得で送る情報は、公開できる一般化した用語や公開仕様に限ります。外部への送信に制約がある場合は、許可された別資料や独立した観測経路を使います。

- 長時間のビルド・CI・全体検証へ進む前に、結果の可否や方式を変える未確認の前提を特定します。各前提には、一次資料・実装・実効設定・小さな再現のうち、最も少ない時間と資源で判定できる確認を対応づけます。その確認を先に実行し、取得側だけでなく供給側や保持先まで、要求された保証が成立するかを確かめます。短く切り出せる前提確認を全体検証へまとめず、前提が崩れたら方式を見直します。
- 長い処理を実行する間も、その結果に依存しない未確認事項の調査を進めます。待機する前に残る調査を確認し、進捗の監視だけを繰り返しません。前提確認で代替できない実際の利用経路・全対象の最終検証は維持します。
- 利用者が操作を明示的に拒否したら、その操作を止めます。実行前審査が拒否した操作も停止します。拒否理由の照合と再判定は [実行環境の観測](references/agent-runtime.md) に従います。
- 通信や調査処理の中断、権限不足などで必要な証拠が取れないときは、欠けた確認と中断の原因を確かめます。確認できた結果と推論は区別します。再試行の規則に従い、許可された別の経路で資料を取る、実装を追うといった方法を試します。必要に応じて条件を絞って再現します。それでも結論を変え得る不足が残る場合は、何が判断できないかとその理由を示して該当部分を保留します。確認できた証拠で判断できる承認済みの作業は進めます。

## 対象と証拠を照合する

- 全件調査や抽出・比較では、元の依頼・訂正・参照資料から対象と要件を特定します。調べる集合は、依頼が指す関係 (対象を変更する主体、対象を参照する箇所など) で決めます。所属プロジェクト・作業ディレクトリ・名前などで絞った集合も含め、ディレクトリ、設定の参照先、呼び出し元、配備先と照合し、その関係を持つもの全体を覆う根拠を確認します。検索の除外、非表示項目、ページ分割、権限による欠落も調べます。
- 各対象の内容と、要件・成果・直接の確認結果・残件を対応づけます。索引や抜粋を全文確認と数えず、切り詰め・取得失敗による未読部分を回収します。対応は会話や既存の計画に置き、専用の管理機構は増やしません。
- 抽出・変換では、入力のうち採用しなかった部分も確認します。除外部分が採用部分の前提になっていないかを調べ、残す内容・移す内容・不要な内容を区別します。
- 既存の証拠や通常の方式では選べず、製品・モデル・方式の候補を比べて選ぶ調査を行う場合 (上の「次の操作を選ぶ前に確認する」2) は、測る前に [references/comparison.md](references/comparison.md) を読みます。評価基準と候補の選び方を先に決めること、正解データの作り方、候補を伏せた判定、測っていない性質で候補を選ばないことが書いてあります。
- 比較前に両側の取得成功と対象件数を確認します。正常な空集合、取得失敗、差分なしを区別し、取得できなかった対象を成功件数へ混ぜません。
- 参照先や利用経路に達成を左右する前提があれば辿ります。対象外にするものは元の依頼との関係から判断します。

## 原因と制約を切り分ける

- 実装上の制約は、要件や外部仕様による制約と分けます。導入時の履歴・意思決定から現在も必要な理由を調べ、実装都合なら外す案も比較します。
- 回避策を適用する前に、観測した原因、対策が変える状態、維持する保証、影響範囲を対応づけます。因果が説明できない場合は仮説を区別する観測へ戻ります。
- 廃止された設定を移行する場合は、開発元の案内を確認し、代替設定が引き継ぐ挙動と適用範囲を確かめます。ユーザー単位やアプリ単位の設定で要件と既存保証を満たせるかを先に確認します。マシン全体の設定や管理者権限が必要な変更は、影響範囲が小さい経路で満たせない条件を特定してから提案・実行します。
- ツールの互換性は OS 名から推定せず、実際のコマンドと必要な機能で確認します。確認したい操作が起きたことを検証し、何もしない成功を権限や到達性の証拠にしません。

## 観測経路と介入を検証する

- 消失・件数減少などの異常は別の取得経路でも測ります。対象の欠陥と判定する前に、同じ入力で起動元・権限・接続などの条件を一つ変えた対比を取ります。対比できない条件は原因未確定として保持し、別の観測で切り分けます。
- 長い処理の前に、その工程で必要な結果と、それへ近づいていることを確かめる観測点を決めます。成果物・転送済み量・対象の状態など、実作業に対応する証拠を使います。標準出力自体が成果の処理では、その内容を確認します。稼働中の表示、プロセスの存在、ログの増加だけでは進捗と判定しません。
- 時間制限の値は、共通 `AGENTS.md`「変更の判断」の打ち切り上限の規則で決めます。待つ間は観測点で必要な原文の取得・判断の確定・成果物の変化を読み、通常期待される進み方と既に得た事実に照らして、内容が前へ進んでいるかを確認します。食い違い、同じ内容の反復、進捗の証拠不足があれば、上限まで待たず、現在の工程・出力先・待機先を調べて継続・中断・方式変更を判断します。途中成果が出ない工程は、その特性に対応する観測点を使い、観測できない範囲を明示します。監視や停止処理を加える場合は、誤判定時に壊れる状態と復旧方法も確認します。
- 観測が消費する CPU・I/O・接続数と観測頻度も測定条件に含めます。観測自身がログの順序や最新値を変える場合は、本来の処理の記録を識別します。
- 設定へ反映する前に、観測が初回・通常運用・復旧などのどの局面に属するかを確認します。一局面の回避策を、前提の異なる局面の既定値へ一般化しません。
- 引き継ぎ・履歴・監視の状態値は、観測時刻と取得経路を確認して現在の実物と区別します。監視 reader は実行 handle と終了状態も確かめます。停止した reader の保存済みログや古い状態値を、実作業が進行中・健全である根拠にしません。次の待機前に生きた取得経路で対象の実状態を再取得し、必要な成果と照合します。

## 保持・削除と影響先を確かめる

- 残すものが提供する機能や保証を実測し、削除する場合に失うものと比較します。隠す・skip する案では、処理後に残る状態と、後続処理がその状態をどう扱うかを確かめます。
- 常時失敗する検証や警告は原因を調べます。廃止する場合は保証が不要になった根拠を確認し、必要な保証を消して成功にしません。
- 前提が変わったら、その前提を使う判断・操作・利用経路を特定し、影響する部分を調べ直します。新しい結果と、引き続き使う仕様・観測・制約を突き合わせます。食い違いがあれば対象の版、適用条件、観測方法から理由を確かめます。コード・テスト・文書・運用手順と、その設計を根拠にした過去の判断を再評価します。結論に関わる食い違いがあれば、引き続き成り立つ条件とともに示します。語句検索だけで判断の依存関係まで確認したことにしません。

## 検証と収束の条件

- 次の処理は、残る未達と取得済みの証拠から選びます。検査・判定の仕組みも、目的に必要な判断を満たしつつ総使用量を抑える対象です。確認済みの情報を再送して再判定せず、変更の影響を受ける部分へ絞ります。追加の呼出しは、その結果が成果や判断をどう変えるか定めてから行います。完了を妨げない小さな問題と、要求・既存保証を損なう欠陥を区別します。
- 検証前に対象版を固定し、変更の影響を受ける証拠だけを再取得します。既に判断できる結果を使って反映へ進み、作業量や確認回数の増加を進捗の代わりにしません。必要な最終受入と独立レビューは維持します。
- レビューには判定に必要な呼び出し元・状態の出所・既存保証・直接検証を渡します。文脈を欠いた分割で推測と追加調査を往復させず、指摘の因果と到達性を実物で判断します。
- 再試行・当該経路の停止・別経路の継続は、共通 `AGENTS.md`「変更の判断」の再試行規則に従います。失敗した回数だけでは作業全体を打ち切りません。
- 元の依頼から成果への対応と、実物から要件への対応を両方向で照合します。漏れがあれば共通原因と影響先へ戻ります。全要件が実物と直接検証で満たされ、具体的な未確認リスクがなければ調査と検査を終え、必要な反映と後片付けへ進みます。

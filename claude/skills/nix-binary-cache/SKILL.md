# Nix のバイナリキャッシュ診断

同じ機能を維持して、対象環境でローカルコンパイルを避けられるかを確認します。
更新・適用の承認範囲は元の依頼に従います。診断だけの依頼で switch は実行しません。
ホスト固有の構成・キャッシュ・運用方針は、対象 repo とプロジェクト記憶から取得します。
一般的な原因切り分けは `investigation-discipline`、CLI の不足は `missing-tools` に従います。

## 対象成果物と予定の特定

1. 問題が出たコマンド、実行ユーザー、Nix の版、対象 system、flake の固定版を確認します。
   更新前後で結果が違う場合は、それぞれの lock と設定を区別します。
2. repo の通常の build / switch 経路から、対象の installable、derivation、出力の
   store path を特定します。アプリ本体、ラッパー、helper、依存パッケージを分けます。
   本体のキャッシュがあっても、別 derivation の helper が取得できるとは限りません。
3. lock を書き換えない dry-run で、取得予定とビルド予定を確認します。
   例えば `nix build --dry-run --no-link --no-write-lock-file "$NIX_TARGET"` を使います。
   `NIX_TARGET` は調べた対象へ設定し、未追跡の Nix ファイルが評価から抜けていないか確認します。
   評価・ソース取得の失敗と、評価後のキャッシュ欠落を分けます。

## 実効設定と配布物の照合

設定ファイルだけでなく、実際に取得を担当するユーザー・daemon の設定を確認します。
`nix config show` などから必要な項目だけを取り出し、認証を含む設定全体は出力しません。
この表示はクライアントの値です。daemon 側の設定ファイル・起動オプション・拒否ログも
照合し、クライアントに表示された値が daemon でも採用されたとは判断しません。
調べる対象は substituters、trusted-substituters、trusted-public-keys、trusted-users、
substitute、署名検証、CLI・flake による上書きです。設定名は使用版の help で確認します。
flake のキャッシュ指定を受け入れることや、ユーザーが daemon の設定を変更できることを
前提にしません。

| 観測 | 次に確かめること |
|---|---|
| キャッシュへ接続できない | DNS・認証・TLS・接続先・実行経路。対象成果物の不在と判断しません |
| 接続できるが対象出力が取得できない | 正確な store path と、その path のメタデータ・取得応答。接続成功だけでは不足です |
| メタデータはあるが取得に失敗する | NAR 本体・参照先の取得、署名・信頼設定、daemon の拒否理由 |
| 上流にはバイナリがあるが path が異なる | system、nixpkgs の pin、override、patch、ビルドオプション、依存差 |
| 同じ名前の release / CI 成果物だけがある | Nix の対象出力と同じ成果物か、公開ジョブがその出力をキャッシュへ配布しているか |

`nix store info --store "$NIX_CACHE"` は接続確認です。
対象出力の存在確認には、例えば `nix path-info --store "$NIX_CACHE" "$NIX_OUTPUT"` を使います。
コマンドの変数には確認した接続先と出力を設定します。404 はその接続先・path・観測時点の
結果であり、全配布経路の不在を意味しません。負のキャッシュや古い観測が関係する場合だけ、
使用版の仕様に沿って再取得します。

## 修正と取得の確認

- 既存キャッシュの設定修正や、不要になった override の除去を先に検討します。
  pin やパッケージを変える場合は、導入理由と失う機能・互換性を確認します。
  キャッシュ利用のために機能や署名検証を無断で外しません。
- 確認済みの配布先での不在と、未調査の配布経路を分けます。
  配布 job など必要な確認が残る間は、新しいビルド・配布手段の必要性は未判定です。
  既存経路で取得できないと確認してから、別のビルド済みパッケージや CI での配布を比較します。
  新しい配布基盤の導入を診断の前提にしません。
- ローカルビルドの回避を実証する場合は、対象出力が未存在の環境で取得します。
  ローカルビルドを禁止し、remote builder も使わずに成功したかを確認します。
  利用中の store は消さず、必要なら承認範囲内の隔離 store を使います。
  隔離 store での成功は配布物を取得できる証拠です。通常の daemon 経路の信頼設定は
  別に確認し、その経路の取得予定・取得結果と混同しません。
  既存 store の再利用だけなら、初回取得は未確認と報告します。
- 適用まで依頼されていれば、修正後の通常の build / switch 経路と、維持する機能を確認します。
  dry-run や単独出力の取得だけで、構成全体の適用成功とはしません。

## 結果

対象版・system・出力、失敗を生む設定または配布差、修正後の取得結果、機能確認を示します。
「この構成では必要」「既存の配布物で回避可能」「別途ビルド・配布が必要」を、
調べた経路と証拠の範囲で答えます。診断完了と、修正・適用・初回取得の完了を区別します。

コマンドと設定は使用版の [Nix マニュアル](https://nix.dev/manual/nix/stable/) で確認します。
主な参照先は [build](https://nix.dev/manual/nix/stable/command-ref/new-cli/nix3-build)、
[path-info](https://nix.dev/manual/nix/stable/command-ref/new-cli/nix3-path-info)、
[store info](https://nix.dev/manual/nix/stable/command-ref/new-cli/nix3-store-info) です。

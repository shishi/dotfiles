# テストは赤から始める

このスキルはテストを書くと決めた後の作法。テストを書くかどうか・何件書くかは
オーバーエンジニアリング禁止規約(依頼された挙動を証明する最小限)で先に決める。

新しい振る舞いをテストで証明するときは、テストを先に書いて実行し、失敗メッセージを読んで
狙った振る舞いの不在が理由になっていることを確認してから実装に入る。
既存の振る舞いを固定する characterization test だけは test-after が正当。

**Why:** 実装のあとに書いたテストは生まれた瞬間から緑で、「振る舞いを検証している」のか
「無関係な何かにマッチしている」のか区別が付かない。事後にコードを壊して確かめる
ミューテーション確認は代わりにならない。自分が選んだ壊し方に対してしか落ちないため、
都合のいい壊し方を選んで自分を騙せる。

**静的テストで自分を騙す典型**: ある関数の呼び出しを検査するつもりで、
**定義本体の中の 1 箇所**を消して「落ちた = 歯がある」と判断する。実際に守りたいのは
**呼び出し側の複数箇所**で、そちらを消しても緑のまま通る。順序バグ(解放 API を
ファイル削除の後に呼ぶ等)を捕まえるのは振る舞いテストだけで、静的テストは捕まえない。

**How to apply:**

- 実測でバグを突き止めた時点で再現条件は手元にある。まずそれを失敗するテストに書き下す
- 観測できるなら振る舞いで観測する。ソース文字列の照合に逃げるのは、振る舞いテストの
  足場が本当に高いと確認したあとだけ
- 静的テストは RED-first でも不十分。機能追加前は文字列自体が存在しないので素朴な
  正規表現でも RED→GREEN が成立する。「この正規表現がマッチしたまま約束した振る舞いを
  壊す方法は何通りあるか」を先に列挙し、その中からミューテーションを選ぶ
- 照合対象は行番号で範囲を切り出してから見る。件数も固定する。範囲を絞らない
  (?s) ＋遅延量指定子はブロックを飛び越えて後方にマッチし、ほぼ必ず歯を失う
- ミューテーション確認の復元に git checkout を使わない。未コミットの作業を巻き戻す。
  先にコミットするか、ファイルを別名で退避してそこから戻す
- LLM の判定を含む部品は、決定的な配管(入出力の組成・パース・分岐)だけを
  スタブでテストする。判定品質そのものをテストで固定しようとしない — 非決定的で
  正解が主観の対象に assertion を書くと、停止条件の無いプロンプト調整ループになる。
  判定品質は実運用の誤判定を観測してからプロンプトを直す。対象の hook・gate を
  配線したまま、その hook 自身が block する種類の作業でテストを開発しない
  (自分の停止が被験体に妨害される)

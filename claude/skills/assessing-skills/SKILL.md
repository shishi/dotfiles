# skill が役に立っているかを判定する

skill が役に立っているとは、その skill がエージェントに生ませる行動に利用者にとっての価値があり、その skill が実際の作業の中で従える形になっていて、読んだエージェントが実際にその行動をとることです。判定はこの 2 つ (行動の価値と実用性) で行い、使われた回数、担う場面が起きた回数、更新日、本文の長さでは決めません。開かれた回数は、担う場面がどれだけ起きたかと、開かれるべきでない場面で開かれた回数が混ざった値で、その場面での行動が良くなったかを表しません。めったに起きない場面で大きな失敗を防ぐ skill もあれば、毎回読まれても行動を変えない skill もあります。

skill はエージェントの結果を悪くすることもあります。[SkillsBench](https://www.skillsbench.ai/skillsbench.pdf) の測定では、人が整えた skill が平均で合格率を 16.2 ポイント上げた一方、84 タスク中 16 タスクで下げました。著者は、モデルが元からうまくこなせる作業で、食い違う指示や余計な複雑さが加わることを原因の候補として挙げています。エージェントが自分で書いた skill は平均で効果がありませんでした。そのため、行動の価値は本文に書かれた意図ではなく、skill ありとなしで実際に生まれる行動と結果の差で確かめます。

## 1. 生む行動と、その価値を書き出す

判定を頼まれた skill はすべて判定します。「既存の skill」のように対象を名指ししない依頼は、由来の一覧にあるすべての skill が対象です。複数の skill を判定するときは、すべての skill について手順 1〜3 で本文・記録・呼ばれ方を確かめ、手順 2 の実行は、そこで問題が見つかった skill と、判定を決めるのに試行が要る skill から流します。使用枠や時間を理由に対象を減らしません。足りない見込みなら、残る試行の本数と見積もりを示して、どこまで流すかを利用者に決めてもらいます。

1. 対象の skill の description と、SKILL.md・references/ の全文を読みます。`agent-shared/skill-sources.tsv` で由来の種類を確かめます。判定は由来の種類によらず同じ基準で行い、直すときの編集先は `docs/agents.md` の「skill の由来と編集先」に従います。
2. その skill がエージェントに生ませる行動を、作業メモに具体的に書きます。どの場面で、どの判断や操作を、どう変えるか。根拠は skill の本文と、作られたときの commit のメッセージ・依頼です。Git で管理する skill は `git log --follow` で辿れます。Git で管理しない skill は、取得元の版と overlay の履歴で辿ります。
3. その行動の価値を、利用者が得るものとして書きます。防ぐ失敗とその損害 (データ消失、手戻り、利用者が同じ説明や訂正を繰り返す手間など)、実現する結果、守る利用者の方針です。利用者が示した価値観・方針 (記憶・共通指示) と照らし、その行動が利用者の望むものかを確かめます。利用者の方針に反する行動を生む skill は、価値がありません。
4. その行動を、skill が無くてもモデルが既にとるかを考えます。とるなら、skill が足す価値は小さく、手順 2 の比較で確かめます。
5. 同じ行動を生ませるほかの skill・共通指示・hook を探します。対象の skill の名前と、生む行動を表す語で repo を検索し、参照し合う skill も読みます。

生む行動や価値を書けない skill は、それ自体が判定の材料です。

## 2. 実用的かを確かめる

実用的とは、エージェントが判断する時点でその skill を読み、書かれたとおりに従えて、その結果として手順 1 の行動と価値が実際に生まれることです。本文、過去の記録、実行の 3 つで確かめます。

- **本文**: 判断する時点で観測できる条件で書かれているか。とるべき操作が具体的か。手元の道具・権限・環境で実行できるか。手間と費用が、防ぐ損害や得る結果に見合うか。ほかの skill・共通指示と食い違わないか。
- **過去の記録**: 担う場面が実際の作業で起きたとき、skill が開かれ、手順 1 の行動が起きたか。skill を開かずに同じ行動が起きていたか。記録から言えるのは、その場面と、実際に確かめた行動についてだけです。確かめ方は [references/usage.md](references/usage.md) にあります。
- **実行**: 担う場面の実際の依頼 (その skill を作るきっかけになった失敗を含む) と、似ているがモデルが元からうまくこなせる依頼で、skill ありとなしを同じ条件で流します。改訂の良し悪しは旧版と比べますが、skill そのものが役に立つかは skill なしと比べて決めます。skill を外した条件の作り方、混入した試行と止まった試行の扱い、版を伏せた判定役による採点は [empirical-prompt-tuning](../empirical-prompt-tuning/SKILL.md) に従います。その結果を判定には次のように使います。
  - 採点項目ごとの区分のうち、両方成功の項目は、skill が足す価値が無いことを示します。両方失敗の項目は、skill があっても必要な行動を生めていない (実用的でない) ことを示し、判定から外しません。
  - 「なし」側の試行が、本文の混入か作業の停止ですべて比較から外れた CLI では、効果を確かめられないので、その CLI の判定は保留にします。

試行の実行は利用者の使用枠や費用を使います。実行の前に、本数と見積もりを [investigation-discipline](../investigation-discipline/SKILL.md) の「費用の確認」に従って決めます。Claude Code と Codex の両方で確かめ、片方の結果をもう片方に当てはめません。

## 3. 呼ばれ方と費用を確かめる

価値のある行動を生む skill も、必要な場面で読まれなければ働きません。次は判定の補助として確かめます。

- **呼ばれ方**: 実際の依頼の言い回しで、呼ばれるべき依頼と、語は重なるが別の作業を求める依頼を作り、新しいプロセスで skill が開かれるかを確かめます。過去の記録で担う場面に開かれていなかったときは、[references/usage.md](references/usage.md) の手順 4 で一覧・文脈・行動を確かめます。description は、一覧に載っていて開かれなかった場合だけ原因の候補にします。
- **費用**: description の文字数 (一覧に description が載る限り毎回入る)、本文と references の文字数 (読まれたときに入る)、試行で測った時間とトークン。

## 4. 判定する

手順 1・2 で確かめた行動の価値と実用性から、skill ごとに次のどれかに判定します。判定には、どの値・引用が支えているかを添えます。

- **残す**: 生む行動に価値があり、実際の作業で従えて、skill なしでは生まれない (または生まれにくい) その行動が skill ありで生まれる。skill なしでも同じ行動が生まれる場合は、利用者が明示的に求めた要件を守るために置いている skill だけを残します。
- **直す**: 行動に価値はあるが、従えない箇所 (観測できない条件、実行できない手順、ほかの規則との食い違い) がある、必要な場面で呼ばれない、一部の場面で結果を悪くする、本文の一部を削っても結果が保たれることを試行で確かめた。直し方は [improving-skills](../improving-skills/SKILL.md) に従います。
- **統合する**: 同じ行動をほかの skill・共通指示・hook が生ませている。どちらに寄せるかは、判断する時点で読まれる位置と実用性で決め、[create-rule](../create-rule/SKILL.md) の「依頼と配置」に従います。
- **外す候補**: 手順 1 で書いた行動のすべてについて、価値がないこと (skill なしでも同じ行動が生まれる、利用者の方針に反する) を、過去の記録か手順 2 の実行で確かめた。または、直しても実際の作業で従える形にできない。一部の行動しか確かめられなかったとき、見込みが推測だけのときは、外す候補にせず保留にし、確かめていない行動を示します。同じ知識が記憶など別の場所にあることが理由なら、外す候補ではなく統合するとして扱います。外すと利用者が失うものと根拠を示して、利用者の判断を待ちます。利用者の承認なしに、skill を消したり無効にしたりしません。
- **保留**: 手順 1・2 で価値か実用性を確かめきれず、上のどれにも決められない。確かめられなかった点と、確かめるのに要る試行・費用を示します。

次の点を守ります。

- 使われた回数、担う場面が起きた回数、更新日、本文の長さを、判定の理由にしません。担う場面がめったに起きないことは、その場面で skill が生む行動の価値を下げません。
- 利用者が明示的に求めて置いた skill (作業の入口として必ず開く skill など) は、その目的を保つ直し方だけを示します。費用を理由に外す・弱めることを推奨しません。
- 確かめられなかったことを、価値がない根拠にしません。

## 5. 報告する

skill ごとに、生む行動とその価値、実用性で確かめたこと (本文・記録・実行の結果と条件)、判定、その判定で利用者が得るものと失うもの、推奨を示します。外す候補と、利用者が決めることは先に置きます。判定に基づいて skill を直すときは improving-skills、配置を変えるときは create-rule に進みます。

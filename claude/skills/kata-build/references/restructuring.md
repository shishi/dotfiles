# 構造の整理

振る舞いを変えずにコードの構造を変えるときに読みます。kata の工程 4 の中でも、kata を経ない作業でも同じです。

振る舞いを変えずに構造だけを変える整理 (名前の変更、関数の抽出、並べ替え、使われないコードの削除、整形) は、振る舞いの変更と別の commit にします。変更しにくい構造が先にあれば整理を先に commit します。振る舞いを変えた後に整える場合も、別の commit にします。

整理するのは、今回の変更を妨げる具体的な構造の問題がある場合と、整理を依頼された場合だけです。通常の実装や修正のたびに別のリファクタリングを足しません。先に行うのは、小さく今回の変更を安全にする整理だけです。大きい整理や今回の焦点から外れる整理は行わず、振る舞いの変更を進め、その整理の必要を最後の報告に書きます。

振る舞いは出力だけでなく、呼び出し元との取り決め全体です。受け付ける入力、入力の検証と変換、出力、副作用、発生するエラーとその条件のどれかが変われば、振る舞いの変更です。出力が同じでも、必須の引数の追加、引数の削除・型やキーワード名の変更、検証を厳しくする・緩める、既定値の変更は振る舞いの変更です。変更の前後でテストが通っても、証明できるのはテストが覆う範囲だけです。差分をこの取り決めと突き合わせて分類します。テストの失敗は調べる対象であり、それだけで振る舞いが変わった証拠にはなりません。

どこまでが振る舞いかは文脈で変わります。外から使われる面が振る舞いで、その内側は組み替えられます。

| 文脈 | 振る舞いに含むもの | 組み替えてよい内側 |
|---|---|---|
| フロントエンド | 表示と操作への反応。外部が参照する CSS クラス名、テストが参照する DOM 構造 | コンポーネントの内部、hook、状態の形 |
| バックエンド | API の応答スキーマ、HTTP ステータス、副作用 | サービスの内部、クエリの組み立て |
| CLI | 出力の形式、終了コード、フラグ名 | 引数の解析処理、内部の関数 |
| ライブラリ | 公開しているすべてのシンボルとシグネチャ | 非公開の関数・モジュール |

ライブラリは誰がどう使うかを把握できないため、公開面の変更はすべて利用者にとって振る舞いの変更です。

重複は、誤った抽象化より安く済みます。次の場合は共通化せずに重複を残します。

- 読めば分かる単純な定型 (空の値の生成、エラーを返すだけの行など)
- 共通化しても間接参照が増えるだけで、分かりやすくならない
- 今は同じでも、今後それぞれ別に変わりうる
- その場に書いてあるほうが検索で見つけやすい

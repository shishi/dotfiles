# 工程 4: task を実装・検証する

[kata](../kata/SKILL.md) の工程 4 を進める手順です。次へ進む条件は kata の工程表にあります。

計画は考える作業を済ませています。この工程では計画どおりに実行し、各ステップを、失敗から通過まで見届けたテストで証明します。会話の記憶は文脈の圧縮を越えて残らず、記録を失った実行者は commit 済みの task を作り直してしまうため、記憶を失っても再開できる記録を残します。

## 着手前の準備

1. 計画ファイルと、計画が参照する設計を一度読みます。設計は計画の根拠であり、計画の中の矛盾は設計に照らして解きます。設計を読めない場合は `progress.md` にその旨を書き、以後の判断を暫定として扱います。
2. 計画と同じディレクトリの `progress.md` を確かめます。無ければ、1 行目を `# 進捗 — 計画: <計画ファイルのパス>` として作ります。あれば読み、現在の tree・HEAD と照合します。記録と一致する task は再実装しません。差分があれば影響する検証を更新します。文脈の圧縮の後は、自分の記憶より `progress.md` と `git log` を信じます。
3. Task 1 の前に、task 間の矛盾を一度だけ照合し、結果を `progress.md` に表で残します。
   - 前の task の出力を使う task ごとに 1 行: 二つの task、提供する側の「提供する」と使う側の「使う」の照合結果
   - task ごとに 1 行: 指定したテストと指定したコード、作るファイルと後で触るファイルが食い違わないか
   - 計画が明示的に求めるのに、レビューで欠陥とされる内容 (何も確かめないテスト、ロジックの丸写しなど)

   共有するインターフェースが無ければ `事前照合: 共有するインターフェースなし` の 1 行で足ります。見つけた矛盾は、下の「判断の記録」で決めてから Task 1 に入ります。実装して初めて分かる矛盾は、レビューで拾います。

## task ごとの手順

1. 基準版 (`git rev-parse HEAD`) と未コミット差分の有無を `progress.md` に記録します。レビューの範囲はこの基準版から切ります。`HEAD~1` で代用すると、複数 commit の task の差分が欠けます。計画のその task の本文を毎回読み直します。覚えている内容は要約なので、値・シグネチャ・テストは本文から取ります。
2. ステップを順に実装します。文書・skill・コードコメント・commit を書くステップでは、書く前に [writing-prose](../writing-prose/SKILL.md) を開き、その「併用する skill」に挙げた該当 skill をすべて同時に使います。テストを作成・変更するときは [test-red-first](../test-red-first/SKILL.md) で赤 → 緑 → 必要な整理を進めます。既存実装を機械的に削除せず、必要な旧版で赤を確認します。テストを追加するかは共通指示で判断し、文書変更に製品テストを一律に増やしません。コードの構造を変える場合は、[構造の整理](references/restructuring.md) に従います。
3. コマンドを実行するステップでは、出力を読んで計画の「期待する結果」と比べます。
   - 一致する: 次のステップへ進みます。
   - コードが誤っている: [investigation-discipline](../investigation-discipline/SKILL.md) で原因を突き止めて直します。出力を合わせるための対症的な修正はしません。
   - 計画が誤っている: 設計と矛盾するステップ、前の task のインターフェースと合わない入力、動かないコマンドなどです。設計を満たす最小の変更を決め、「判断の記録」に残して続けます。

   長い出力は計画のディレクトリのファイルへ保存し、末尾と必要な箇所だけを読みます。表示した出力は以後ずっと文脈に残るためです。
4. 次をすべて、この session の証拠で満たしたら task の検証を終えます。差分の見た目からの推測では足りません。完了を主張する前に、[kata-verify](../kata-verify/SKILL.md) の手順で主張ごとの証拠を確かめます。
   - task の本文が挙げるテストがすべて存在し、この task で実行して出力を読んだ
   - task 全体の最後のテスト実行が通った
   - 「期待する結果」をすべて実際の出力と比べた
   - 計画からの逸脱のすべてに、判断の記録がある
5. `progress.md` に `Task N: verified (review pending)` と、基準版・変更ファイル・内容の識別情報・検証コマンドと結果・証拠の場所を残します。記録は作業と同じ時点で書き、数 task 分をまとめて後から書きません。
6. 下の「実行方式と区切り」の順でレビューと commit を済ませたら、`Task N: complete (commit <sha>)` を追記します。
7. 全 task を終えるまで 1〜6 を繰り返します。司令塔が直接実行する方式では、レビューと commit を最後にまとめて行うため、各 task では 1〜5 を進め、6 は最後の commit の後に全 task 分を書きます。task の間に途中経過の報告や「続けますか」で止まりません。止まってよいのは、[kata-plan](../kata-plan/SKILL.md) の手順 8 に挙げた場合だけです。
8. 全 task を終えたら kata の工程 5 (独立レビュー) へ進みます。`review-gate` へは、計画の「全体の制約」と「レビューの重点」を逐語で渡し、`progress.md` の判断の行も示します。レビューの重点は、テストが扱わない条件を reviewer が個別に確かめるための入力です。司令塔は工程 6 の照合で完了を確かめたら `~/.agent-shared/bin/kata-active claude done` で実装中の記録を消します。kata-active の記録は司令塔のセッションのものなので、委譲された実装担当は `kata-active` を実行しません。

## 判断の記録

- 計画の矛盾・曖昧さ・欠陥は、利用者に尋ねて止まらず、設計を根拠に自分で決めます。設計にも計画にも答えが無い点は自分の判断で決めます。
- 決めたら `progress.md` に `Task N: 判断: <決めた内容> — <理由> — <誤りだった場合の影響>` と残して続けます。記録の無い逸脱は、誰にも見えない決定になります。同じインターフェースに触れる後の task は、この記録を読んで引き継ぎます。
- 自分で決めてよいのは、依頼と設計の範囲内にある計画の欠陥です。利用者の要件・必須条件を変える必要がある場合、目的と許容困難なリスクが衝突する場合は、共通指示に従って人間の判断を待ち、依存しない task は続けます。
- 完了の報告では、記録した判断をすべて、決めた順に、誤りだった場合の影響とともに示します。利用者が、代わりに決められた事項を確かめて誤りを直せるのは、この一覧だけです。

## 実行方式と区切り

### 子へ task を渡す方式

task ごとに新しい実装担当へ必要な入力を渡します。親がその task の検証・独立レビュー・commit を済ませてから、それに依存する次の task へ進めます。レビュー経路が利用不能でも、依存せず対象が重ならない仕事は別 worktree で続けられます。保留中の差分を混ぜず、それぞれの全差分をレビューし、最後に branch 全体の統合もレビューします。

依頼文の内容、担当に求めること、報告の状態ごとの扱い、task の独立レビューと指摘の修正は、担当を起動する前に [子へ task を渡す手順](references/delegation.md) を読んで従います。

### 司令塔が直接実行する方式

各 task を検証して次へ進み、最後に branch 全体を新規担当で独立レビューします。task ごとのレビューが無い分、上の「task ごとの手順」の完了条件と `progress.md` の記録で、各 task の確かさと再開の手がかりを保ちます。再開時は `progress.md` の記録と現在の tree・証拠を照合します。最後に確定する commit 範囲は、まとめて確定した task 群の範囲として扱い、task 別の変更・証拠は `progress.md` で区別します。

## 委譲と commit の順序

- 親が直接実行するか子へ任せるか、モデル・推論量・利用枠・代替は [agent-delegation](../agent-delegation/SKILL.md) で判断します。
- 同一ファイルの writer は一人とし、実装担当を並列に動かすのは、対象が重ならず worktree を分けた場合だけです。最上位だけが他 CLI を起動し、受託側は追加の独立レビューや別 CLI への再委譲をしません。実行記録は既存 adapter の手順を維持します。
- 委譲する実装担当は変更と検証結果を返します。親が実物の照合と独立レビューを済ませてから、自分の変更だけを commit します。
- `review-gate` へは、task 開始時の基準版と作業差分・untracked・証拠を渡します。最終レビューでは branch 全体の基準版からの差分も含めます。親が通過を確認して commit した後に、`progress.md` の完了行を書き、その commit・証拠と照合します。検証した作業 tree と記録する commit に差分があれば、結果へ影響しないことを確かめます。影響する場合は記録対象の版で検証します。実装担当の作業完了報告を、独立レビュー・commit 済みの記録にしません。
- 再開時は現在の HEAD・変更・未達を `progress.md` と照合します。完了行だけで完了と判断しません。短い仕事へ専用の記録機構を追加しません。

## 避ける判断

| 考え | 実際 |
|---|---|
| task の内容は覚えている | 覚えているのは要約です。値・シグネチャ・テストは本文から取ります。 |
| 全テストは最後にまとめて流せばよい | ステップごとの実行が、どのステップで壊れたかを示します。task の最後の実行は完了条件であり、途中の実行の代わりになりません。 |
| 計画が誤っているので、正しいほうを黙って実装する | 正しいほうを実装し、判断を記録します。 |
| 進捗は数 task 後にまとめて書く | 文脈の圧縮は都合のよい時点を待ちません。task ごとに、作業と同じ時点で書きます。 |
| 自分の差分を丁寧に読んだので独立レビューは要らない | 同じ作者は同じ見落としをします。`review-gate` を省きません。 |
| 変更は小さいのでテストは通るはず | 「はず」は証拠になりません。コマンドと出力で確かめます。 |

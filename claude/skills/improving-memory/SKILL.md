# 記憶を直す

記憶への変更は、新しい文をどこに足すかではなく、変更後の記憶が、必要な場面で取得され、読んだだけで正しく判断できる構成になっているかで決めます。記憶の検索は語句の一致で候補を示し、エージェントが選んだファイルの本文 (条件が合えば該当の節) を渡します。渡した本文の中で、新旧の主張のどちらが今のものかを示す仕組みはありません。新旧が両方残っていれば、読むエージェントはどちらが今の主張かを推測で決めます。文を足し続けた単位は話題が混ざって大きくなり、起動時に注入する記憶では上限を超えて本文ごと省かれます。そのため編集の方法は削除・再構成・分離を先に検討し、追記は最後に選びます。

この skill は、編集の方法を選び、本文を直し、変更を確かめて、検証済みの patch を作るまでを担います。保存は呼び出し元が一度だけ行います。日々の保存は [capturing-memory](../capturing-memory/SKILL.md) の「書き込み」、全体の整理は [memory-consolidate](../memory-consolidate/SKILL.md) が保存し、この skill を単独で使ったときも capturing-memory の「書き込み」の helper で保存します。

## 1. 対象と周辺を読む

1. 記憶 repo の確定 commit を基準に記録し、その版の `CONVENTIONS.md` を読みます。同じ版を会話で読んでいれば読み直しません。編集は Git 管理外の一時 clone の `main` を基準版に揃えて行い、記憶 repo を直接編集しません。
2. 直す単位 (ファイル・節・箇条) を含むファイルの全文を読みます。一部の節だけを読んで直しません。
3. 索引 `MEMORY.md` と語句検索 (`bash ~/.agent-shared/hooks/inject-memory.sh <記憶 repo> lookup '<検索語>'`) から、同じ対象・同じ原則・同じ原因を扱う記憶を、新しい知識と直す主張の対象名・操作・症状で探して全文を読みます。重複と矛盾は書き込み先のファイルの外にも及ぶためです。分担して直すときも、割り当てられたファイルは書き込む範囲で、読む範囲は記憶 repo 全体です。使った検索語と全文を読んだファイルを作業メモに残し、手順 5.2 の照合に使います。記憶が参照する AGENTS.md・skill・repo の文書も、関係する箇所を読みます。
4. 変更の動機 (保存する新しい知識、指摘、観測した失敗) を確かめます。保存するかどうかは先に [assessing-memory](../assessing-memory/SKILL.md) で、置く範囲は capturing-memory の「保存範囲の判定」で決めます。

## 2. 主張の一覧を作る

変更前の対象を、文ではなく、意味を独立して確かめられる主張 (事実、方針、適用条件、例外、根拠、再確認の条件) ごとに作業メモへ書き出します。各主張には、それを支える原文 (変更前の記憶の文、本人の発言、一次資料) と、根拠を確かめた結果 (確かめた、誤り、確かめられない) を添えます。今回の新しい知識も、支える原文と一緒に加えます。この一覧は、再構成の後に主張が落ちていないか、元に無い主張が入っていないかを確かめる基準で (手順 5)、確かめられない主張を全体で把握する材料にもなります。作業メモと試行の記録は Git 管理外の private な場所に置きます。

## 3. 問題を見つける

主張の一覧と本文を突き合わせ、次の問題を探します。見つけた問題は、新しい知識を入れる箇所かどうかにかかわらず、同じ編集で直します。判定に取得回数・更新日・文字数だけを使いません。記憶の価値と実用性は assessing-memory の基準で判定します。

| 問題 | 見分け方 | 直し方 |
|---|---|---|
| 誤り・古い主張 | 主張が、種類に合う根拠と食い違う。現在の設定・挙動なら今の設定ファイル・コードと通常の操作、OS・版を限定した実測ならその条件と測定結果、本人の価値観・方針なら元発言と撤回・後継方針が根拠です。ファイルやコマンドが現存するだけでは、書かれた挙動まで確かめたことになりません | 根拠で無効と確定した主張を消すか、正しい主張に置き換えます。別の版の現在値が変わっても、元の条件で再利用する実測は無効にしません。安全に使える経路を調べても確かめられない主張は誤りと区別し、確かめられない範囲と再確認の条件を残します。期限のある状況 (旅行・一時的な設定など) は終了を確かめたものだけを消し、確かめられなければ `CONVENTIONS.md` に従って本人に確認します |
| 矛盾 | 同じ条件の下で両立しない結論を述べる主張がある | 先に条件 (OS・版・プロジェクト・適用範囲) を揃えます。条件が違うだけなら矛盾ではないので、各主張に条件を書いて区別します。矛盾なら、現行の事実・明示的な撤回・後継方針で正しい側を決め、もう一方を消します。消した主張を、変更前の内容や変更の日付を書いた注記 (「以前は X」「X から変更」など) や優先順位の注記の形で残しません。古い内容は記憶 repo の Git 履歴に残ります。撤回したこと自体が今後の判断を変える (撤回された案を再び提案しない) 場合は、その判断を今の方針として書きます。どちらが正しいかを推測で決めず、決める根拠が本人の判断にしか無いときは本人に確認します |
| 重複 | 同じ主張が、複数の記憶、または記憶と AGENTS.md・skill・repo の文書にある | 主張と根拠・適用条件を一か所に残し、ほかは削るか参照に替えます。手順は AGENTS.md・skill に置き、記憶には写しません。写した手順は元の手順が変わっても古いまま残ります。本人が示した価値観・好み・訂正を記憶に残すかは、assessing-memory の手順 1.3 で判定します。言い回しが違う重複は、片方だけが持つ条件を主張の一覧で確かめてから一つにまとめます |
| 事例の列挙 | 同じ原因・同じ原則から出た事例・例外・症状が、一件ずつ箇条や但し書きとして並んでいる | 事例に共通する原因か原則を言葉にし、それを書く文に置き換えます。原則は事例に共通することだけで書き、事例が支えない範囲 (別のコマンド、別の環境など) へ広げません。事例は原則の理解に要る範囲で例として残します。新しい事例を入れるときも、既存の原則に入るなら事例を足さず、入らないなら原則そのものを見直します。共通の原因を確かめられない事例や、条件ごとに測定結果が違う実測 (版ごとの実測など) は、原則から導けないので条件付きの観測として残し、条件で整理します |
| 単位の切り方 | 一つの単位が、使う場面・適用範囲・更新の契機が違う話題を抱えている。または逆に、同じ場面で取得し共通の条件で一緒に更新する知識が、別々の単位に分かれている。一つの箇条に別々に確かめられる主張が足し続けられている、題名と description で中身を一行で言えない、起動時の注入の上限で本文が省かれる、検索の候補に頻出するのに取得されない (memory-consolidate の測定で分かります) のは調べる手がかりです | 単位は、同じ場面で取得し一緒に更新する知識のまとまりで切ります。話題が混ざった単位は話題ごとに分け、分かれた同じ話題は一つにまとめます。各単位には、それだけで判断できる適用条件・理由・例外を持たせ、共通の条件は一か所に置いて参照します。分けた単位どうしは、元の単位と分割先の間も含めて、互いに参照 (`[[.md を除いた記憶 repo 内のパス]]`、例 `[[projects/github.com-shishi-dotfiles]]`) を張ります。内容は写しません。分けた先の置き場も capturing-memory の「保存範囲の判定」で決めます。プロジェクトをまたいで再利用する実測は root の記憶へ分け、そのプロジェクトだけの知識は `projects/<slug>.md` に残します。`projects/<slug>.md` は起動時に slug で注入されるので、別のプロジェクトの記憶と統合しません。題名が似ていることや文字数だけでは統合・分割しません |
| 価値の無い記述 | assessing-memory で価値が無いと判定した記述。一回限りの作業記録・経緯 (失敗談、指摘された回数、セッション ID)、repo・skill・AGENTS.md がすでに書いている事実や手順の再掲、その場限りの指示、ほかの作業の判断を変えない個別の決定、「重複させない」などのメタ注記がよくある例です | assessing-memory の「消す」に示した根拠を確かめてから削ります。行動を変える技術的な因果 (「A だと B が壊れるので C する」) と、その決定を超える理由や原則は残します。経緯を削るときも、一回限りの承認や判断を今後の規則へ書き換えません |

## 4. 編集の方法を選び、書く

変更ごとに、何もしない、削除、置き換え・再構成 (統合を含む)、分離・移動、追記の順に当てはめ、最初に成り立つ方法を使います。新しい知識を一件保存するときも、書く前にこの順で判定します。方法を決めたら本文を書き換える前に、手順 5.3 の取得確認が要るかを判定し、要るなら実例を選びます。その記憶が必要になる場面から質問と必要な事実・適用条件を選び、正解を変更前の本文や元発言から決めます。変更後の文に合わせて正解を作らないためです。

- 何もしないのは、同じ主張が既にあり、手順 3 の問題も無い場合です。
- 新しい知識が既存の主張を変える・否定する・既存の原則の事例である場合と、入れると単位に話題が混ざる場合は、手順 3 の直し方で既存の文ごと直します。
- 追記を選ぶのは、新しい知識が手順 1 で読んだどの記憶の主張とも重ならず、否定もせず、既存の原則の事例でもなく、足した後も単位が一つの話題のままの場合だけです。起動時に注入する記憶 (`CORE.md`・`projects/<slug>.md`) では、足した後も注入の上限に収まることも条件です。どの単位の話題にも入らない知識は、新しいファイルにします。
- 追記するときも、その主張が属する節の流れの中に書きます。箇条の末尾に別の主張や「ただし」を付け足しません。
- 単位を書き換えるときは、差分を小さくすることを目的にせず、主張の一覧から単位全体を書き直します。書き直しは再編であって再分析ではありません。主張の一覧に無い事実・規則・範囲を作りません。

書くときは次に従います。

- 文章は [writing-prose](../writing-prose/SKILL.md) の規約で書き、用語は記憶の中で一つに揃えます。相対日付は絶対日付に直します。
- 題名・`description`・索引の行は、その記憶を探すときに使う対象名・操作・症状で書きます。索引には本文や手順を写しません。
- 現在の状態と条件付きの実測を区別し、確かめていない主張を確かめたと書きません。技術的な実測には、適用する OS・環境・版と根拠を残します。適用範囲の判断に要る確認日は、経緯として消しません。
- 変わりやすい現在の状態 (PR の待ち状態、導入済みの版など) は、その状態を確かめられる場所への参照と再確認の条件に置き換えます。
- 統合・要約では、結論だけでなく適用範囲・理由・例外・変更や撤回の条件を残します。重要な訂正の根拠が要るなら元発言や検証結果への参照を残し、会話全文を写しません。
- 個人マシン名・私的なパス・接続先は、再利用に要るなら private 記憶に残します。一般化できることを、公開文書へ移す理由にしません。
- `retrieval: sections` は、共通の条件が最初の `##` より前にあり、各 `##` 節を単独で読める技術リファレンスだけに付けます。付いた記憶を直すときも、各節が単独で読める状態を保ちます。条件の所在や節どうしの依存が曖昧になったら指定を外し、全文取得にします。

## 5. 確かめて patch を作る

1. 変更後の本文の主張ごとに、主張の一覧のどの原文が支えるかを対応づけます。書き換えた主張は、原文がその操作・適用範囲・継続期間 (一回限りか今後もか) まで支えるかを確かめ、支えない部分を消します。LLM による書き換えには、元に無い内容が混ざる、条件や例外が落ちるおそれがあります。記憶の commit は独立レビューの対象外なので、この照合は直した本人が行います。
2. 主張の一覧の側からも突き合わせます。残す主張はすべて行き先 (元の単位、統合先、分割先) にあり、消した主張には消した理由 (誤り、矛盾の解消、原則への統合、価値が無い) を作業メモに残します。変更後の本文と、手順 1.3 で全文を読んだ記憶との間に、新しい矛盾・重複・事例の列挙が無く、分けた単位どうしの参照が往復で張られ、参照先が存在することも確かめます。
3. 分割・統合・移動、既存の記憶の題名や索引の行の変更をしたら、取得を確かめます。新しい記憶とそれに対応する索引の 1 行を足すだけの変更は対象にしません。一時 clone の `main` に変更を commit し (この commit は push しません)、一時 clone に向けて hook を実行して、出力が示す取得元の commit が検証用の commit と一致することを確かめます。本文の取得は `bash ~/.agent-shared/hooks/inject-memory.sh <一時 clone> lookup '<相対パス>'`、起動時の注入は `printf '{"cwd":"%s"}' '<作業 repo>' | bash ~/.agent-shared/hooks/inject-memory.sh <一時 clone> core` (プロジェクト記憶は `core` を `project` に替える) で実行します。`core`・`project` は標準入力の JSON を読むので、渡さないと入力を待って止まります。変更前は、同じコマンドを基準 commit の clone に向けて実行します。記憶 repo の作業ツリーで編集しただけでは hook は確定済みの旧版を読むため、取得の確認に使えません。手順 4 で選んだ実例について、索引や候補に出たことだけで成功とせず、取得した本文から必要な判断までできるかを変更前 (基準 commit) と比べます。必要な事実・条件・例外・参照先が落ちていたら、編集を直してから確かめ直します。起動時に注入される記憶 (`CORE.md` と `projects/<slug>.md`) は、hook の出力が上限に収まり本文が省かれないことも確かめます。
4. 確かめた内容を呼び出し元の保存へ渡します。日々の保存と単独で使ったときは、capturing-memory の「書き込み」手順 4 で基準 commit からの patch を作ります。全体整理のように呼び出し元が同じ一時 clone で索引などの編集を続ける場合は、ここで patch を作らず、呼び出し元が最後に一度だけ作ります。削除・新規作成したファイルも patch と変更対象のパスに含めます。

## この方法を選ぶ理由

外の記憶の仕組みも、書く前に編集の方法を選び、記憶を小さな単位とリンクに保つ側に寄っています。Mem0 の論文 ([arXiv 2504.19413](https://arxiv.org/abs/2504.19413)) は、新しい事実を似た既存の記憶と比べてから追加・更新・削除・何もしないのどれかを選び、同じ意味の記憶が無いときだけ追加します。A-MEM ([arXiv 2502.12110](https://arxiv.org/abs/2502.12110)) は記憶を一つの事柄ごとのメモにして関連するメモどうしをリンクし、新しいメモを入れるときに、リンクした既存のメモの文脈の説明や属性も更新します。リンクと更新を外した比較では成績が下がっています。Letta の [共有メモリーの文書](https://docs.letta.com/guides/core-concepts/memory/shared-memory/) は、追記・部分の置き換え・ブロック全体の書き直しを使い分け、全体の書き直しは同時に書くと後の書き込みが勝つので一人の担当に任せるとしています。この記憶では、`--patch` が基準の commit から記憶 repo が進んでいれば適用しないことで、同じ役目を果たします。

Anthropic の Dreaming を自前で組む [クックブック](https://platform.claude.com/cookbook/managed-agents-cma-dreaming-with-a-dynamic-workflow) の整理役は、別の小見出しは分けたまま `[[slug]]` で相互にリンクし、事実を作らず事実の行を消さず (再編であって再分析ではない)、どちらが正しいか推測しないと指示しています。この skill の分割・確認の手順はこれに合わせています。違う点が二つあります。クックブックは矛盾を直すとき置き換えた古い値を日付と出典つきで注記し、決められない矛盾は両方を残して CONFLICT と書きます。複数のエージェントが同時に書く前提で、監査の記録を記憶の中に持たせるためです。この記憶は Git が履歴を持ち、規約が経緯を書かないと決めており、決められない矛盾は本人に確認できるので、注記を残しません。また、クックブックの解析役は既存を確かめてから新しいことを足す追記寄りの書き方で、統合・分割は後で動く整理役が受け持ちます。この記憶の全体整理は依頼されたときにしか動かないので、書くときに再構成します。

反対の例として、Mem0 v3 は書き込みを 1 回の LLM 呼び出しに減らすため追加だけに変え、新旧の事実を並べて残し、今の情報を選ぶのを検索の順位付けに任せています ([移行の文書](https://docs.mem0.ai/migration/oss-v2-to-v3))。この記憶の検索には今の情報を上位にする順位付けが無いので、この方式は採りません。

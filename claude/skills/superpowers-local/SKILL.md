# superpowers の作業ワークフロー

変更作業は、以下の順序と通過条件に従って進めます。共通 AGENTS.md とこの skill を入口に、現在の工程に合う有効な配布版の `superpowers:*` skill を読んで使います。工程内の詳しい実施方法は上流、ローカルの承認・担当・証拠の条件はこの skill と共通指示に従います。上流の更新は plugin 管理機能で取得し、vendor cache は編集しません。

接続を確認した上流版は superpowers 7.0.1 です。使用版を固定する値ではありません。利用時は plugin の登録情報にある版と比較し、異なる版の関連する役割・helper の契約は未確認として照合します。

## 読込と担当範囲

- 工程の開始前に、その工程へ適用する上流 skill の現在版の本文を取得して読みます。同じ版をこのコンテキストで既に読んでいれば再利用します。一覧の説明、ローカル補足、別 skill 内の参照だけでは上流本文の読了にしません。担当が取得できない場合は、確認した経路と不足を司令塔へ返します。司令塔は有効な配布版の必要本文を入力として渡すなど、正規の読込経路を確保します。本文がない工程を実施済みにせず、依存しない作業は続けます。作業に関係しない skill まで一括読込せず、選択を入力の固定文字列の一致で代替しません。
- 呼び出し可能な名前と配布先は、skill 一覧・plugin の登録情報から確認します。キャッシュの固定バージョンを正本として参照し続けません。必要な配布物を取得・読込できなければ、その経路を確認済みにせず正規の更新・復旧経路を調べます。
- この補足が接続する役割・helper の契約は、利用する配布版の実物で照合します。上流の版が変わったときは関連する本文・template・helper の前提と入出力を確認し、旧版と同じ名前だけで適合済みとしません。意味が変わっていれば、この補足の該当接続を直して検証してから使います。
- 上流とローカル補足は一つの作業に適用します。同じ成果物について、独立した計画・実装・検証・レビューを二重に起動しません。

## 開始から終了まで

司令塔は着手時に、成果物・全対象・維持条件・完了を示す観測結果を依頼と実物から定めます。既存の計画・作業メモに、現在の工程・適用する上流本文の読了状態・次へ進める根拠を残し、切替時に確認します。skill 名を宣言しただけでは通過にしません。根拠が足りなければ、それを取得する工程へ戻ります。短い仕事では会話内の簡潔な記録で足り、専用帳票は増やしません。

| 工程 | 担当と上流 skill | 次へ進む条件 |
|---|---|---|
| 1. 目的・設計を固める | 司令塔が `superpowers:brainstorming` で依頼・既存資料・実物を照合します。 | 何を変え、何を保ち、何で成功を確かめるかが具体的です。主要な方式と根拠を定め、上流が project 相当と判断する設計では builder check で計画に必要な不足質問を回収します。本人しか決められない選択と必要な承認は解消してから、その判断に依存する実装へ進みます。 |
| 2. 作業場所と基準版を確かめる | 司令塔が `superpowers:using-git-worktrees` で既存の分離・Git 状態・実行環境を確認します。 | タスクの作業場所と基準版を確定し、他者の変更を保全しています。必要な既存検証で開始時の状態を把握し、失敗・未確認を成功扱いしていません。 |
| 3. 実行可能な計画にする | 複数工程の仕事では司令塔が `superpowers:writing-plans` を使います。 | 各 task の成果物・対象ファイル・依存する入出力・検証方法と合格結果が定まり、元の全要件を覆っています。実行方式と担当を選び、実行 skill が使う実在の計画ファイルを用意しています。 |
| 4. task を実装・検証する | 選んだ担当が `superpowers:subagent-driven-development` または `superpowers:executing-plans` を使います。テスト作成時は下記のテスト手順を適用します。 | task の要求結果を実物で確認し、必要な既存検証を通しています。追加・変更するテストは赤から緑を確認し、通常の入口による独立受入の結果も該当範囲で揃っています。失敗は原因調査へ戻します。 |
| 5. 独立レビューと指摘対応 | 司令塔が `superpowers:requesting-code-review` と `review-gate` で編成します。指摘受領者が `superpowers:receiving-code-review` で採否・修正を進めます。 | 全対象・必要な観点のレビュー結果があり、採用した blocker / should を修正・再検証し、影響する観点の再確認を終えています。受領手順を reviewer 自身の検査方法に割り当てません。 |
| 6. 証拠を確認して確定する | 完了を主張する担当が `superpowers:verification-before-completion` を使います。司令塔が親として照合します。 | 元の全要件と現在の実物・対象版の証拠が一致し、未確認・未達が残っていません。親がレビュー後に承認範囲内の変更だけを commit し、その後に helper の完了記録を確定します。 |
| 7. 統合・保全・後片付け | 司令塔が `superpowers:finishing-a-development-branch` を使います。 | 承認済みの統合・反映を実施して利用先を確認しています。未統合の成果を保全し、自分の不要な作業場所だけを片付けます。push・破壊操作の承認範囲は広げません。 |

工程は作業の規模に合わせます。小さく明確な変更では、既に揃った要件・設計を使い、実行計画 skill を要しない直接作業にできます。既存 checkout の使用条件も共通指示に従います。その判断と根拠を示し、必要な検証・独立レビュー・完了前の証拠確認を「小さいから」で飛ばしません。既存の設計・計画がある仕事や再開時は、現在の実物との一致を確認して該当工程から再開します。

実行方式によって工程 4〜6 の区切りを変えます。

- **子へ task を渡す方式:** task ごとに新しい実装担当へ必要な入力を渡します。親がその task の検証・独立レビュー・commit を済ませてから、それに依存する次の task へ進めます。レビュー経路が利用不能でも、依存せず対象が重ならない仕事は別 worktree で続けられます。保留中の差分を混ぜず、それぞれの全差分をレビューし、最後に branch 全体の統合もレビューします。
- **司令塔が直接実行する方式:** 各 task を検証して次へ進み、最後に branch 全体を新規担当で独立レビューします。各 task の検証後に、その計画の `progress.md` へ `Task N: verified (review pending)` と、変更ファイル・内容の識別情報・検証コマンドと結果・証拠の場所を残します。再開時は上流 helper の未完了判定より先に、この記録と現在の tree・証拠を照合します。一致する task は再実装せずレビュー待ちとして継続し、差分があれば影響する検証を更新します。親のレビュー後 commit に先行する `task-done` / ledger の完了行は書きません。最後に確定する commit 範囲はまとめて確定した task 群の範囲として扱い、task 別の変更・証拠は進捗記録で区別します。

原因調査・テストは次の条件で作業へ組み込みます。

- 不具合・想定外の挙動では、修正案の前に [investigation-discipline](../investigation-discipline/SKILL.md) と `superpowers:systematic-debugging` で観測・原因・既存保証を確認し、原因に対応する設計・計画へ戻します。調査だけの依頼を実装へ広げません。
- テストを作成・変更すると決めたら [test-red-first](../test-red-first/SKILL.md) と `superpowers:test-driven-development` で赤 → 緑 → 必要な整理を進めます。既存実装を機械的に削除せず、必要な旧版で赤を確認します。テストを追加するかは共通指示で判断し、文書変更に製品テストを一律に増やしません。
- 受入の準備は工程 1 から `review-gate` に従って独立担当が始めます。上流の手順と別の実装・レビューを重ねず、同じ対象・目的・前提・証拠が一致する結果を組み込みます。

## 設計・計画と承認

- `brainstorming` と `writing-plans` は、依頼・既存資料で決まった内容を前提に進めます。小さく明確な依頼に、質問や新しい設計書・計画書を一律に追加しません。
- 既に承認された範囲の調査・実装・検証・統合は続けます。上流の設計書・計画書の承認待ち、実行方式の選択メニューを、新たな承認条件にしません。本人にしか決められない選択や、依頼・repo の手順が求める承認は維持します。
- 正式な設計・計画を求められた場合は既存の正式な保存先へ置きます。実行用の計画・進捗・引継ぎは会話や Git 管理外のメモを使い、上流の保存先だけを理由に公開文書を増やしません。
- `executing-plans` / `subagent-driven-development` を使う場合は、上流 helper が読める実在の計画ファイルを用意します。公開文書でなければ Git 管理外へ置き、`Task N` など必要な形式と再開記録を維持します。保存先の変更を理由に、実行入力を会話だけで代用しません。

## 実行と委譲

- 親が直接実行するか子へ任せるか、モデル・推論量・利用枠・代替は共通指示で判断します。上流の実行方式や安価モデルの推奨を、固定の編成にしません。
- 同一ファイルの writer は一人とし、並列 writer は worktree を分けます。最上位だけが他 CLI を起動し、受託側は追加の独立レビューや別 CLI への再委譲をしません。実行記録は既存 adapter の手順を維持します。
- 委譲する実装担当は変更と検証結果を返します。上流が担当側での commit を指示しても、親が実物の照合と独立レビューを済ませてから、自分の変更だけを commit します。
- この順序では、未コミットの作業を commit 範囲だけの `scripts/review-package` で組成しません。`review-gate` へ task 開始時の基準版と作業差分・untracked・証拠を渡し、最終レビューでは branch 全体の基準版からの差分も含めます。親が通過を確認して commit した後に、`task-done` や ledger の完了行を確定し、その commit・証拠と照合します。検証した作業 tree と記録する commit に差分があれば、結果へ影響しないことを確かめ、影響する場合は記録対象の版で検証します。実装担当の作業完了報告を、独立レビュー・commit 済みの記録にしません。
- 長い計画では既存のメモに完了範囲・証拠・判断を残し、再開時に現在の HEAD・変更・未達を照合します。ledger の完了行だけで完了と判断せず、短い仕事へ専用の記録機構を追加しません。

## レビュー・修正と完了

- 上流がレビューを求めたら、対象だけでなく、その段階の template の確認目的・入力・返す結果も `review-gate` へ渡します。設計の builder check なら計画に必要な不足質問、task なら要件と品質、最終なら task 間の統合を、必要なレビューの対応する観点へ割り当てます。同じ対象・前提・証拠の結果だけを再利用し、同じ確認の reviewer を重ねません。操作に影響する実装の独立受入は着手時から準備します。
- 指摘は元の依頼と実物で採否を判断します。根拠がない指摘のために固定回数まで修正を繰り返さず、採用した欠陥は修正・再検証します。不明点が一つあっても、依存しない作業は続けます。
- 上流に固定回数で修正を終える手順や再レビューしない指示があっても、要件未達を完了扱いしません。修正が影響する範囲・観点を再レビューし、未達がある間は通過・完了としません。収束と停止は共通指示に従います。
- 完了前に元の全要件と実物・検証結果を照合します。同じ対象版・前提の証拠は再利用でき、報告のたびの同一コマンド再実行は要求しません。変更で影響した証拠、失敗・未検証の条件は回収します。

## 環境・Git・専門作業

- 環境は Nix → Docker → その他を優先します。上流の worktree 準備を理由に package manager を一律に起動せず、読解・編集だけなら環境を起動しません。既存のタスク用 worktree は再利用します。
- 統合前の競合予測と稼働設定の保全、未コミット変更の保持、統合後の関連検証を維持します。`finishing-a-development-branch` の選択メニューは既存の承認に従い、未承認の push・破壊操作はしません。
- 後片付けは作成主体・使用状況・成果の保全を確かめます。ディレクトリ名だけで所有者を決めず、使用中・未統合の worktree や未コミット成果を削除しません。
- ADR・ドメイン設計・RSpec・コメント・文章・GitHub 投稿などは、対応する既存 skill の固有要求を維持します。日本語説明文の草稿後は `explain-before-shorten` を適用し、文章作成を再実行しません。

## skill 作成とセッション診断

- `writing-skills` は `create-rule` の配置・検証手順に合わせて使います。利用環境に `skill-creator` などの作成支援 skill が付属する場合は、その配布版の適用範囲・形式にも従います。上流にある規則を複製せず、必要な利用経路と維持条件を検証します。全変更への固定回数の実験、先行して書いた文書の機械的削除、自動 push は要求しません。
- `diagnosing-superpowers` は依頼されたセッション調査で使います。調査範囲に必要な観点から担当を選び、分析 agent 数を固定しません。対象・問題が既に明確なら聞き直さず、調査だけの依頼と修正まで求める依頼を区別します。改善まで承認された仕事を診断報告だけで終了しません。

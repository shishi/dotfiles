# 稼働中の設定を保全する Git 統合

更新対象が稼働中のエージェント・ツールから直接、または symlink 経由で読まれる設定か、統合前に確認します。稼働中の設定へ競合マーカーを書き込む操作は実行しません。通常の調査・編集のために環境を起動する手順ではありません。

1. 対象の HEAD・実 log・基準版との祖先関係・未コミット変更・読み込み経路と、履歴更新の承認範囲を確認します。他者の未コミット変更を維持します。別セッションで履歴が変わっている場合は、古い merge-base からの統合で削除済みファイルを復活させないか、統合結果も照合します。
2. merge は fetch 後に `git merge-tree --write-tree HEAD <取得済みcommit>` で競合を予測します。競合のある設定や事前判定できない統合は、稼働側を有効な状態に保ったまま別 worktree で解消します。
3. 両側の必要な設定・構文・読み込みを検証します。解決済み commit が稼働側の HEAD を祖先に含む場合は fast-forward で反映します。
4. rebase など履歴を書き換える場合は fast-forward を前提としません。元の HEAD・未コミット変更の保全と履歴更新の承認範囲を確認してから、検証済みの履歴へ切り替えます。
5. 反映直前に HEAD と未コミット変更を再確認します。変化していれば候補を作り直し、影響する検証を更新します。反映後に対象の設定と読み込み結果を確認します。

push・破壊操作の承認範囲は共通指示に従います。統合を理由に未承認の操作へ広げません。

## squash merge 後のブランチと worktree の整理

squash merge は元の commit を統合先の祖先に残さないため、`git branch -d` の判定や patch-id だけで完全統合を決めません。PR の `MERGED` 状態と日時だけでも、削除対象の最新内容が含まれた証明にはなりません。

1. PR の merge 対象 head commit と、削除しようとしているローカルブランチ / worktree の HEAD を取得して一致を確認します。PR とブランチ名だけの対応で済ませません。
2. PR が `MERGED` であり、その head の内容を統合した PR であることを確認します。merge 後の追加 commit、未コミット変更、untracked の未保全成果がないことも確認します。
3. 作成主体と使用状況を確認し、自分が作った不要な作業場所だけを既存の承認範囲で整理します。使用中・他者の worktree・未統合の成果を持つものは保持します。head の一致や成果の保全を証明できない場合も削除しません。

履歴が違うことだけを理由に強制削除しません。破壊的 Git 操作は共通指示の明示承認条件を守ります。

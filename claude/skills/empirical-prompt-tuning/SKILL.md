# 実行結果に基づく指示文の改善

対象指示を実行し、要求と結果の差を根拠に指示文を修正して、改善と既存保証を再評価します。skill・共通指示・タスク用プロンプトなどに単独で使えます。ルールの配置判断や通常の作業実行を、指示文改善の実験へ置き換えません。

1. **評価対象と合否を先に決める。** 依頼と失敗の観測から、成果物・必須条件・維持する正常動作を定めます。既知の失敗条件を現行版と変更候補で比較し、別の現実的な条件でも維持を確認します。対象の条件を覆うシナリオを選び、採点しやすさのために要件を減らしません。既存指示のない新規作成では、通常の依頼だけによる実行や既存の代替経路を比較の基準にします。比較対象を確保できなければ機能の確認と改善の因果判定を分けます。description の用途と本文が一致するかは実行前に確認します。
2. **比較条件と予算を固定する。** 指示の版、入力、モデル・推論量、共通指示、ツール・権限、環境を記録します。取得できる範囲で初回・再利用時の状態も揃えます。比較に必要な試行と時間・使用枠の予算を開始前に決め、揃わない条件は差として残します。変更候補と違う条件の成功を、指示変更の改善とは断定しません。
3. **通常入力と内部採点を分ける。** 各試行は作者や前回試行の会話履歴を持たない新規コンテキストで行います。作業場所の状態・生成物・記録も前提として揃えます。前試行の成果物を持ち込む場合は通常利用に必要なものか確認し、残る状態や条件差を記録します。実行者には対象指示と、通常の利用者が渡す依頼・必要な資料を渡します。利用者の要求は隠さず、特定 skill の呼出など評価者だけが使う検査項目は渡しません。追加の質問や自己申告を求める診断試行は、通常入力による試行と区別します。作者が対象指示を説明し直して成功させた結果を、元の指示だけの成功と扱いません。
4. **成果と観測で判定する。** 出力・実物の差分・ツール記録・終了結果などを、事前の必須条件と照合します。実行者の不明瞭点、補完した判断、原因説明は改善の手掛かりであり、実行や原因の観測事実と区別します。呼出回数・時間・再試行などは、取得した記録と自己申告を分け、取れない値は未取得にします。達成項目の割合や速さで、必須条件の未達を相殺しません。
5. **対象の指示文を修正する。** 原因を指示文に帰属する前に、対象本文と実行経路を照合します。本文が未取得なら指示の不足は未判定とし、権限・環境による実行不能と指示の欠陥を分けます。失敗した箇所と原因仮説、変更する指示、確認する要求を対応させます。同じ目的の既存記述があるなら、適用されなかった経路を先に調べます。関連する修正を一つの仮説にまとめ、症状ごとの禁止や例を増やす代わりに、責務・入力・順序の不足を直します。修正まで依頼されている場合は、承認された対象ファイルやプロンプト本文へ反映し、提案だけで終了しません。
6. **修正の確認と合格を分ける。** 新規コンテキストで影響する条件を再評価し、改善に使っていない条件でも要求を確認します。失敗を見て調整に使った条件は、以後は未使用条件に数えません。ばらつきが判断を妨げる場合は、予算内で比較を追加します。下の記録を揃え、必須条件と維持条件が満たされた証拠を合格の根拠にします。未取得の条件が判定へ影響する場合は、その範囲を未判定とします。改善の頭打ちや予算終了は評価を止める判断であり、未達を合格・作業完了にしません。未達を記録し、承認範囲内の再計画・予算の見直し・別経路の利用は司令塔が判断します。追加の承認が必要な操作だけ本人へ確認し、残件への対応と停止は共通指示に従います。

記録は既存の Git 管理外の作業記録を使い、以下の各項目に値か「未取得」を必ず残します。

- 対象指示の版と、通常入力・期待する成果
- 実モデル・推論量・共通指示、ツール・権限、環境・残留状態と条件差
- 事前の試行・時間・使用枠の予算、取得した回数・時間・使用量
- 必須条件と維持条件ごとの合否、観測根拠の場所
- 採用した修正、未確認、比較から言えること・言えないこと

文書の整合確認、進行判断の回答、実際の操作による評価は区別して報告します。評価用の成功を、未確認の通常利用や別モデルへ広げません。

方法の参考は [empirical-prompt-tuning](https://github.com/mizchi/skills/blob/main/empirical-prompt-tuning/SKILL-ja.md) です。通常入力の維持、観測に基づく判定、合格と評価停止の区別は共通指示に合わせています。

## 他の作業から使う場合

呼出元の対象・成果物・承認範囲・正常動作の保証を引き継ぎます。`create-rule` や `superpowers:writing-skills` から使う場合も一つの改善ループとし、上流のシナリオ検証と別の実験を二重に起動しません。変更が実行者の判断・行動・生成物を変えるなら、影響する条件を実行して確認します。意味や挙動を変えない表記整理は、既存の証拠と必要な通常経路の確認を使います。全変更に一定回数の実験を課しません。

指示文の修正・再評価を終えたら、呼出元の最終確認・独立レビュー・保存の手順へ戻ります。独立レビューや commit・投稿の許可をこの skill で省略・拡張しません。

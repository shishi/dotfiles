# 記憶に価値があるかを判定する

記憶を書くことは、将来のエージェントがその知識に頼りたくなるという予測です。予測が当たる記憶は、無いと別の作業で起きる損失を防ぎ、読んだエージェントがそのまま正しく判断できます。誤った記憶は逆に、読まれるたびに誤りを持ち込み、記憶が無いより悪い結果を生みます。そのため判定は、記憶があることで判断がどう良くなるか (価値) と、必要な場面で読んで正しく従えるか (実用性) の 2 つで行います。

取得回数・更新日・文字数は、価値の判定の理由にしません。取得回数は、集計した会話でその本文を取得したと確かめられた入力の数です。読んだ後の判断が良くなったかも、必要な場面がどれだけ起きたかも表しません。取得 0 回は、必要な場面がまだ来ていないことと区別できず、毎回取得されても判断を変えない記憶もあります。取得の記録や注入の上限は、置き場と単位の切り方を調べる手がかりにだけ使います。

## 1. 価値を確かめる

既存の記憶を見直すときは、記憶の単位 (ファイル、または独立して読む節) から判定します。単位ごとに、その単位全体が支える判断の範囲と、同じ場面で取得されるほかの単位を作業メモに書きます。その単位について下の 1〜6 と手順 2 を確かめ、手順 3 の判定を単位について先に出します。単位ごと消す・移すと決める前に、その根拠が単位のすべての主張に及ぶかを確かめます。及ばない主張があれば「分ける」に当たり、分けた後の各単位を改めて判定します。主張ごとの判定は、単位の判定の後に、単位ごと消すと決めた単位を除いて行います。主張ごとの修正だけで見直しを終えると、単位の重なりや、単位ごと不要になった記憶が残るためです。記憶群全体を見直す依頼は、[memory-consolidate](../memory-consolidate/SKILL.md) の手順で全単位を対象にし、この基準で判定します。新しい知識には単位がまだ無いので、候補の主張に 1〜6 と手順 2 を当てて保存するかを決めます (手順 3 の末尾)。

単位と主張のそれぞれについて、次を確かめます。

1. **変える判断**: どの場面で、エージェントのどの判断・操作を、どう変えるか。書けない記憶は、価値が無い候補です。
2. **無いと起きる損失**: 記憶が無いと何が起きるか。利用者が同じ説明・訂正を繰り返す・同じ調査や失敗をやり直す・利用者の意図に反する判断をする・取り返しの付きにくい事故 (データの消失、本番の誤った変更など) を起こす、のどれかです。損失が大きい記憶は、必要な場面がめったに来なくても残します。典型は次のとおりです。訂正や不満に表れた判断基準・選択の理由として示された原則・恒常的な好み。実測で確定した環境の落とし穴・コードや Git から復元できないプロジェクトの制約・外部の資料や管理画面の場所。
3. **ほかから得られるか**: コード・設定・Git 履歴・AGENTS.md・skill・repo の文書をその場で読めば同じ判断ができるなら、記憶が足す価値は小さくなります。写した内容は、元が変わると古いまま残ります。ほかにあると判定するときは、その箇所を開いて同じ内容があることを確かめます。利用者が示した価値観・好み・訂正は、同じ規則が skill や共通指示にあっても、判断基準とその理由として記憶に残します。
4. **正しいか**: 主張を、種類に合う元の根拠と照らします。本人の方針なら元の発言と、その後の撤回・後継方針です。実測なら測った条件と結果、現在の設定なら今のファイルです。照らし方は [improving-memory](../improving-memory/SKILL.md) の表の「誤り・古い主張」の行にあります。元の根拠と食い違う主張は、価値が負です。
5. **利用者の今の方針と合うか**: 全体の方針 (`CORE.md`) と共通指示に照らします。方針に反する行動を生ませる記憶は、価値が負です。プロジェクトの記憶が全体の方針と違う場合は、そのプロジェクトだけの例外として本人が示したものかを元の発言で確かめます。確かめられなければ、どちらが今の方針かを推測で決めず、本人に確認します。
6. **一回限りか**: 作業の経緯と、ほかの作業の判断を変えない個別の決定には価値がありません。個別の決定とは、結果が設定・コード・commit に表れる一度きりの選択 (一つの道具の設定値など) で、利用者が明示した選択でも同じです。その決定を超える理由や原則が示されていれば、その理由と原則に価値があります。その場限りと示された指示も同じです。

## 2. 実用性を確かめる

価値のある記憶も、必要な場面で読まれ、読んだエージェントが従えなければ働きません。

作業の規則・手順・事実の記憶は、次の 6 点を確かめます。本人の価値観・好みの記憶は判断の背景として書くものなので、最初の 2 点は当てず、それだけで判断の背景が伝わるか (単独で読めるか) を確かめます。

- **条件を観測できるか**: 適用する条件が、判断する時点で観測できるかを確かめます。「忙しいとき」「重要な変更のとき」のように判断の時点で確かめられない条件は、従う場面を決められません。
- **行動が具体的か**: 何をするかが具体的かを確かめます。「ちゃんとやる」「気をつける」は行動を決めません。
- **単独で読めるか**: 元の会話を知らないエージェントが、その記憶だけで判断できるかを確かめます。適用範囲 (プロジェクト・OS・版) は本文に要ります。ただし、置き場 (`projects/<slug>.md` など) で決まる範囲は本文に書かなくてかまいません。理由と例外は、元の根拠にあるものを本文に書きます。元の根拠に無い理由は作りません。
- **必要な場面で取得されるか**: 題名・`description`・索引の行に、探すときに使う対象名・操作・症状があるかを確かめます。
- **読んで従われるか**: 読み込んだ記憶に、エージェントが従うとは限りません。価値が大きい記憶について従われていないと疑う根拠 (同じ失敗が繰り返された記録など) があれば、条件をそろえた試行で確かめます。手順と試行の本数は [empirical-prompt-tuning](../empirical-prompt-tuning/SKILL.md) に従い、課金される試行の費用は [investigation-discipline](../investigation-discipline/SKILL.md) の「費用の確認」で決めます。
- **置き場の範囲が内容に合うか**: `CORE.md` と `projects/<slug>.md` は、その範囲のすべての作業の起動時に注入されます。内容の適用範囲が置き場の範囲と合うかを、[capturing-memory](../capturing-memory/SKILL.md) の「保存範囲の判定」で確かめます。複数のプロジェクトで使う本人の判断原則は、使う場面が限られていても `CORE.md` に置きます。注入の量を減らすことだけを理由に移しません。

## 3. 判定する

単位と、単位ごと消すと決めた単位を除いた主張ごとに、次のどれかに判定します。判定には、それを支える引用と確かめた資料を添えます。

- **残す**: 価値があり、実用的です。
- **直す**: 価値はあるが、誤っている・古い・条件を観測できない・行動が具体的でない・単独で読めない・必要な場面で取得されない記憶です。正しい中身を元の根拠から決められるなら、[improving-memory](../improving-memory/SKILL.md) で直します。本人の方針にかかわり、正しい中身を元の発言から決められないときは、本人に確認します。
- **まとめる・分ける**: 価値はあるが、同じ場面で取得し一緒に更新する知識が別々の単位に分かれている、または一つの単位が別々の場面の知識を抱えている記憶です。切り方は [improving-memory](../improving-memory/SKILL.md) の表の「単位の切り方」の行で決めます。
- **移す**: 価値はあるが、置き場が合わない記憶です。別のプロジェクトや root の記憶へは capturing-memory の「保存範囲の判定」で移します。作業の手順は skill や共通指示へ、[create-rule](../create-rule/SKILL.md) の「依頼と配置」で移します。
- **消す**: 価値が無い記憶 (変える判断が無い・ほかから得られる・一回限り) と、価値が負で正しい中身に直せない記憶です。消す根拠は、手順 1 のどの項目で価値が無い (または負) と判定したかと、その判定を支える引用で示します。引用するのは、判定に使った資料です。記述そのもの・同じ内容がある箇所・元の根拠・結果が表れた設定やコードや commit などがそれに当たります。たとえば作業の経緯なら、記述を引用して、ほかの作業へ引き継ぐ原因・原則・技術的な因果を含まないことを示します。根拠を示した記述は、本人に確認せずに消します。根拠を示せない記述は消さずに残します。本人が示した価値観・好み・訂正を誤りや方針との食い違いを理由に消すときだけは、扱いが違います。本人の撤回か後継の方針を確かめられなければ消さず、本人に確認します。

新しい知識を保存するかの判定も同じ基準で行います。会話の中では前後の発言で中身が決まる知識 (「さっき決めた言語で」など) は、元の発言にある適用範囲・中身・理由で補って単独で読める形にしてから判定し、「残す」に当たるものを保存します。保存するときも、元の発言に無い理由は書き足しません。利用者の言い方や「記憶して」の有無では決めません。保存は、明示の依頼の有無にかかわらず、気づいたターンで capturing-memory の手順で行います。

## 4. 報告する

記憶を見直したとき (全体の整理や利用者の依頼) は、単位の判定を先に並べ、主張ごとの判定をその後に示します。それぞれに、変える判断と無いと起きる損失・実用性で確かめたこと・判定とその根拠を添えます。日々の保存では、保存したことと判定の要点だけを伝えます。本人の判断が必要になった項目は、その中でも最初に置きます。そこには、選んだときと選ばないときに起きることを添えます。

## この基準の根拠

Anthropic の [The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory) は、確かめた事実を書くことを将来のセッションがそれに頼るという予測と位置づけています。そして、起動時に注入する層の誤ったメモは毎回のセッションに持ち込まれうること、読み込んだメモにエージェントが従うとは限らないことを示しています。何を保存するかを固定の規則で縛るより、記憶が何のためにあるかを伝えて重要さを判断させるほうが成績がよく、「失敗だけを記録する」と縛ると記憶による伸びが大きく減りました。この skill が規則の一覧ではなく、判断を変えるか・損失を防ぐかという目的で判定するのはこのためです。

Xiong らの [How Memory Management Impacts LLM Agents](https://arxiv.org/abs/2505.16067) は、似た記憶を取得したエージェントがその内容をなぞること、質の悪い記憶を足すと誤りが後の作業へ伝わることを示しました。削除の比較では、取得の頻度で周期的に消す方式は、記憶を大きく減らす一方で成績を少し下げました。信頼できる評価器と組んだ実験では、使われたときの結果の良し悪しで消す方式が多くの条件で最もよい成績になりました (エージェントと評価器によっては、周期的な削除との併用がわずかに上回りました)。この方式も、取得回数は判定に足る観測があるかの条件に使い、価値の尺度にはしていません。記憶の価値は、使ったときに判断が良くなるかで決まり、取得された回数では決まりません。この skill が取得回数を判定の理由にせず、正しさと従われるかを確かめるのはこのためです。

Claude Code の [記憶の文書](https://code.claude.com/docs/en/memory) は、コードや指示ファイルから導けることを記憶に入れず、将来の会話で役立つかで保存を決めるとしています。また、具体的な指示ほどよく守られ、矛盾する指示はどちらかが勝手に選ばれるとしています。手順 1 の「ほかから得られるか」と手順 2 の「行動が具体的か」は、これに合わせています。

反対の例として、[Generative Agents](https://arxiv.org/abs/2304.03442) は重要度・関連度と並べて新しさで取得する記憶の順位を決めます。[MemoryBank](https://arxiv.org/abs/2305.10250) は忘却曲線で記憶を保持する確率を決め、想起された記憶ほど忘れにくくします。長く取得されない記憶は、前者では新しさの加点が減り、後者では保持される確率が下がります。めったに使わない記憶でも、必要なときに取り出せなければ大きな損失につながることがあります。この記憶ではそうした記憶こそ保持したいので、新しさや回数で価値を決める方式は採りません。

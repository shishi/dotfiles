# ルールを実行に結び付ける

依頼されたルールは、実行前ガード、skill、AGENTS.md の順に配置を検討し、実際の実行に結び付けます。作業固有の判断・手順は skill を優先します。記憶保存、同意、今後の宣言だけで完了にしません。

## 挙動について指示・修正を受けたとき

エージェントの判断・操作・応答をどう行うかという指示と、実際の挙動への修正要求を対象にします。
既存の失敗の指摘がなくても適用します。「ルールを直して」「覚えて」「skill に反映して」という追加依頼や、同じ範囲の再承認を待たず、そのターンで関連 skill の反映と検証まで進めます。
疑問形や短い指摘も、元の依頼と実際の行動に照らして意味を判断します。
通常の成果物だけの依頼、引用、ユーザー自身の訂正と混同せず、固定語句の検知にはしません。

1. **元の依頼から次の行動を決めます。** 指示の対象・適用条件・求める結果と現在の実物を照合し、修正要求には元の成果物・未達・承認範囲を引き継ぎます。
   最初に、指摘や訂正の前提 (挙げられた事実、現在の挙動、誤りとされた点) が正しいかを実物で確かめます。現在の挙動が正しければ、根拠を示して維持し、規則も変えません。前提の一部だけが正しければ、正しい部分だけを是正と恒久対策の対象にします。「今後はこうしてほしい」という新しい指示は事実の指摘ではないため、現在の挙動が誤りでなくても適用します。
   中止や取り消しの対象は、直前のやり取りと既に反映した変更に照らして特定します。選んだ方式を取り消す指示なら、その方式で入れた自分の変更を戻し、元の目的と残る制約を満たす別の方式で進めます。作業全体を中止する指示なら、そこで作業を止めます。
   元の目的が未達で実行可能な是正が残るなら、その操作と結果確認まで進めます。指摘への説明を返しても、元の実行要求を満たしたことにはしません。
   利用者が説明のみ・変更禁止を明示した場合はその範囲を守ります。完了か続行かは指摘の表現でなく、元の依頼の達成状況と共通指示の停止条件で判断します。
   前提が正しく是正が要る場合、元の依頼の是正と以下の恒久対策は 2 つを同時に扱います。片方でもう片方を代替せず、片方のためにもう片方を止めません。
   是正した答え・成果物を作るのに要る確認だけを先に済ませて利用者へ示し、恒久対策の調査・実験・レビューはその後に同じターンで続けます。
2. **既存の規則と適用経路を調べます。** 共通指示・関連 skill・hook・記憶の本文と、
   実際の読込・呼出・判断を照合します。既存にあれば「既に書いてある」で終えず、
   なぜ適用されなかったかを調べます。未読、入口や適用条件の不足、規則間の矛盾、
   実行時の判断や環境の問題を証拠で切り分け、未取得の原因を断定しません。
   利用者の報告を調査の手掛かりにして、判断を変える事実とその確認方法を決めます。結論は、観測した操作・対象・環境が支える範囲に限ります。明示された作業条件は、理由の調査を待たずに適用します。
   過去の内因を復元できなくても、観測された行動と既存規則が食い違う判断点を特定し、
   その判断点で規則を使うための入力・手順・検証を既存箇所へ結び付けて改善します。
   原因が未確定であることだけを「反映不要」の根拠にせず、再現と対策後の実行で仮説を確かめます。
3. **原因を担う正本へ反映します。** 反映先は、失敗した場面の名称ではなく、適用されなかった判断・手順の責務から選びます。複数の作業に共通する規則は既存の共通入口へ統合します。個別 skill ごとに同じ規則や呼出条件を追記しません。作業固有の手順は対応する既存 skill を更新し、対応先がなければ下の配置判断に従います。
   指示は守るべき性質と判断基準として既存の手順へ統合し、skill の本文は [improving-skills](../improving-skills/SKILL.md) の手順で直します。改訂は対策候補の保存として扱い、挙動の改善は次の手順で実証します。AGENTS.md や記憶への保存、今後守るという返答だけで代替しません。操作を止める既存ガードと、常時必要な原則・呼出条件の維持も同じ配置判断に従います。
   同じ要件が既に正しく反映され、新しい要求も観測された逸脱もなければ重複編集しません。既存に書かれているのに挙動が外れた場合は、本文だけでなく適用経路を改善します。
   記憶に置く個人方針・知識は [capturing-memory](../capturing-memory/SKILL.md) で統合します。
   規則と保存手順は記憶に複製しません。
4. **挙動の変化を実証します。** 指摘された失敗を判断点まで切り出して再現し、対策後の通常の利用経路で守るべき性質が保たれた証拠を得てから改善を判定します。規則の保存や読込確認だけでは、挙動の是正は未完了です。
   再発は既存対策が不成立だった証拠として扱い、同じ指示文の追記へ戻らず、判断を実行へ結び付ける責務を見直します。強制できる性質は既存の機構で強制し、その経路で結果を確認します。実証できなければ未達として扱い、改善・遵守を達成したと報告しません。
   Git 管理外の作業メモに、望まれた行動との差、適用されなかった原因と根拠、反映先と変更、
   検証結果を短く残します。反映しないと判断した内容にも理由を残します。
   この記録はユーザー向けの返答へ転記しません。返答自体への訂正には、訂正後の答えを返します。

毎回行うのは、指示と関連 skill の照合、必要な反映、通常の利用経路での検証です。
以後も適用する価値観・判断基準・行動方針が示された場合は、共通指示に従って
同じターンで適切な永続化手段を必ず使います。その場限りの条件は恒久化しません。
ただし、その指摘から再利用できる判断・適用経路の欠陥が分かれば、原因を担う箇所を直します。
新しい規則や記憶が不要でも、元の依頼の是正と確認は省きません。
改善が必要なのに実施・検証できない場合は、未解決のまま「不要」や「完了」としません。
エージェントの行動を制御する指示・skill・hook の正本は、この是正の関連対象です。
元の作業 repo が別でも正本を特定し、そこへ反映します。作業 repo への複製で代替しません。
編集・反映時は共通指示の作業場所・独立レビュー・稼働設定の保全に従います。
この手順はエージェント自身の行動を直す範囲に適用し、無関係な repo の改変、外部への投稿、
認証・権限・変更禁止の境界を広げません。必要な承認や実行不能な範囲は共通指示に従います。

## skill・規則・hook・記憶の構成を見直すとき

構成の見直しや棚卸しを依頼されたときは、各単位が役割を果たしているかを、使われ方と外の基準・事例から判定し、構成の変更を提案します。文言の重複・参照切れ・表記の修正から始めません。それらは、構成の提案の後に、残った箇所を修正候補として別に示します。

1. **使われ方を測ります。** 過去のセッション記録から、次の項目を取ります。Claude Code と Codex の両方を測ります。片方の値をもう片方に当てはめません。利用者が直接依頼した作業 (以下、実作業)、実験用の repo や試行、委譲先・判定役のセッションは分けて集計します。各単位が使われた回数と場面は、その単位が実際の依頼で使われる場面の値で判定し、実験の値を数えません。読んだ場合と読まない場合の差のように、実作業の記録から測れない項目は、条件をそろえた試行で測り、試行の結果であることを添えます。測れなかった側と項目は、理由とともに示します。記憶の利用実績と注入量は [memory-consolidate](../memory-consolidate/SKILL.md) の「利用実績と注入量の測定」で測ります。記憶の利用実績の集計は実作業と実験を区別しないため、その旨を値に添えます。
   - 各 skill が開かれた回数とセッション数 (skill の呼出しと、本文のファイル読取の両方)
   - hook がツールを止めた回数と、注入した回数・分量
   - 常時読み込む文書 (共通指示、起動時と毎入力で注入する記憶) の分量
   - 規則があるのに挙動が外れた事例
2. **外の基準と事例を調べます。** 手元の構成どうしを比べるだけでは、構成そのものが外の想定から外れている場合に気づけません。次の 3 種類を、現行の一次資料を開いて確かめます。記憶や一般論で代用しません。
   - 各 CLI の公式の仕様と推奨 (指示ファイル・skill・hook の分量の上限、超えたときの挙動、強制の使い分け)
   - 指示や skill の量・構成が遵守や成果に与える影響を測った研究と検証記事
   - 公開されている構成の事例 (分量、単位の切り方、強制の仕方)

   資料の扱いは [investigation-discipline](../investigation-discipline/SKILL.md) の「外部情報と現物を並行して調べる」に従い、資料ごとに出典・時期・測定の条件と限界を作業メモに残して、実測と経験則を分けます。手順 1 の実測を、外の上限・推奨・事例の値と突き合わせます。外の基準に対応する値が手順 1 に無ければ、その基準と同じ単位で追加で測ります。食い違う箇所は手順 3 で判定する手掛かりです。外の資料が示す問題が手元で起きているかは、手元の記録か試行で確かめ、外の資料だけでは手元の問題と断定しません。手元の実測が外の資料と逆を示した場合は、手元の単位は手元の実測で判定し、外の資料は反する証拠として併せて示します。
3. **単位ごとに、存在の根拠を判定します。** 手順 1・2 の結果と本文から、次の点を確かめます。
   - その単位が防ぐ失敗、または実現する結果
   - 必要な場面で実際に読まれていること
   - 読んだ後の判断や操作が、読まない場合と変わること
   - 同じ責務を担うほかの単位の有無

   次の特徴は調べる手掛かりです。当てはまるだけでは問題にしません。その単位が目的を果たしていない、または目的を損なっている根拠を得たときに、構成の問題と判定します。
   - 必要なはずの場面で開かれていない skill
   - 毎回読まれるのに、読んでも判断が変わらない本文
   - 失敗のたびに文を足して、一つの箇条に独立した規則が並んだ箇所
   - 同じ規則を複数の仕組み (共通指示・skill・hook) で重ねて伝えている箇所
   - 変更の大きさや危険度が違っても同じ重さで適用される工程

   記憶の単位を残すか、削るか、統合・分割するかは、[improving-memory](../improving-memory/SKILL.md) の「問題を見つける」で判定します。利用実績を記憶の削除の根拠にしません。
4. **構成の変更を先に提案します。** 統合・分割・廃止、配置替え (ガード・skill・共通指示・記憶の間の移動)、強制方法の変更を、得るものと失うものとともに示します。提案ごとに、その問題が起きている根拠と、その変更で解消する根拠を示します。問題が手元で起きている根拠は、手順 1 の実測、試行、実物の引用のいずれかで示します。手順 2 の一次資料は、上限や挙動の仕様と、変更で解消する根拠に使います。外の資料が示す問題を手元で測れないと確認した場合は、下の推測と同じ扱いにします。根拠を示せない案は提案にせず、先に確かめる測定を実行します。推測を根拠にしてよいのは、利用者が推測でよいと言った場合と、利用できる経路で測れないと確認した場合だけです。その場合も、推測である箇所と、推測にした理由 (利用者の指定、または測れなかった経路と理由) を提案の中に書きます。利用者が明示的に求めた仕組みは、その目的を保つ案だけを示します。費用を理由に、廃止や緩和を推奨しません。
5. **文言の修正は分けて示します。** 重複・参照切れ・表記の修正候補は、手順 4 の提案とは別の一覧にします。提案と修正候補を skill へ反映するときは、improving-skills で本文を直します。構成の提案が無い結果を出す場合は、手順 1〜3 の実測・外の資料・判定を単位ごとに示し、構成を変えない理由を説明します。

子や別 CLI に読ませる場合も、依頼文に手順 1〜3 の観点と、実測・外の資料の結果を入れます。ファイルごとの整合性の確認だけを依頼しません。

## 依頼と配置

- 元の依頼と訂正から、禁止する判断・行動、求める結果、適用範囲、維持する保証を定めます。
  例に登場した単語だけを禁止せず、文脈上の意図を外した判断を対象にします。
- 配置は次の順に検討します。これは実装先の検討順であり、指示の権限や優先関係を変えるものではありません。
  1. **既存の実行前ガード。** push、破壊的な Git 操作、削除など、操作前に拒否すべきものは、両 CLI の判定 (Claude Code の auto mode の分類器と Codex の Auto-review) に渡すルールの正本 `agent-shared/policy/action-policy.json` へ統合し、`agent-shared/bin/apply-action-policy` で両 CLI の設定へ書き出します。通常の承認済み操作を維持できるか確認します。機構があることだけを理由に、作業の判断や手順までガードへ移しません。
  2. **既存 skill への統合、必要なら skill の新設。** 作業固有の判断・手順はここを第一候補にします。適用場面を description に書き、本文を作業直前に取得できる入口を確保します。同じ目的の skill を先に探し、新設は既存の責務へ収まらない場合に限ります。
  3. **AGENTS.md。** 常時必要な共通原則・承認境界と、skill を呼ぶ条件だけを残します。作業別の詳細を追記する前に、上の配置では満たせない理由を確認します。
- 既存の AGENTS.md や記憶に詳細手順がある場合も、上の順に移行します。移動先を先に用意し、元の条件・例外・必須要件が保たれ、通常の入口から参照できることを確認してから、移動元を短い呼出条件や参照へ置き換えます。同じ詳細は両方へ残しません。
  個人の価値観・好み・環境事実・版を限定した観測は private 記憶に保持します。手順と混在していれば分け、個人マシン名・私的なパス・接続先を公開 skill へ転記しません。
- 規則は入力のたびに hook で注入しません。入力ごとに kata を最初に開かせる `kata-first.sh` は、利用者が明示的に求めた例外です。入力時に記憶の検索結果と、会話にまだ渡していない版の索引を渡す `inject-memory.sh` は記憶の取得経路で、規則の注入ではありません。回答の事後採点・差し戻しや失敗後の命令再注入は、ユーザーがその仕組みを明示的に依頼した場合だけ扱います。ルール改修や遵守改善の依頼だけを事後検査の承認にしません。
  明示依頼がある場合は、廃止した事後検査の判断 (`docs/ADR/20261103-213806-output-gate-post-check.md`) の理由と影響を確認してから設計します。
- リポジトリの指示ファイルを作成・変更する前に、エージェントの実行版・設定、対象と祖先の既存指示ファイル、公式の読込仕様を確認します。
  既存の読込経路で必要な規則が届く場合は、その経路を使います。
  Claude Code が対象の `AGENTS.md` を直接読む環境では、読込のためだけの `CLAUDE.md`・import・symlink・hook を追加しません。
  直接読めない環境では、既存の読込経路の不足を確認してから、必要な入口だけを補います。
- hook やガードを使う場合は、現在の本文、登録イベント、配備先と symlink、共通指示との関係を読みます。
  危険操作の拒否は、上のルールの正本へ統合します。
  Claude Code と Codex の両方に同じ共有 hook を登録しているため、既存登録を再利用します。
  作業別の詳細手順は skill に置き、hook から必要なときに参照させます。

## 実装と検証

- モデルによる意味の判断を、ユーザー入力や回答の固定文字列の一致・不一致で代替しません。
- 既存の同じ規則を置換・統合し、同じ詳細を記憶や複数の配置に複製しません。
  共通指示との矛盾があれば、現在のユーザー指示と上位の権限制約に合わせて解消します。
  vendor cache は変更せず、正本と有効な配布先を更新します。
- 既存の skill の編集・分割・統合は [improving-skills](../improving-skills/SKILL.md) で行います。skill を新設・fork・廃止するときは、由来の台帳 `agent-shared/skill-sources.tsv` と `docs/agents.md` の「skill の由来と編集先」に従い、同じ変更で台帳も直します。外部の skill の導入・更新と、plugin・system skill の本文は `skill-source-overrides` に従います。
- 採用した配置の通常の読込・呼出経路で、規則が必要な時点に使われることを確認します。
  両エージェントの登録と実際の参照先、既存 hook の契約、関連する既存テストも確認します。
  新しい hook の登録や定義変更で trust の更新が必要なら、通常の承認経路で扱います。
- skill へ移した場合は、呼び出されて本文が取得されたことと、その後の判断・操作が要件を満たしたことを分けて確認します。配置を変えただけで遵守が改善したとは扱いません。移行元に残す入口も検証対象に含めます。
- 元の失敗例と維持条件を使い、規則に沿う判断と結果を確認します。
  規則が渡ったことやガードの出力の確認と、モデルの実際の応答・操作の確認を区別し、未確認の挙動を確認済みとしません。
  応答の抑止を依頼された場合は、通常の入力経路で元の失敗が抑止された実回答を確認するまで未完了です。
  誤った前提の訂正や、明示的に求められた別案の説明など、維持すべき応答も確認します。
  配備成功や独立レビューの指摘なしを、抑止できた証拠の代わりにしません。
  必要な独立レビューと commit は共通指示に従います。
- skill・共通指示・再利用するプロンプトを新規作成する場合や、実行者の判断・手順・出力を変える指示の改訂では、
  [empirical-prompt-tuning](../empirical-prompt-tuning/SKILL.md) で実行・修正・再評価を行います。
  上の通常経路の確認と同じ評価として組み込み、全ルール変更へ一律に実験を追加しません。

ルールの作成・変更を明示的に依頼された場合の完了報告には、選んだ配置とその理由、反映したルール、確認した利用経路を記します。未確認の事項の扱いは、共通指示の「応答」と最終報告の規則に従います。
行動の訂正への最終回答は、訂正後の答え・成果物から始めます。手順 1 で既に示した場合は繰り返しません。規則・記憶を実際に変更した場合は、その末尾に変更した正本と検証結果を示す一文を添えます。
分析・作業経緯は転記せず、本人の判断や操作に必要な未達は明示します。
将来の応答をすべて保証したという表現で、実装・検証結果を置き換えません。

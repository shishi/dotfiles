# 共通経路と補完フィルタを調べる

複数の無関係なアプリやサイトに広告が残る場合は、共通の DNS 経路と実際のフィルタ適用を先に確認します。ドメインを一つずつ足す運用だけを続けません。

## 通信経路と適用を確認する

- 該当時刻の通過・遮断・除外をすべて取得し、ページングや件数制限による欠落を確認します。DNS ログだけから記事の完全な URL や広告素材のパスが分かるとは扱いません。
- クライアントの識別、IPv4・IPv6、OS とブラウザーの DNS、VPN・出口ノード・中継経路を照合します。出口ノード使用時の DNS 適用設定と、実際に端末が出口ノードを使用した証拠は別です。
- 永続設定と稼働中の設定、購読の有効状態・更新結果、保護の一時停止、クライアント別設定、許可ルールによる優先を確認します。サーバーへの直接問い合わせ成功だけでは端末の経路を証明できません。
- CNAME は元の問い合わせと応答の連鎖を対応づけます。広告通信と近い時刻に現れた CDN 別名を、その理由だけで広告として遮断しません。

## 保守される補完フィルタを比較する

1. 利用者が拒否した強度・製品を除き、現在の購読に不足する用途を定めます。ある強力なリストの不採用を、ほかの補完リストを検討しない理由にしません。
2. 公式配布元、対象製品の構文、保守状況、強度を確認します。例えば [1Hosts](https://github.com/badmojr/1Hosts) は Lite と Xtra の目的を分けています。名称や件数だけで採用せず、現在の配布物を確認します。
3. 実ログの通過先と通常機能に必要な通信へ照合し、既存購読との重複・追加対象・許可ルールを調べます。リストへの一致件数と、実際に追加遮断される件数を分けます。独自パーサーが未対応の構文を、非一致として数えません。
4. 採用する購読と裏付けのある個別ルールを永続設定へ反映します。更新間隔、反映後の実判定、通常機能、元の広告表示を確認します。名前解決が残るだけでは通常機能の維持を証明できません。

複数端末を対象にする依頼では、共通ルールを基本にします。端末限定や例外には、実際に維持する機能と適用範囲の根拠を求めます。共有サービスという分類だけで一括除外せず、広告を止める利益と失う通常機能を同じ基準で比較します。

DNS の判定 API、実際の DNS 応答、DoH 経由の応答、端末画面の結果はそれぞれの証拠として記録します。負荷制限に合わせて問い合わせを間引き、検査の集中によるタイムアウトを広告経路の障害と混同しません。

# 広告の通信経路とフィルタを調べる

広告を読み込む実際の通信と、残す通常機能を特定してから設定を変えます。ホスト一覧へのアクセスを終えても、広告の用途や遮断の成否を確認したことにはなりません。原因調査と収束の共通条件は `investigation-discipline` に従います。

## ログから配信物まで追う

- まず対象アプリ、広告が出る操作、現行フィルタ、ログの採取範囲を確認します。全件を依頼されたら、通過・遮断・除外を含む元ログの対象と取得件数を照合します。DNS ログで分かるホスト・応答と、HTTP で分かる URL・内容を区別します。
- 広告表示前後の通信、アプリやページの参照、公式の広告 SDK・導入ガイドから、配信 URL を辿ります。取得した SDK、設定、素材が次に参照する URL も調べ、広告の読み込みとの関係を確かめます。SDK が存在するだけでは、その端末が利用した証拠になりません。
- ホストの root が 403・404・空本文でも、その応答が示すのは取得した URL の結果です。実際の用途の判定は保留し、公式の現行ガイド、既知の配信 URL、リダイレクト先、取得物内の参照へ進みます。資料間でパスや大文字・小文字が異なる場合は、出典を残して両者を確認します。根拠のないパスの総当たりはしません。
- 観測結果は「取得した入口」「辿った参照」「広告との関係を確認した用途」「未確認」に分けます。ホスト名・提供企業・共有 CDN という分類だけで広告専用・無害・調査不能を決めません。公開資料をまだ探していない状態を DNS の限界と呼びません。

## 通常機能を保って調整する

- 現在使う製品・OS・動作モードの実物と公式仕様で、適用できる制御単位を確認します。DNS のホスト遮断、アプリ側の URL 制御、コンテンツ制御を区別し、必要な機能を利用できる経路から選びます。追加製品・証明書・通信復号を前提に進めません。
- 共有ホストは、観測した広告通信と通常通信を対応づけます。ホスト全体を遮断する案では、失う通常機能を先に確認します。広告を識別できる制御単位が利用できるなら、その範囲で設定を調整します。ホストの一括遮断も、共有ホストの一括除外も、用途の確認にはなりません。
- 設定変更を依頼されている場合は、採用した調整を実物へ反映し、既存の永続化方法に保存します。変更前の状態と戻し方を保持します。利用可能な制御では両立できない場合は、その根拠と失う機能を示し、権限内の別経路と依存しない調整を続けます。

## 通常の入口で結果を確認する

- 元の広告が出た操作を再実行し、広告表示と実際の通信・遮断結果を照合します。通常コンテンツの表示や操作も確認します。キャッシュ・既存セッション・通信未発生による非表示と、フィルタによる遮断を分けます。
- 判定には対象設定、操作、観測結果、通常機能への影響、未確認を対応づけます。反応が返るまでと結果を使えるまでの時間も測り、依頼と既存動作に照らします。端末操作や採取が必要なら、利用可能な経路を先に調べ、本人にしかできない最小操作だけを依頼します。
- 「全ホストへ接続した」「候補を分類した」「レビューで指摘がなかった」は調査作業の記録です。広告を識別できたことや設定改善の証明には使いません。広告との因果や維持条件が未確認なら、その観測を補ってから完了を判断します。

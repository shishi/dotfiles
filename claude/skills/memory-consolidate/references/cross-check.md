# 記憶群の主張を突き合わせる

記憶群全体の重複と矛盾は、主張を一件ずつ取り出し、同じ場面に当てはまる主張どうしを話題ごとに比べて見つけます。ファイルを一つずつ読む方法や語句で検索する方法では、読み手が思い付いた語の範囲しか比べません。そのため、言い回しの違う重複や、別々のファイルにある矛盾を見落とします。ファイルを分担して読むと、各担当は自分のファイルの外を見ません。

機械的に確かめられる工程は [scripts/cross_check.py](../scripts/cross_check.py) で確かめます。作業ディレクトリは Git 管理外に置き、本文を `text/<repo 名>/<相対パス>` に、各工程の結果を JSON Lines で置きます。

## 1. 比べる版と対象を決める

記憶は整理の基準 commit の本文を使います。指示は、指示を置く repo の HEAD (commit 済みの本文) を使い、その commit を作業メモに残します。ほかのセッションの未コミット変更は、比べる版に入れません。未コミットの本文は捨てられることがあり、それを根拠に記憶を消すと、その内容がどこにも残らなくなるためです。

比べる指示は、記憶と同じ判断を述べうるものすべてです。一覧を作って作業メモに残し、対象から外したものは理由を添えます。

- 共通指示: global と repo の AGENTS.md・CLAUDE.md と、それが読み込むファイル
- skill: 両エージェントの skill の SKILL.md と references/。片方の CLI にしかない skill も含めます
- エージェントの定義: 両エージェントの agents/
- フックが注入する指示: 両 CLI の設定に登録されたフックのスクリプトを、記録した commit の本文で読み、分岐ごとに出しうる文をすべて取り出して本文として保存します。注入される文はスクリプトの中で組み立てられ、条件によって変わるためです。通常の入力で一度実行するだけでは、ほかの分岐の文が漏れます。フックを実行すると、状態を書き換えるもの (取り込みの通知を消費するものなど) があるため、取り出しのためには実行しません。記憶の本文を注入するフック (起動時の記憶、記憶の検索結果) が出す記憶の本文は、記憶の写しなので指示に含めません。写しを指示として比べると、記憶とその写しが重複に見え、記憶の側を消してしまうためです。そうしたフックは、フック自身が書く案内の文だけを指示にします。取り出した文は `text/hooks/<CLI>/<フック名>.md` に置き、どのスクリプトのどの分岐から取ったかを作業メモに残します

記憶と指示の本文を、決めた版で作業ディレクトリの `text/` に保存します。

## 2. 主張の一覧を作る

`text/` の各ファイルの全文から、意味を独立して確かめられる主張 (事実・方針・手順・適用条件・例外・価値観) を一件ずつ取り出し、`claims.jsonl` に書きます。一行が一件です。

```json
{"file": "<repo 名>/<相対パス>", "id": "<file>#<連番>", "source": "memory|instruction", "subject": "<述べている対象>", "condition": "<OS・版・プロジェクト・場面。無ければ空>", "assertion": "<中身を 1 文で>", "quote": "<原文の引用>", "line": <引用した文が始まる行。引用が複数の文に当たるときだけ>}
```

- `source` は、取り出す側がファイルの場所 (記憶 repo か、指示のファイルか) から付けます。比べる側に判断させると、指示のファイルを記憶として数える取り違えが起きます。
- 見出しや参照だけの文は主張にしません。複数の主張を含む文は分けます。要約するときも、元に無い条件や事実を足しません。
- 取り出しはファイル単位で分担できます。

取り出した後に `cross_check.py extraction <作業ディレクトリ>` を実行し、問題が無くなるまで直します。スクリプトは、各 `quote` が本文にあることと、本文の各文がどれかの `quote` に含まれることを確かめます。LLM に文書を事実へ分解させると、一部を落とすことが知られています (臨床文書での測定で、GPT-4o の事実の再現率は 8 割前後でした。[FactEHR](https://arxiv.org/abs/2412.12422))。落とした主張は以降のどの工程にも現れず、後の数え上げでも見つからないため、ここで本文の側から確かめます。引用は一つの文の中から取ります。同じ語句が複数の文にあって 1 か所に決まらないときは、引用を長くするか、`line` に引用した文が始まる行を書きます。どの `quote` にも含まれない文は、主張を取り出すか、主張にしない理由を `skipped.jsonl` (`{"file", "text", "reason"}`。決まらないときは `line` も) に残します。一つの文に二つの主張があって片方だけを取り出した場合は、このスクリプトでは見つけられません。

## 3. 話題に分ける

`subject` の表記は担当ごとにばらつくので、そのままでは同じ対象をまとめられません。話題は対象の名前ではなく、主張が当てはまる場面 (いつ、何を、どうするときか) で作ります。名前の違う対象を挙げていても、同じ判断を述べる主張を同じ話題に入れるためです。一覧の主張を見渡して話題の一覧 (話題の名前と当てはまる場面) を作り、各主張を、当てはまる場面の話題すべてに振り分けて `topics.jsonl` (`{"id", "topics": [...]}`) に書きます。

## 4. 話題の中で比べる

話題ごとに、`source` が `memory` の主張の一件ずつを、同じ話題のすべての主張と比べます。指示どうしの組は比べません。比べる単位は (記憶の主張, 話題) の組です。複数の話題に振り分けた主張は、話題ごとに比べます。

相手の一件ずつについて、まず二つの主張が両方とも当てはまる場面があるかを決めます。条件が同じ場合に加え、一方の条件が他方を含む場合 (全体の方針とプロジェクトの記憶など) も、その場面では両方が当てはまります。両方が当てはまる場面が無ければ、その相手とは関係がありません。両方が当てはまる場面があれば、その場面での中身を比べ、次のどちらかに当たる相手を挙げます。

- `duplicate`: 中身が同じ (言い回しが違っても同じ意味なら重複)
- `contradiction`: 両立しない。狭い側が例外として書かれていても、ここでは矛盾として挙げます。例外かどうかは手順 6 で元の根拠から確かめます。

(記憶の主張, 話題) の組ごとに必ず一行を `judgments.jsonl` に書きます。

```json
{"id": "<記憶の主張の id>", "topic": "<話題>", "pairs": [{"with": "<相手の id>", "verdict": "duplicate|contradiction", "note": "<理由を 1 文>"}], "outside": ["<別の話題>"]}
```

重複も矛盾も無ければ `pairs` を空にします。同じ場面の主張が担当の話題の外にありそうだと気づいたら、その話題を `outside` に挙げます。比べる作業は話題単位で分担できます。分担するときは、各担当に手順 3 の話題の一覧も渡します。ほかの話題を知らないと、`outside` に挙げる先が分からないためです。

## 5. 判定を数え、見落としを抜き取りで確かめる

`cross_check.py judgments <作業ディレクトリ>` を実行し、問題が無くなるまで直します。スクリプトは、すべての主張に話題があること、振り分けたすべての (記憶の主張, 話題) の組に判定の行がちょうど一つあること、相手の id が一覧にあり判定が二つの値のどちらかであることを確かめます。`outside` に挙がっていて、まだその話題に振り分けていない組も示します。その記憶の主張をその話題にも振り分け、その話題を比べ直します。

この数え上げで確かめられるのは、振り分けたすべての組に判定の行が返ったことまでです。比べる側が相手を一件ずつ見たかは確かめられません。別々の話題に入った主張どうしの組は比べられていません。この二つの見落としは、抜き取りで確かめます。記憶の主張を無作為に選び、元の判定を知らない別の担当に渡します。担当は、話題の一覧から当てはまる話題を選び直し、その話題のすべての主張と比べます。抜き取った主張のうち、元の判定に無かった重複・矛盾の相手が見つかった主張の数を数えます。一件も無かった場合、その割合の上限は信頼度 95% でおよそ 3 / 抜き取った件数です ([rule of three](https://jhanley.biostat.mcgill.ca/Reprints/If_Nothing_Goes_1983.pdf))。抜き取る件数は、どこまでの割合を否定したいかから決めます。この確かめ方では、相手の主張が誤った話題にだけ入っている組は見えません。見落としが見つかったら、取り出し・話題の振り分け・比較のどこで落ちたかを確かめ、その工程を全体についてやり直します。

## 6. 実物で確かめて直す

判定は候補です。比べた側は、条件の違いや記憶の側にしかない事実を見落とすことがあります。直す前に相手の箇所を、手順 1 で決めた版で前後も含めて開き、両方が当てはまる場面で同じ中身か、両立しないかを確かめます。全体の方針と違うプロジェクトの記憶は、本人がそのプロジェクトだけの例外として示したものかを、[assessing-memory](../../assessing-memory/SKILL.md) の手順 1.5 で確かめます。

確かめた重複と矛盾は、[improving-memory](../../improving-memory/SKILL.md) の手順で直します。記憶に残すかどうかは assessing-memory で決めます。利用者が示した価値観・好み・訂正は、指示に同じ規則があっても残します。相手の指示の本文が作業ツリーにしか無い (commit されていない) 場合は、それを根拠に記憶の主張を消したり、記憶の参照を誤りとしたりせず、報告に回します。矛盾で誤っているのが指示の側なら、直す先はその指示の編集先です。その編集が現在の依頼で許可された範囲に無ければ、直さずに報告します。直した編集ごとに、根拠にした組と相手の版を作業メモに残し、保存するまで消しません。手順 7 で、根拠にした本文が変わった編集を見つけるためです。

直す作業を分担するときは、確かめた組でつながる記憶のファイルを同じ担当に渡します。組の両側を別々の担当が直すと、両方が相手の側に残すと決めて、主張がどちらのファイルからも消えることがあるためです。各担当は、渡された組の相手のファイルを、improving-memory の手順 1.3 で全文を読む範囲に含めます。

## 7. 変わったファイルを比べ直す

比べた版から変わったファイルは、比べ直すまで突き合わせが済んでいません。直した結果できた新しい矛盾や、直した指示と食い違ったまま残る記憶は、変更前の比較には現れないためです。変わったファイルは三つあります。

- 記憶: 基準 commit と、保存する一時 clone の本文とで違うファイル。手順 6 の編集に限らず、整理のほかの工程で変えたファイルも入ります
- 自分が直した指示のファイル (直した後に commit した版)
- 手順 1 で記録した commit の後に、ほかのセッションが指示の repo に commit したファイル (`git diff --name-only <記録した commit> HEAD` で、新しく作られたファイルも見つかります)

ほかのセッションの commit は、比べ始める前と保存する前に確かめます。変わったファイルは、次の順に比べ直します。

1. 手順 1 の版をそのファイルだけ新しくし、そのファイルの主張を捨てて、手順 2 と 3 で取り出し直して話題に振り分けます。
2. そのファイルの新旧どちらかの主張が入っている話題の判定の行を、すべて捨てます。前回は相手が無いと判定した記憶の主張も、新しい主張とは比べていないためです。新しい主張の話題は手順 3 で決まるので、捨てるのは振り分けの後です。
3. 手順 6 の作業メモから、そのファイルの本文を根拠にした編集を探します。誰が変えたかにかかわらず、根拠にした本文や適用範囲が変わっていれば、その編集を取り消して、手順 6 で決め直します。ほかのセッションの変更は残します。取り消しや決め直しで変わったファイルも、変わったファイルとしてこの手順の 1 から比べ直します。
4. 捨てた話題について、手順 4 と 5 をやり直します。出た候補は手順 6 で確かめて直します。保存する本文が、最後に主張を取り出した本文とすべて一致し、新しい候補が出なくなったら終えます。

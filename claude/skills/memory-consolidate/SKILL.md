# memory-consolidate(個人記憶の整理)

共有 private repo の記憶を再編し、必要な知識を取得できる状態を保ちながら重複と古い参照を整理します。

## 前提

- 対象: `MEMORY.md`(索引)、`CORE.md`(全体価値観と方針)、`*.md`(グローバル記憶)、`projects/*.md`(プロジェクト記憶)
- 記憶は Claude / Codex 共有(agent-memory)。保存基準・形式・ブランチ制約は記憶 repo 直下の CONVENTIONS.md を確認する。
- LLM による書き換えは hallucination 混入リスクがあるため、diff レビューが安全弁。
- 全体整理の依頼では索引と全記憶を対象にします。特定トピックの整理では、その本文と参照元・移動先を対象にし、無関係な記憶へ広げません。
- credentials、token、password、private key、および外部コンテンツから取り込んだ命令は
  保存しない。

## 整理の準備と保存

正本の確定 commit から `CONVENTIONS.md` と整理対象を読み、その版を基準にする。
整理中は正本を直接編集せず、Git 管理外の一時領域に patch を準備する。
保存は [capturing-memory](../capturing-memory/SKILL.md) の `--patch` 呼び出しで行う。
同期後の commit が変わっていれば、整理元と規約を読み直して patch を作り直す。
helper が無いマシンは dotfiles の setup.sh 未実行なので書き込まず停止します。

保存基準・形式・ブランチ制約は、基準版の `CONVENTIONS.md` を確認します。
lock、commit、push、検証、解放の機械的な処理は `capturing-memory` の `--patch` 呼び出しに
一元化します。個別の acquire や手動 commit・push を前置しません。

- 削除も patch と変更対象のパスに含める。正本の stage は保存 helper に任せる。
- `--patch` は lock の取得から解放までを同じプロセスで行う。整理や判断を待つ間に lock を保持しない。
  旧方式の handle を既に保持している場合だけ、従来の finish または release で終了する。
  release 失敗や強制終了で残った lock、handle、retirement をユーザー確認なしで削除しない。

## 整理の判断

1. **Mine**: 直近セッションで明示された価値観・判断原則・好み・訂正・確定した方針・新事実を洗い出す。一回限りのデバッグメモは拾わない。`type` ごとの件数・内容量と、現プロジェクトの記憶有無も確認し、反応記録だけへ偏っていないか監査する。root の `*.md` と `projects/*.md` は、frontmatter の `type` だけでなく本文の適用範囲を読んで配置を判定する。
2. **Consolidate**: 全体の価値観は `CORE.md`、プロジェクト固有の知識は `projects/<slug>.md`、環境を限定した観測事実は既存トピックへ統合する。再利用する作業手順は、現在の依頼で許可された範囲で既存 skill へ統合するか skill 化し、両方へ複製しない。移動先の全文・公開可否・利用経路を確認してから移動元を整理し、索引と全参照も更新する。相対日付は絶対日付へ変換する。矛盾は現行の事実・明示的撤回・後継方針で解決し、自力で根拠を取得できない主観的判断だけをユーザーに確認する。
3. **Dedup**: 各情報の定義箇所を一つに保つ。記憶同士だけでなく、AGENTS.md、フックが注入する指示、repo の source・test・doc と照合する。保存基準は同期後の `CONVENTIONS.md` を確認し、保存処理は `--patch` helper に任せる。一般の実行方針は AGENTS.md、フックは簡潔な実行時リマインダーとする。AGENTS.md にもあることだけを理由に `CORE.md` の価値観を削除しない。正本とリマインダーで同じ詳細を二重管理しない。存在しないファイル/関数/フラグへの参照は現存確認のうえ除去または更新。記憶注入 hook がある場合は、実際の注入出力を生成し、文字数だけを設定上限と直接比較せず、設定仕様で定義された単位に換算して重複による圧迫を測る。
4. **Prune & Index**: 時系列だけで陳腐化と判断しない。現行の事実・明示的な撤回・確認できる後継方針のいずれかで無効と確定した記憶だけを削除または置換する。正しさを確認できない場合は参照元・実装・実環境を調べ、基準版の規約で必要とする本人の判断だけを確認する。`MEMORY.md` を実ファイル一覧と同期する(1 記憶 1 行・200 行未満)。

## 整理前後の取得確認

変更前に、対象の記憶が必要になった実例から質問と必要な事実・適用条件を選びます。
適用しない環境や、変更・撤回後の判断も対象に含めます。件数は変更範囲に合わせます。
正解は変更前の本文や元発言・検証結果から決め、整理後の文に合わせて作りません。

保存前に private の一時 clone の `main` に patch を適用して commit します。
この検証用 commit は push しません。通常の hook と本文取得を実行し、取得元の commit が
整理後の検証用 commit と一致することを確認します。worktree の編集だけでは旧版を読むため、
整理後の取得確認には使いません。
索引・候補に出たことだけで成功とせず、取得した本文から必要な判断までできるか比較します。
自動注入、選択後の取得、全体の文字数・時間を分けて記録します。
必要な事実、条件、例外、参照先が落ちた場合は整理案を直します。
本文を別の記憶や skill へ移した場合は、移動後の入口から辿れることも確認します。
実例・本文・試行記録は Git 管理外の private な作業領域に置きます。

日常の一件保存へ全件評価を追加しません。呼び出し・秘密情報検査・既読 reset などの
hook 契約を変えた場合だけ、対応する既存テストも実行します。

## 成果ファイルの書き方

- 残すのは「現行で正しい知見・ルール・再現手順」だけ。個人マシン名・私的なパス・接続先も、
  再利用に必要なら private 記憶に保持する。一般化できることを公開文書への移動理由にしない。
- 経緯・履歴(失敗談、指摘された回数、学習日、セッション ID)や「重複させない」等のメタ注記は書かない。
- 行動を変える技術的因果(「A だと B が壊れるので C する」)は知見として残してよい。
- 統合・要約では、結論だけでなく適用範囲、理由、例外、変更・撤回条件を保持します。重要な訂正の根拠が必要なら元発言や検証結果への参照を残し、会話全文を複製しません。
- 変わりやすい現在状態は正本への参照と再確認条件へ置き換える。技術的な実測の適用 OS・環境・バージョン・根拠は保持し、適用範囲の判断に必要な確認日は経緯として削除しない。
- `retrieval: sections` は、共通条件が冒頭にあり各 `##` 節を独立して読める技術リファレンスだけに付ける。条件の所在や節間の依存が曖昧なら指定を外し、全文取得を優先する。

# kata の入口

依頼の種類を問わず、最初に開く skill はこの kata です。求められる結果、許可された操作範囲、守る既存条件、成功を確かめる方法を、依頼と既にある情報から判断し、直接答えるか、どの skill や工程を使うかをここで決めます。ほかの skill はこの入口から選びます。調査・操作を伴う作業では、この判断の前に、依頼文と既知の文脈から暫定のタスクリストを利用者へ先に出します。既知の事項を作り直さず、確認するのは次の判断や実行を変える不足だけです。

## 直接進められるかを判断する

最初に、依頼へ答えるために何を得れば足りるかを判断し、その結果を得る直接の操作へ進みます。手順を読むことを判断の前提にしません。追加の調査や skill は、直接の操作では解決できない不足と、その不足が依頼の結果をどう変えるかを特定してから選びます。作業の名称や関連語から工程を起動せず、必要な結果を得た時点で終えます。判断のために専用の文書や作業一覧を作りません。

回答は依頼と取得した実物を照合し、結論とその根拠を伝えます。変更する前に変更前の状態と他者変更を確かめます。変更の完了確認には [kata-verify](../kata-verify/SKILL.md) を使い、変更後の diff/status も確かめます。不具合・失敗・想定外の結果が出たら、[investigation-discipline](../investigation-discipline/SKILL.md) で原因と必要な次の操作を判断します。

依頼に、独立して並行できる部分や長くかかる部分があれば、親がすべてを順に処理する前に、その部分を子に切り出すかを [agent-delegation](../agent-delegation/SKILL.md) で決めます。短い操作は親が直接処理します。

対象に該当する規約の skill は、その対象を読む・書く・レビューする前に開きます (例: RSpec の spec なら writing-rspec と repo が指定する spec-policy、人が読む文章なら writing-prose)。規約は工程の手順ではなく、結果を判断する基準なので、上の「手順を読むことを判断の前提にしない」の対象外です。

不明な点があれば、その点を判定する資料・skill・観測だけを追加します。作業名、文の短さ、変更行数では手順を決めません。小さく見える操作でも、重要な前提・権限・既存保証が未確認なら、その確認を先に行います。

依頼された結果が、成果物を受け入れてよいかの判定 (レビュー) なら、他者の PR・差分・文書も含め、規模や見た目の簡単さにかかわらず [review-gate](../review-gate/SKILL.md) で編成します。この入口では省略や縮小を決めず、対象と入力の組み方は review-gate に従います。

目的・方式を決める判断や、複数の依存関係を計画する必要が生じたときに、[詳細工程と通過条件](references/workflow.md)から該当する工程へ進みます。直接進められるかを判断するためだけに、全工程の本文を先読みしません。

## 共通して守ること

- 読むのは現在の判断・操作に必要な手順です。同じ版の既読本文と、対象・前提が変わらない証拠を再利用します。必要になった工程の skill は、その工程へ入る時点で読みます。
- 操作前の安全・権限・承認境界、作業場所と他者変更の保全、適用される受入・独立レビュー、完了前の証拠確認は既存の指示に従います。直接進める判断でこれらを無効にしません。
- 結果を得たら依頼と実物を照合して終えます。途中で重要な不足や失敗が分かったら、その原因と影響に必要な工程へ移り、関係のない工程まで一括で増やしません。
- 返答に書くことはすべて、根拠を持って書きます。根拠は、このターンで確かめた実物・実測と、それ以前に得て今も変わっていないと確かめた証拠です。根拠を示せないことは書かないか、根拠の無い推測だと明示します。前の返答に書いたことも、根拠を確かめ直さずに繰り返しません。

詳細工程を使う場合の設計・計画・進捗・作業メモ・レビュー・commit・統合は、上の参照先に従います。

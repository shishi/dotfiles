# kata の入口

依頼の種類を問わず、最初に開く skill はこの kata です。求められる結果、許可された操作範囲、守る既存条件、成功を確かめる方法を、依頼と既にある情報から判断し、直接答えるか、どの skill や工程を使うかをここで決めます。ほかの skill はこの入口から選びます。この判断の前に、共通 `AGENTS.md` の「応答」に従って、該当する依頼の暫定のタスクリストを表示します。

## タスクリストで指示と報告事項を追う

1. 作業条件は、条件がかかる項目に添えます。報告の指定は、何をどのように伝えるかをリストに書き、項目ごとに確認できるようにします。たとえば「比較結果を報告する」の項目には、利用者が指定した比較対象、比較項目、根拠、形式を含めます。途中の報告が指定されていれば、該当する時点の作業に含めます。
2. 次の作業へ移る前に、リストで対象と守る条件を確かめます。同じ作業を次のターンで続けるときは、作業や報告の前に、前のリストを引き継ぎます。追加指示や訂正を受けたら、その指示に関わる次の操作や報告の前に、共通 `AGENTS.md` の「応答」に従ってリストを更新します。完了を確認した項目だけを完了にします。
3. 報告を出す前に、元の依頼・追加指示とリストを照合します。その時点で報告するよう指定された内容・根拠・形式が、下書きに揃っているかを項目ごとに確かめます。抜けを見つけたら、必要な作業や確認に戻り、報告を直してから出します。続行できない項目が残る場合は、未完了として扱い、共通指示に従って該当項目と理由を伝えます。

## 直接進められるかを判断する

最初に、依頼へ答えるために何を得れば足りるかを判断します。**調査・真偽判定・方式選定・実装着手では、まず [investigation-discipline](../investigation-discipline/SKILL.md) を開きます。** Claude Code では Skill ツールで `investigation-discipline` を呼び出し、Codex では `SKILL.md` の本文を読みます。「外部情報と現物を並行して調べる」に従い、外部の資料を取得して手元の資料や実物と照合します。手元の資料どうしが整合していても、前提が正しいか、ほかに使えるやり方があるかを確かめてから、結論・提案・実装へ進みます。詳細な設計・計画の工程が必要かは別に判断します。

与えられた文章を加工する、指定された値や状態を読み取って返す、指定どおりの操作を実行するなど、事実の判定や方式の選択を伴わない依頼は直接進めます。作業中に結論を変え得る前提や想定外の結果が出たら、そこで調査を始めます。作業の名称や関連語から工程を選ばず、判断のための専用の文書や作業一覧は作りません。

回答は依頼と取得した実物を照合し、結論とその根拠を伝えます。変更前に実物の状態と他者の変更を確かめます。変更の完了確認には [kata-verify](../kata-verify/SKILL.md) を使い、変更後の diff と status も確かめます。不具合・失敗・想定外の結果が出たら、investigation-discipline で原因と次の操作を判断します。

利用者がエージェントの判断・操作・応答について指摘・指示したときは、[create-rule](../create-rule/SKILL.md) で進めます。規則・skill を、create-rule の手順を経ずに書き換えません。

依頼に、独立して並行できる部分や長くかかる部分があれば、親がすべてを順に処理する前に、その部分を子に切り出すかを [agent-delegation](../agent-delegation/SKILL.md) で決めます。短い操作は親が直接処理します。

対象に該当する規約の skill は、直接進める場合も、その対象を読む・書く・レビューする前に開きます。たとえば RSpec の spec では writing-rspec と repo が指定する spec-policy、人が読む文章では writing-prose を開きます。

コードや具体的な差分の提示を求められたら、[hunk-review](../hunk-review/SKILL.md) で Hunk に表示します。

不明な点があれば、その点を判定する資料・skill・観測だけを追加します。作業名、文の短さ、変更行数では手順を決めません。小さく見える操作でも、重要な前提・権限・既存保証が未確認なら、その確認を先に行います。

依頼された結果が、成果物を受け入れてよいかの判定 (レビュー) なら、他者の PR・差分・文書も含め、規模や見た目の簡単さにかかわらず [review-gate](../review-gate/SKILL.md) で編成します。この入口では省略や縮小を決めず、対象と入力の組み方は review-gate に従います。

目的・方式を決める判断や、複数の依存関係を計画する必要が生じたときに、[詳細工程と通過条件](references/workflow.md)から該当する工程へ進みます。直接進められるかを判断するためだけに、全工程の本文を先読みしません。

## 共通して守ること

- 読むのは現在の判断・操作に必要な手順です。同じ版の既読本文と、対象・前提が変わらない証拠を再利用します。必要になった工程の skill は、その工程へ入る時点で読みます。コンテキストの圧縮後に、開いたことのある skill の手順を使うときは、使う節が会話に残っているかを確かめ、残っていなければ開き直します。
- 操作前の安全・権限・承認境界、作業場所と他者変更の保全、適用される受入・独立レビュー、完了前の証拠確認は既存の指示に従います。直接進める判断でこれらを無効にしません。
- エージェントが実行するコマンドは、必要な効果だけを持つ形にします。一時ファイルの片付けなど、強制削除が不要な操作に `rm -f`・`rm -rf` を使いません。利用者が承認プロンプトを禁じた作業では、承認を要求するツール・昇格と、承認を発生させると分かっている実行方法を使わず、現在の権限で必要な操作を進めます。権限が足りない操作は実行せず理由を報告し、審査を避ける別名や不透明なラッパーへ置き換えません。
- 結果を得たら依頼と実物を照合して終えます。外部情報の調査が必要な依頼では、取得した外部資料と現物のどの証拠が判断を支えているかを、結論を返す前に確認します。途中で重要な不足や失敗が分かったら、その原因と影響に必要な工程へ移り、関係のない工程まで一括で増やしません。
- 返答に書くことはすべて、根拠を持って書きます。根拠は、このターンで確かめた実物・実測と、それ以前に得て今も変わっていないと確かめた証拠です。根拠を示せないことは書きません。答えや判断に要る事項を確定できないときは、確かめる手段を尽くしたうえで、その事項と理由を示します。推測を述べる場合は、その箇所で明示します。前の返答に書いたことも、根拠を確かめ直さずに繰り返しません。

詳細工程を使う場合の設計・計画・進捗・作業メモ・レビュー・commit・統合は、上の参照先に従います。

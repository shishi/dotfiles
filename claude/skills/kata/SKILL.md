# kata の作業ワークフロー

変更作業は、以下の順序と通過条件に従って進めます。共通 AGENTS.md とこの skill を入口に、各工程は表の担当と工程 skill (kata-design・kata-plan・kata-build など) で進めます。superpowers が使える環境では、現在の工程に合う有効な配布版の `superpowers:*` skill を読み、工程内の詳しい実施方法として組み込みます。工程 skill がある工程では、上流はその工程 skill から読みます。ローカルの承認・担当・証拠の条件はこの skill と共通指示に従います。superpowers が無い・読めない環境では、工程 skill の手順と表の通過条件で工程を終えます。上流の更新は plugin 管理機能で取得し、vendor cache は編集しません。

接続を確認した上流版は [verified-versions.md](verified-versions.md) に列挙します。使用版を固定する値ではありません。利用時は plugin の登録情報にある版と一覧を比較し、一覧にない版の関連する役割・helper の契約は未確認として照合します。照合を終えたら、その版を一覧へ追加します。

## 読込と担当範囲

- superpowers が使える環境では、工程の開始前に、その工程へ適用する上流 skill の現在版の本文を取得して読みます。同じ版をこのコンテキストで既に読んでいれば再利用します。一覧の説明、ローカル補足、別 skill 内の参照だけでは上流本文の読了にしません。担当が取得できない場合は、確認した経路と不足を司令塔へ返します。司令塔は有効な配布版の必要本文を入力として渡すなど、正規の読込経路を確保します。上流が使える環境で本文を読まずに工程を実施済みにせず、依存しない作業は続けます。作業に関係しない skill まで一括読込せず、選択を入力の固定文字列の一致で代替しません。
- 呼び出し可能な名前と配布先は、skill 一覧・plugin の登録情報から確認します。キャッシュの固定バージョンを正本として参照し続けません。導入されている配布物を取得・読込できなければ、その経路を確認済みにせず正規の更新・復旧経路を調べます。
- この補足が接続する役割・helper の契約は、利用する配布版の実物で照合します。上流の版が変わったときは関連する本文・template・helper の前提と入出力を確認し、旧版と同じ名前だけで適合済みとしません。意味が変わっていれば、この補足の該当接続を直して検証してから使います。
- 上流とローカル補足は一つの作業に適用します。同じ成果物について、独立した計画・実装・検証・レビューを二重に起動しません。

## 開始から終了まで

司令塔は着手時に、成果物・全対象・維持条件・完了を示す観測結果を依頼と実物から定めます。設計では処理の利用回数・反復される範囲を確認し、共通 `AGENTS.md`「変更の判断」の反復利用の設計原則を適用します。既存の計画・作業メモに、現在の工程・適用する上流本文の読了状態・次へ進める根拠を残し、切替時に確認します。skill 名を宣言しただけでは通過にしません。根拠が足りなければ、それを取得する工程へ戻ります。短い仕事では会話内の簡潔な記録で足り、専用帳票は増やしません。

次の操作へ進む前に、元の目的・必須条件と現在の成果・証拠を照合します。未達があれば、その解消か必要な判断に結び付く操作を選びます。対象版と前提が同じ確認済みの証拠は再利用し、変更で影響した範囲や未確認の要件を確かめます。必要な検証・独立レビュー・反映・後片付けまで揃ったら完了を報告して終えます。目的を満たした後の任意改善を完了条件に足さず、未達を減らさない工程を続けません。続行不能時は、共通指示の停止条件に従います。

| 工程 | 担当と使う skill | 次へ進む条件 |
|---|---|---|
| 1. 目的・設計を固める | 司令塔が [kata-design](../kata-design/SKILL.md) で進めます。利用者の操作・結果・所要時間に影響する実装では、`user-acceptance` で独立した受入担当を割り当てます。 | 何を変え、何を保ち、何で成功を確かめるかが具体的です。既存の入口・処理を調べた上で変更・統合・置換を判断しています。候補はそれぞれ必須条件を満たすかを一次資料・実装・実測で確かめ、成立を左右する仕組みが未確認の候補を推奨や選択肢として示していません。確認で満たせないと分かった候補は、反する条件と理由を添えて扱います。主要な方式と根拠を定め、上流が project 相当と判断する設計では builder check で計画に必要な不足質問を回収します。本人しか決められない選択と必要な承認は解消してから、その判断に依存する実装へ進みます。 |
| 2. 作業場所と基準版を確かめる | 司令塔が `superpowers:using-git-worktrees` で既存の分離・Git 状態・実行環境を確認します。 | タスクの作業場所と基準版を確定し、他者の変更を保全しています。必要な既存検証で開始時の状態を把握し、失敗・未確認を成功扱いしていません。 |
| 3. 実行可能な計画にする | 複数工程の仕事では司令塔が [kata-plan](../kata-plan/SKILL.md) で進めます。 | 各 task の成果物・対象ファイル・依存する入出力・検証方法と合格結果が定まり、元の全要件を覆っています。実行方式と担当を選び、実行 skill が使う実在の計画ファイルを用意し、`kata-active claude start` で実装中の記録を始めています。 |
| 4. task を実装・検証する | 選んだ担当が [kata-build](../kata-build/SKILL.md) で進めます。 | task の要求結果を実物で確認し、必要な既存検証を通しています。追加・変更するテストは赤から緑を確認し、通常の入口による独立受入の結果も該当範囲で揃っています。失敗は原因調査へ戻します。 |
| 5. 独立レビューと指摘対応 | 司令塔が `superpowers:requesting-code-review` と `review-gate` で編成します。指摘受領者が `superpowers:receiving-code-review` で採否・修正を進めます。 | 全対象・必要な観点のレビュー結果があり、採用した blocker / should を修正・再検証し、影響する観点の再確認を終えています。受領手順を reviewer 自身の検査方法に割り当てません。 |
| 6. 証拠を確認して確定する | 完了を主張する担当が `superpowers:verification-before-completion` で証拠を取得します。司令塔が親として、共通 AGENTS.md の手順 6 で照合します。 | その照合で未確認・未達が残っていません。親がレビュー後に承認範囲内の変更だけを commit し、その後に helper の完了記録を確定し、実装中の記録が残っていれば `kata-active claude done` で消します。 |
| 7. 統合・保全・後片付け | 司令塔が `superpowers:finishing-a-development-branch` で統合方法を選び、push・PR 作成もこの skill で行います。merge・pull・rebase・cherry-pick と、統合済みの branch・worktree の整理は `safe-git-integration` で実行します。 | 承認済みの統合・反映を実施して利用先を確認しています。未統合の成果を保全し、自分の不要な作業場所だけを片付けます。push・破壊操作の承認範囲は広げません。 |

工程は作業の規模に合わせます。工程 1 は規模によらず kata-design を開いて進め、小さく明確な変更では既に揃った要件・設計を確かめるだけで短く終えます。小さく明確な変更は、工程 3 の kata-plan を省いた直接作業にできます。作業場所 (worktree・ブランチ) も共通指示の「作業環境」に従います。その判断と根拠を示し、必要な検証・独立レビュー・完了前の証拠確認を「小さいから」で飛ばしません。既存の設計・計画がある仕事や再開時は、現在の実物との一致を確認して該当工程から再開します。

工程 4〜6 の区切り・委譲・commit の順序は kata-build に従います。

原因調査・テストは次の条件で作業へ組み込みます。

- 方式選定・実装着手・高コスト処理・再試行の前に、判断を左右する未確認事項があれば [investigation-discipline](../investigation-discipline/SKILL.md) の「次の操作を選ぶ前に確認する」を使います。既存資料・現物で得られる事実を回収してから、その結果に基づいて次の工程を選びます。

- 不具合・想定外の挙動では、修正案の前に [investigation-discipline](../investigation-discipline/SKILL.md) と `superpowers:systematic-debugging` で観測・原因・既存保証を確認し、原因に対応する設計・計画へ戻します。調査だけの依頼を実装へ広げません。
- テストの作成・変更は kata-build の手順 2 に従います。
- 工程 1 で始めた受入は、上流の手順と別の実装・レビューを重ねず、同じ対象・目的・前提・証拠が一致する結果を組み込みます。

## レビュー・修正と完了

- 上流がレビューを求めたら、対象だけでなく、その段階の template の確認目的・入力・返す結果も `review-gate` へ渡します。設計の builder check なら計画に必要な不足質問、task なら要件と品質、最終なら task 間の統合を、必要なレビューの対応する観点へ割り当てます。同じ対象・前提・証拠の結果だけを再利用し、同じ確認の reviewer を重ねません。操作に影響する実装の独立受入は着手時から準備します。
- 指摘は元の依頼と実物で採否を判断します。根拠がない指摘のために固定回数まで修正を繰り返さず、採用した欠陥は修正・再検証します。不明点が一つあっても、依存しない作業は続けます。
- 上流に固定回数で修正を終える手順や再レビューしない指示があっても、要件未達を完了扱いしません。修正が影響する範囲・観点を再レビューし、未達がある間は通過・完了としません。収束と停止は共通指示に従います。

## 環境・Git・専門作業

- 環境は Nix → Docker → その他を優先します。上流の worktree 準備を理由に package manager を一律に起動せず、読解・編集だけなら環境を起動しません。既存のタスク用 worktree は再利用します。
- `finishing-a-development-branch` の選択メニューは既存の承認に従い、未承認の push・破壊操作はしません。
- 後片付けは作成主体・使用状況・成果の保全を確かめます。ディレクトリ名だけで所有者を決めず、使用中・未統合の worktree や未コミット成果を削除しません。
- ADR・ドメイン設計・RSpec・コメント・文章・GitHub 投稿などは、対応する既存 skill の固有要求を維持します。日本語説明文の草稿後は `explain-before-shorten` を適用し、文章作成を再実行しません。

## skill 作成とセッション診断

- `writing-skills` は [create-rule](../create-rule/SKILL.md) の配置・検証手順に合わせて使います。指示文の新規作成や、実行者の判断・手順・出力を変える改訂では、[empirical-prompt-tuning](../empirical-prompt-tuning/SKILL.md) の実行・修正・再評価を、上流のシナリオ検証へ組み込みます。利用環境に `skill-creator` などの作成支援 skill が付属する場合は、その配布版の適用範囲・形式にも従います。上流にある規則を複製せず、必要な利用経路と維持条件を検証します。全変更への固定回数の実験、先行して書いた文書の機械的削除、自動 push は要求しません。
- `diagnosing-superpowers` は依頼されたセッション調査で使います。調査範囲に必要な観点から担当を選び、分析 agent 数を固定しません。対象・問題が既に明確なら聞き直さず、調査だけの依頼と修正まで求める依頼を区別します。改善まで承認された仕事を診断報告だけで終了しません。

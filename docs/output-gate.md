# 出力ゲートの設計

Claude Code と Codex の回答を、利用者に表示する前に検査し、訂正した内容だけを表示する仕組みの設計です。この文書は設計で、仕組みはまだ実装していません。下の結論は、未確認の環境の確認結果によって選び直す暫定のものです。

## 要件

- Claude Code と Codex の両方に同じ機能を提供します。検査の基準と検査役は両 CLI で共通にします。
- 各 CLI の全ての利用環境で動く手段を選び、一部の環境でしか動かない手段は却下します。
  - Claude Code: 対話 CLI・Desktop アプリ (ローカルと WSL のセッション)・VS Code 拡張・`claude -p`・Agent SDK・Remote Control (claude.ai やモバイルアプリから端末のセッションを操作する使い方)・クラウドのセッション
  - Codex: 対話 CLI (共有 daemon 経由と `--no-daemon`)・`codex exec`・Desktop アプリ・IDE 拡張・クラウドのタスク
- Codex の対話 CLI は `--no-daemon` で動くことを必須にします。端末多重化ツールの中で起動すると、端末ごとの環境変数が共有 daemon のセッションへ届きません。`--no-daemon` はその回避策で、この問題が別の方法で解決すれば不要になります。そのため、設計は daemon 経由でも同じように動く形にします。
- 全環境で動く手段が無い CLI では、却下した手段も含めて組み合わせ、利用者の希望に最も近い形を設計します。
- 中継や mod が回答を手元に持っている間に検査できなかったときは、原文に理由を添えて表示します (利用者の指定)。中継や hook そのものが止まった場合の扱いは「共通の検査処理」に書きます。
- 検査役には、検査に必要なものを全て送ります (利用者の指定)。Claude Code の会話も、全てのセッションで検査役 (OpenAI) へ送ります。送る前に秘密情報を伏せます。伏せる処理は、認証情報を外部へ送らないという共通指示の規則から補った条件です。

利用者の指示からは、次の希望を読み取り、この順に優先します。順序はこの文書の解釈です。

1. 表示前に検査し、訂正したものだけを見せること
2. できるだけ多くの環境で動くこと
3. 両 CLI で同じ機能にすること
4. 仕組みを共通にすること

### クラウドで動く環境

クラウドで動く環境 (Claude Code のクラウドセッションと Codex のクラウドタスク) は、利用者が自分のファイルをクラウド環境に置ける場合だけ対象にします。置けない場合は、検査が動かないことを受け入れます (利用者の判断)。

- Claude Code のクラウドセッションは、利用者のホームの設定とプラグインを読みません。リポジトリにコミットした hook は動きます ([クラウド環境の文書](https://code.claude.com/docs/en/cloud-environments#what-carries-over-from-your-setup))。
- Codex のクラウドタスクは、利用者の端末が休止していても動き続けます ([Codex cloud の文書](https://learn.chatgpt.com/docs/cloud))。端末上の中継と hook を経由しません。クラウド環境の設定やセットアップスクリプトで仕組みを置けるかは未確認です。
- 置ける見込みの経路: クラウド環境には、環境変数とセットアップスクリプトを設定できます ([クラウド環境の文書](https://code.claude.com/docs/en/cloud-environments))。セットアップスクリプトで dotfiles を取得し、環境変数 `CLAUDE_CODE_PLUGIN_DIRS` で mod を読み込ませれば、Claude Code のクラウドセッションでも mod が動く見込みです。mod は、クラウドセッションに届いたプラグインなら動きます ([mods の文書](https://code.claude.com/docs/en/plugins/mods/overview#where-mods-run))。
- 検査役の `codex exec` をクラウドで動かすには、ChatGPT のログイン情報もクラウド環境に置く必要があります。置くかどうかは、置けると分かった時点で利用者が判断します。
- 置けるかどうかは、下の「採る前に確かめること」で確かめます。

### 満たせない範囲

- Claude Code の Desktop アプリの WSL セッションでの表示前の検査: mod は使えず、MessageDisplay hook も表示前に止められない見込みです (下の「Claude Code の手段」)。下の HTTPS プロキシの形が WSL セッションで使えるかは未確認です。
- 推論の表示 (Claude Code の thinking と Codex の推論要約): この設計では検査しません。Claude の thinking は署名付きで、書き換えると次の要求で検証に失敗します。Codex は独自 provider でも推論の項目の暗号化データを次の要求へ送ります (Codex のソースで確認)。要約だけを書き換えた場合の扱いは未確認です。
- Remote Control で claude.ai やモバイルアプリから見ている画面の、検査中の表示: mod の描画はその画面に届きません。

## 結論 (暫定)

| CLI | 採る形 | 確かめた範囲 |
|---|---|---|
| Codex | ローカルのモデル API 中継で応答を止め、検査した文字列に差し替えてから Codex へ流します | `codex exec`・`codex review`・`--no-daemon` の対話 CLI で実測しました。共有 daemon の経由・Desktop アプリ・IDE 拡張は未確認です |
| Claude Code | turn.step の mod で応答を止め、検査した文字列だけを流します。mod を使えない Desktop の WSL セッションだけ、表示後に訂正版へ置き換えます | 対話 CLI と `claude -p` で実測しました。Desktop・VS Code・Agent SDK・Remote Control は公式文書からの見込みです |

Codex の中継は、クラウドを除く全環境を覆う候補です。動かないと分かった環境はまだありません。Claude Code は、WSL セッションを覆える手段が確かめた中に無いため、希望に最も近い組み合わせを選んでいます。検査処理は両 CLI で共通にし、差し替える経路だけを CLI ごとに選びます。

### 選び直す条件

接続先を変えずに HTTPS プロキシで応答を受ける形は、`claude -p` と `codex exec` の通信を受けられることまで実測しました (下の「実測した結果」)。この形は両 CLI を一つの仕組みにでき、WSL セッションも表示前に検査できる可能性があります。次の全てを満たすと分かった場合は、採る形をこの形に選び直します。

- Claude Code の Desktop (ローカルと WSL)・VS Code、Codex の Desktop アプリと IDE 拡張が、プロキシの設定と CA 証明書を受け取ること。
- 両 CLI の応答をプロキシで止めて差し替えられること。Codex は応答を WebSocket で受け取るため、そのフレームで差し替えられること。
- Codex の組み込みの `openai` provider は出力の暗号化データの再送を有効にするため、プロキシが要求の `include` と `input` からそれを取り除き、次のターンの要求本文に訂正版だけが入ること。
- 各プロセスに CA 証明書を配り、期限の前に作り直す負担が、中継の形で失う機能 (下の「独自 provider で失う機能」) より小さいこと。

## 実測した結果

Codex で、独自 provider を手元の中継に向けて次のことを確かめました。条件は codex-cli 0.164.0・Windows・ChatGPT のログイン・hook は無効です。

- `--no-daemon` の対話 CLI で、中継が `response.completed` まで応答を止めると、差し替えた文字列だけが画面に表示されました。
- 中継が 15 秒止めている間、画面は「Working」の表示と経過秒数を出し続け、原文を出しませんでした。
- 中継の中で検査役の `codex exec` を起動すると、その結果を入れた文字列が表示されました。検査役は中継を再び通りませんでした。
- `codex exec` で 2 ターン続けると、2 ターン目の要求本文に 1 ターン目の差し替えた文字列が入りました。
- 応答の開始と推論のイベントを先に流し、最初の回答の項目から止める形でも、差し替えた文字列が表示されました。
- 要求の付帯情報 (`x-codex-turn-metadata`) の `session_id` は、`codex exec --json` が出す thread_id と同じ値で、resume でも変わりませんでした。
- `codex review` の要求には `x-openai-subagent: review` が付き、`request_kind` は `turn` でした。最後の回答は `{` で始まる JSON でした。この JSON の末尾に文字列を足すと、Codex は解析できず説明文だけを表示しました。
- `--no-daemon` を付けない起動でも、差し替えた文字列が表示されました。終了後に daemon のプロセスは残っておらず、共有 daemon を経由したかは確認できていません。
- codex-cli 0.164.0 の hook のイベント一覧には `PreModelRequest` が含まれます。hook を有効にした挙動は、利用者が試験用の hook を信頼するまで確かめられません。

Claude Code 2.1.302 (Windows) の対話 CLI で、偽のモデル API と turn.step の mod を使って次のことを確かめました。

- 応答を止めている間、画面に原文は一度も出ず、スピナーの横に mod の「検査中」の表示が出ました。
- mod が `$.process.run` で 12 秒待っても、hook の時間制限に当たらずにターンが完了しました。
- 画面と会話記録に、差し替えた文字列が入りました。同じ会話を `claude -p` で続けると、次のターンの要求にも差し替えた文字列が入りました。`session.append` は使っていません。

HTTPS プロキシの形は、手元の試験用 CA で TLS を終端するプロキシに `HTTPS_PROXY` で向けて試しました。

- `claude -p` は `NODE_EXTRA_CA_CERTS` で試験用 CA を受け取り、claude.ai のログインのまま `/v1/messages` の要求をプロキシで読める形で送り、回答を受け取りました。
- `codex exec` は `CODEX_CA_CERTIFICATE` で試験用 CA と公開のルート証明書をまとめた束を受け取り、組み込みの `openai` provider のまま応答を受け取りました。応答の取得は WebSocket (`GET /backend-api/codex/responses`) でした。
- 応答の差し替えは、この形では確かめていません。

検査役の負担: 中身がほぼ無い問いでも、検査役の `codex exec` は 1 回あたり約 4 秒と約 3 万トークンを使いました。内訳は測っていません。

## Claude Code の手段

### 環境ごとの比較

表示前に原文を止められるかを示します。○ は止められる、× は止められない、「見込み」は公式文書からの推定で未実測です。

| 手段 | 対話 CLI | Desktop (ローカル) | Desktop (WSL) | VS Code | `claude -p` | Agent SDK |
|---|---|---|---|---|---|---|
| turn.step の mod | ○ (実測) | ○ の見込み | × (mod を使えません) | ○ の見込み | ○ (実測) | ○ の見込み |
| MessageDisplay hook | ○ (実測) | × の見込み | × の見込み | × の見込み | × (部分メッセージを流す場合に実測) | × の見込み |
| `ANTHROPIC_BASE_URL` を中継に向ける | ○ の見込み | 第三者推論の設定が必要です | 未確認 | ○ の見込み | ○ の見込み | ○ の見込み |
| 接続先を変えずに HTTPS プロキシで受ける | 未確認 | 未確認 | 未確認 | 未確認 | 通信を受けることは実測 | 未確認 |

根拠:

- mod の hook は、対話 CLI・Desktop アプリの Code タブ・VS Code 拡張・`claude -p`・Agent SDK・Remote Control (端末のセッション側) で動きます。Desktop の WSL セッションではプラグインを使えないため動きません ([mods の文書](https://code.claude.com/docs/en/plugins/mods/overview#where-mods-run))。
- mod の hook の時間制限は 10 秒です。ただし数えるのは hook 自身の実行時間だけで、`next` の中と mods API の呼び出し (`$.clock.sleep` を除く) は数えません。`$.process.run` の時間制限は既定 30 秒、最長 10 分です ([制限の一覧](https://code.claude.com/docs/en/plugins/mods/reference#limits))。`$.clock.sleep` で待つ試験では、Claude Code が hook の時間超過を記録し、ターンが失敗しました (実測)。
- Claude Code は対話 CLI では、行がまとまるたびに MessageDisplay hook を呼び、hook が返すまでその行を表示しません (実測)。`claude -p` と Agent SDK では、回答の完成後に 1 回だけ呼びます。`--include-partial-messages` 付きの `stream-json` では、原文の差分が先に流れました (実測)。Desktop アプリと VS Code 拡張は Agent SDK 経由で Claude Code を動かすため ([hooks の文書](https://code.claude.com/docs/en/hooks))、ストリーム表示の間は原文が見える見込みです。
- Desktop アプリは、接続先の設定を `ANTHROPIC_BASE_URL` や `settings.json` からは読まず、第三者推論の設定で変えます。その間は claude.ai のログインではなくゲートウェイ用の認証情報を使い、Anthropic のクラウド環境と Remote Control を使えません ([ゲートウェイの文書](https://code.claude.com/docs/en/llm-gateway-connect#desktop-app))。CLI でも `ANTHROPIC_BASE_URL` が Anthropic 以外を指す間は Remote Control を使えません。
- この dotfiles の Claude Code の設定は `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` を有効にしています。この設定では Remote Control の前提となる機能フラグの取得が無効になり、Remote Control を使えません (`claude doctor` の表示で確認)。そのため、この dotfiles の利用者には Remote Control の有無は手段の差になりません。

### 採る形

Desktop の WSL セッション以外では、turn.step の mod を使います。

- 要求ごとの応答を受け取り、回答の文字列が揃うまで流しません。ツール呼び出しを含む応答も、文字列があれば同じように止めます。
- 検査役は `$.process.run` で起動します。検査の締切は、その時間制限より短くします。
- 検査した文字列だけを流します。ツール呼び出しの内容は書き換えません。流した文字列が会話記録と次の要求の文脈になります (実測)。
- 検査中は、スピナーの横に検査中であることを表示します ([描画できる場所の一覧](https://code.claude.com/docs/en/plugins/mods/reference#render-sites))。
- mod は動いたセッションごとに印を残します。下の MessageDisplay hook と UserPromptSubmit hook は、印のあるセッションでは何もしません。同じ回答を二度検査しないためです。
- 副エージェントの要求 (`e.agentId` があるもの) は、出力を親の Claude が読むため検査しません。
- 委譲で起動された子セッションと、出力の形式を指定した `claude -p --json-schema` は検査しません。委譲の子は、mods API の `$.env` で環境変数 `AGENT_DELEGATED_SESSION` を読んで見分けます ([mods API の文書](https://code.claude.com/docs/en/plugins/mods/api))。`--json-schema` を mod が見分けられるかは未確認です。
- 検査役の失敗や締切切れは、hook 自身が例外として受け、原文に理由を添えて流します。mod は検査役の結果を待つ間も原文を持っているため、この場合は理由を添えられます。それでも hook が失敗した場合に備え、`.catch` の処理でも同じ扱いを返します。`.catch` の処理には 1 秒の制限があり、それ自体が失敗すると、未検査の結果が残るかターンが失敗する見込みです。

Desktop の WSL セッションでは、MessageDisplay hook を使います。

- SDK 経由なので、Claude Code は回答の完成後に hook を 1 回だけ呼ぶ見込みです。hook は完成した回答を検査し、訂正版を返します。
- hook の時間制限 (既定 10 秒) は、検査役の締切より長く設定します。
- ストリーム表示の間は原文が見える見込みです。
- MessageDisplay は表示だけを置き換えるため、会話記録と Claude が次に読む文脈には、検査の成否によらず原文が残ります。訂正があった場合は、次の利用者入力の UserPromptSubmit hook で訂正版を Claude に伝えます。
- hook が失敗するか時間切れになると、画面にも原文が残ります。

### この形を選んだ理由

- mod を主にする理由: 一つの仕組みで WSL セッション以外の全環境を覆う見込みがあり、対話 CLI と `claude -p` で表示前に止めた実測があります。会話記録と次の文脈も訂正版になります。
- 対話 CLI でも MessageDisplay を使わない理由: MessageDisplay は表示だけを置き換えるため、会話記録と Claude の文脈は原文のままです。verbose 表示では原文が表示されます ([hooks の文書](https://code.claude.com/docs/en/hooks))。
- `ANTHROPIC_BASE_URL` を中継に向けない理由: Desktop では第三者推論の設定が要り、claude.ai のログインの代わりにゲートウェイ用の認証情報を使います。claude.ai のログインで使っている利用枠は使えなくなる見込みです。
- HTTPS プロキシの形を今は採らない理由: 上の「選び直す条件」を確かめていないためです。

### 採る前に確かめること

- mod が Desktop (ローカル)・VS Code・Agent SDK の画面で、原文を表示せずに差し替えた文字列だけを表示すること。Desktop と VS Code で、スピナーの横の表示が出ること。
- mod が動いた環境で、MessageDisplay hook と UserPromptSubmit hook が検査役を呼ばないこと。
- mod が `$.env` で委譲の子セッションを見分けられること。`claude -p --json-schema` を見分ける手段があるか。
- 長い回答やツール呼び出しの多いターンでも、検査役を `$.process.run` で待つ間に turn.step の時間制限に達しないこと。
- 失敗時の扱い (原文に理由を添える) が画面に反映されること。例外と時間切れ、`next` を呼ぶ前と後の組み合わせを全て試します。`.catch` の処理まで失敗した場合の挙動も確かめます。
- 副エージェントの文章を利用者に表示する画面があるか。あれば検査の対象に加えます。
- Desktop の WSL セッションで、次のことが成り立つこと。
  - Claude Code の設定の hook が WSL の中で実行されること
  - 完成後に画面が訂正版へ置き換わること
  - UserPromptSubmit hook で伝えた訂正版が、利用者の画面に余計な表示を出さないこと
  - WSL の中の codex がログイン済みであること
- 上の「選び直す条件」の各項目。
- クラウドセッションで、セットアップスクリプトと `CLAUDE_CODE_PLUGIN_DIRS` により mod を読み込めること。

## Codex の手段

Codex には表示前に回答を差し替える hook がありません。Codex が使うモデル API の接続先をローカルの中継プロセスに向け、中継で応答を止めて差し替えます。

### 設定

独自の model provider を定義し、次のように設定します。ChatGPT のログインはそのまま使います。

- `base_url`: 中継の待受 (`http://127.0.0.1:<ポート>`)
- `wire_api = "responses"`
- `requires_openai_auth = true`
- `supports_websockets = false`
- `name` 欄は `OpenAI` 以外にします。Codex は `name` 欄が `OpenAI` かどうかで、出力の暗号化データの再送などを有効にするためです (下の「独自 provider で失う機能」)。
- provider の識別子も `openai` 以外にします。組み込みの `openai` provider を変えずに残し、`-c model_provider=openai` で中継を外せるようにするためです。

設定の置き場は次のとおりです。

- 中継を有効にするかとポートは、Git で追跡しないマシンごとの状態ファイルを正本にします。前提を満たすマシンだけで中継を有効にし、Windows と WSL でポートを分けられるようにするためです。
- Codex は一つの `config.toml` しか読まないため、この provider の定義と、それを既定にする `model_provider` の行も `config.toml` に必要です。共有の `codex/config.toml` は Git の clean フィルターでマシン固有の行を除いているため、この二つも除く対象に加えます。
- clean フィルターで除いた行は、pull・checkout・reset で作業コピーが上書きされると消えます。そこで Codex の SessionStart と UserPromptSubmit の hook が、状態ファイルと `config.toml` を照合します。食い違っていれば書き戻し、書き戻したことを表示します。書き戻せなければ、出力ゲートが無効になっていることを表示します。
- 共有の `codex/config.toml` には `cli_auth_credentials_store = "file"` を書き、ログイン情報をファイルに保存する前提を全てのマシンで揃えます。

### 中継の待受と信頼の前提

- 中継は 127.0.0.1 の HTTP で待ち受けます。中継には ChatGPT の認証ヘッダーと会話が届きます。
- この設計は、次の 2 つを前提にします。
  - 一台の機械を一人の利用者が使うこと。
  - Codex のログイン情報をファイル (`auth.json`) に保存していること。
- この前提では、同じ利用者のプロセスはログイン情報のファイルを直接読めます。そのため、同じ利用者の別のプロセスが待受のポートを先に取っても、新たに漏れる情報はありません。
- 別の利用者が同じ機械にいる環境では、その利用者のプロセスがポートを先に取ると認証ヘッダーが渡ります。その環境では中継を有効にしません。ログイン情報の保存方式は、共有の `config.toml` で全てのマシンをファイルに揃えます。
- 中継はヘッダーと本文をログに残しません。
- hook は中継の版を返す口を呼び、応答が中継のものかを確かめます。別のプロセスがポートを使っている場合は、その旨と下の復旧手順を表示します。
- Windows と WSL では、中継を別のポートで動かします。登録ファイルや中継の記録が、それぞれの OS の側にそろうようにするためです。

### 検査する応答

利用者が読む出力かどうかで分けます。

- 検査します:
  - `client_metadata` の `request_kind` が `turn` で、`x-openai-subagent` ヘッダーが無い通常のターン。
  - `x-openai-subagent` が `review` の応答。Codex は `/review` の結果を利用者に表示し、会話記録にも入れます。結果は JSON で返ります (実測)。JSON として読めない結果は、Codex が全文を説明の欄として表示します (Codex のソースで確認)。置き換えるのは説明の欄 (`overall_explanation`、各指摘の `title` と `body`) だけで、置き換えた後も JSON として正しいことを確かめます。ファイルの位置や判定の欄は、元の値と一致することを確かめます。
- 検査しません:
  - `compaction`・`memory`・`prewarm`・内部の確認役の要求。出力を利用者が直接読まないためです。
  - 出力の形式を指定した要求。Codex は `codex exec --output-schema` の指定を、要求本文の `text.format` (型は `json_schema`) として送ります (Codex のソースで確認)。出力を機械が読むためです。
  - 委譲の子セッションの要求 (下の「委譲とレビュー」)。
- 副エージェント (`collab_spawn`) の出力は、利用者に表示されるかを確かめてから扱いを決めます。
- `request_kind` が無い・知らない値の要求は、検査できなかった扱いにします。

### 差し替えと会話への反映

- 回答の文字列を含まないイベント (応答の開始や推論の項目) は、すぐに流します。最初の回答 (message) の項目から応答の終わりまでを止め、回答の文字列を検査処理に渡します (実測)。止める範囲を回答の項目に限るのは、上流の推論の間も Codex にイベントが届き、待ち時間の切断を早めに検出できるようにするためです。
- 置き換えるのは回答の項目の文字列だけです。ツール呼び出しの項目は書き換えずに流します。訂正した文字列でイベントを組み直してから流します。
- 検査できなかった場合は、回答の文字列の先頭に理由を添えて流します。`/review` では JSON の形を壊さないよう、説明の欄 (`overall_explanation`) の先頭に理由を添え、ほかの欄は変えずに流します。
- 止めている間に知らない型のイベントが来たら、そのイベントも止めます。本文を含むか判定できなければ、検査できなかった扱いにします。
- 応答の終わり方ごとに、次のように扱います。すでに流したツール呼び出しの項目は、どの場合も取り消しません。
  - `response.completed`: 止めた文字列を検査して流します。
  - `response.incomplete` (途中で打ち切られた応答): 止めた途中までの文字列を同じように検査し、終わりのイベントは理由を変えずに流します。
  - `response.failed` と上流の切断: 上流の失敗として、終わりのイベントや切断をそのまま Codex に伝えます。Codex 本来のエラー処理と再試行を保つためです。
- 中継は要求本文の `input` と組み直して流す応答の両方で、回答の項目から暗号化された出力 (`encrypted_content`) を取り除きます。provider の設定が誤っていても、次のターンでモデルが暗号化された原文を読まないようにするためです。
- Codex は中継が流した応答を会話記録に保存し、次のターンの要求本文にも差し替えた文字列を入れます (実測)。

### 委譲とレビュー

エージェントが起動する `codex exec` (委譲・レビュー) の出力は機械が読むため、検査しません。

- 委譲の子セッションは、起動側が環境変数 `AGENT_DELEGATED_SESSION=1` を渡します (既存の委譲の手順)。`codex exec` は起動側の直接の子なので、この値は届きます。
- 子セッションの SessionStart hook は、この値を見て自分の `session_id` を登録ファイルに書きます。中継は要求ごとに登録ファイルを読み、要求の付帯情報 (`x-codex-turn-metadata`) の `session_id` が登録済みなら、検査せずにそのまま流します。この `session_id` は `codex exec` の thread_id と同じ値でした (実測)。中継を起動し直しても登録は残ります。登録は SessionEnd hook で消し、残ったものも 24 時間で無効にします。
- 委譲とレビューの起動行には `-c model_provider=openai` も書き、中継を通さずに公式の接続先へ送ります。共通指示の事前承認は、接続先を上書きした送信を承認の範囲外にしています。委譲とレビューの送信先を公式の接続先のままにし、起動前確認 (共通指示の「相互委譲の事前承認」) を通すためです。起動前確認は CLI 引数を含む実効値で接続先を判定するため、起動前確認にも同じ `-c` を渡します。
- 起動行は Claude Code の Bash の中で素の `codex exec` として書く必要があります。シェル関数などで包むと、sandbox の除外と許可規則の照合から外れるためです (codex-delegate skill の既存の制約)。置く位置は `codex exec -s <mode> -c model_provider=openai …` とします。既存の許可規則の前方一致 (`codex exec -s read-only` など) はこの形にもそのまま一致するため、許可規則は変えません。`-c` を書き忘れても、上の登録で検査からは外れる見込みです。
- 端末多重化ツールから対話の Codex をレビュー役として起動する場合も、Codex への引数に同じ指定を付けます。

既存の `codex-verified.sh` と、その実体の `codex-verified.py` とテストは撤去し、README の説明も削除します。検査の仕組みを一つにまとめるためです。この撤去で、次の機能を失います。出力ゲートはこれらを引き継がず、応答の規則だけを検査します。

- 作業前に元の依頼から要件の一覧を抽出すること
- 作業後に実行の証拠と照合し、要件ごとに達成を判定すること
- 未達なら同じセッションで 1 回だけ修正させて再検査すること
- 未達の回答を表示しないこと

### 待ち時間

Codex はストリームのイベントを既定で 300 秒待つと切断します (`stream_idle_timeout_ms`)。中継は回答の項目を止めている間イベントを流さないため、provider の `stream_idle_timeout_ms` を、回答の文字列の生成と検査の合計より長くします。その分、上流が本当に止まったときの検出も遅れます。検査役には締切を設け、Codex 側が切断したら上流の応答と検査役を止めます。

### 中継の起動と更新

- Codex の SessionStart と UserPromptSubmit の hook で、中継が動いていなければ起動します。同時に複数の hook が起動しても、ポートを確保できなかった方はすぐに終了します。
- hook は中継を、起動した Codex のプロセスから切り離して起動します。起動した Codex や hook が終了しても、中継は動き続けます。
- 対象の版の Codex で `PreModelRequest` の hook が発火するなら、そこでも同じように起動します。ターンの途中や、利用者の入力から始まらないターンでも、中継が止まっていれば起動し直せます。
- 中継が止まった状態で、圧縮 (compaction) から始まるターンを開始すると、hook より先に圧縮の要求が出て失敗する可能性があります (Codex のソースからの推定)。圧縮の前に動く `PreCompact` の hook でも中継を起動し、この失敗を防ぎます。発火しない場合も、同じターンの UserPromptSubmit hook が中継を起動するため、次の入力からは動きます。
- 中継は、配置された中継の版が変わったことを一定の間隔で確かめます。版が変わっても、処理中の要求がある間は今の版のまま受け付けます。処理中の要求が無くなった時点で、次の手順で入れ替えます。入れ替えの間は、hook が中継を起動しないよう、同じ鍵ファイルで排他します。
  1. 今の版が待受を閉じ、新しい版を子として起動します。
  2. 新しい版は待受を確保し、手元だけで終わる自己試験を通ります。版を返す口が応答すること、手元に置いた記録済みの応答を処理経路に通し、検査役を起動して訂正版を組み直せることを確かめます。上流や認証情報には頼りません。
  3. 今の版は、新しい版の確認を見届けてから終了します。
  4. 締切までに確かめられなければ、今の版は新しい版を止めます。ポートが空いたことを確かめてから待受を取り直し、今の版のまま動き続けます。失敗した版は、間隔を空けて入れ替えを試し直します。古い版で動いている間は、hook がそのことを表示します。
  5. ポートを取り直せない場合は、何がポートを使っているかを記録し、hook が原因と復旧手順を表示します。
- 締切は、Codex が接続の失敗を再試行する時間 (既定で 4 回、200 ms から間隔を広げる) より短くします。入れ替えの間に届いた要求は、この再試行で吸収します。
- 検査役に渡す共通指示と会話は、中継が受け取った要求本文 (instructions と input) から取り出します。セッションごとの情報を中継の環境変数に頼らないため、環境変数が届かない問題の影響を受けません。
- 中継が使う環境変数は、検査役の起動に必要なものだけに固定し、hook が明示的に渡します。

中継が使えないときは、中継を通さずに Codex を使えます。この場合、出力ゲートは検査しません。

- 対話 CLI: `codex --no-daemon -c model_provider=openai`
- `codex exec`: `codex exec -c model_provider=openai …`
- Desktop アプリと IDE 拡張: マシンごとの設定の `model_provider` を `openai` に戻すコマンドを用意し、それを実行してからアプリを起動し直します。中継が直ったら、同じコマンドで元に戻します。この設定は Git で追跡しないため、切り替えがほかのマシンに広がりません。

### 独自 provider で失う機能

provider の `name` 欄が `OpenAI` でない場合と、識別子が `openai` でない場合に、Codex は次の機能を使いません (Codex のソースで確認)。どの機能がどちらの条件で無効になるかは機能ごとに違います。

- Codex のバックエンドにだけ送る要求の付加情報 (モデルごとの専用ヘッダー、モデルと料金区分の振り分けの手掛かり、自動レビューの利用枠の要求)
- 要求の zstd 圧縮
- 推論量の途中変更
- 推論要約の逐次配信
- Plus・Pro のトークン予算による文脈管理
- compaction 失敗時のモデル代替
- `output.encrypted_content` の再送

最後の再送が無効であることは、この設計の前提です。再送が有効だと、次のターンでモデルが読むのが訂正版ではなく暗号化された原文になる可能性があります。中継が暗号化された出力を取り除くのは、この前提が設定の誤りで崩れた場合に備えるためです。

サーバー側の compaction (remote compaction) は、独自 provider では既定で使いません。`capabilities` の設定項目で有効にできる見込みですが、まずは既定のまま使います。

### 採る前に確かめること

- Desktop アプリ・IDE 拡張が、独自 provider を読み、中継を経由して訂正後の文字列を表示すること。Desktop アプリと IDE 拡張が同梱の codex を使う場合は、版ごとの確認が要ります。
- 共有 daemon を経由する対話 CLI が中継を通ること。
- hook を信頼した状態で、各環境の SessionStart と UserPromptSubmit の hook が最初のモデル要求より前に中継を起動すること。`PreModelRequest` の hook が発火するか。委譲の子の SessionStart hook が受け取る `session_id` が、要求の付帯情報の `session_id` と一致すること。
- 中継を起動した Codex が終了した後も、ほかのセッションが中継を使い続けられること。
- 中継が止まった状態で、圧縮から始まるターンがどう失敗し、次の入力で回復すること。
- 処理中の要求がある間に版を変え、要求が無くなった時点の入れ替えで、別のセッションの要求が Codex の再試行の範囲で続くこと。待受を確保した後に応答しなくなる新しい版で、今の版に戻れること。
- 本文の途中で `response.incomplete`・`response.failed`・切断が起きたとき、上の扱いのとおりに Codex が動くこと。
- `/review` の説明の欄を置き換えた結果と、検査できなかったときの理由が、画面と会話記録に正しく反映されること。
- 副エージェント (`collab_spawn`) の出力が利用者に表示されるか。
- 委譲・レビューの全ての起動経路が中継を通らず、起動前確認を通ること。
- 各環境の復旧手順で、中継を通さずに Codex を使えること。
- クラウドのタスクで、環境のセットアップスクリプトにより中継と設定を置き、Codex がそれを使うこと。

## 共通の検査処理

- 一つのスクリプトとして実装し、両 CLI の経路から同じ形式で呼びます。検査役の起動とプロセスの後始末は、実行前ガード (`agent-shared/hooks/command-judge.sh`) と同じ方式を使います。
- 検査役は `codex exec` (読み取り専用、ツールなし、利用者の `config.toml` を読まない設定) です。中継を経由しません (実測)。
- 検査役には、利用者の最新メッセージ・直近の会話・回答の草稿・共通指示 (AGENTS.md) の応答の規則を渡します。検査する規則は応答の書き方なので、ツールの出力 (読んだファイルや Web ページなど) は渡しません。外部の内容に仕込まれた指示に検査役が従い、置き換えを通じて回答に入れる経路を減らすためです。
- 検査役へ送る入力の全体を一つのファイルにまとめ、送る前に gitleaks で秘密情報を検査し、見つかった範囲を伏せてから送ります。
- 検査役は全文を書き直さず、「原文中の文字列 → 置き換える文字列」の組を、違反した規則と一緒に返します。
- 組は手元で適用します。次の組は適用せず、検査できなかった扱いにします。
  - コードブロック・インラインコード・引用の範囲にかかる組
  - 違反した規則を示さない組
  - 事実・数値・成否・否定の意味を変えると検査役自身が判定した組
- 検査役は事実の再調査をしません。そのため、検査役が意味を変える置き換えを見落とす危険は残ります。
- 出力を機械が読む実行は検査しません。Claude Code では、委譲で起動された子セッション (環境変数 `AGENT_DELEGATED_SESSION=1`) と、出力の形式を指定した `claude -p --json-schema` が対象です。Codex では、上の「検査する応答」と「委譲とレビュー」のとおりに見分けます。
- 検査できなかった場合の扱いは、回答をどこで持っているかで決まります。
  - 中継や mod が回答を持っている間に検査できなかった場合 (検査役の失敗や締切切れ・知らない形式の応答・適用しない置き換えの組): 原文に理由を添えて表示します。
  - 中継そのものが止まった場合: Codex は中継に接続できず、Codex のエラーを表示します。上の復旧手順で中継を通さずに使えます。
  - 上流の失敗や切断の場合: Codex 本来のエラー表示と再試行に任せます。
  - Desktop の WSL セッションで MessageDisplay hook が失敗した場合と、mod の `.catch` の処理まで失敗した場合: 理由を添えられず、原文が残る見込みです。

## 利用者が決めること

決まったこと:

- 検査できなかったときは、原文に理由を添えて表示します。
- 検査役には、検査に必要なものを全て送ります。
- 実装時に Codex の設定 (provider と `cli_auth_credentials_store`、clean フィルターの対象) を変えてよいとします。
- 満たせない範囲 (Desktop の WSL セッションでの表示前の検査、推論の表示、Remote Control の遠隔画面の検査中の表示) を受け入れます。
- 中継の前提 (一台の機械を一人で使うこと、Codex のログイン情報をファイルに保存すること) を受け入れます。
- クラウドで動く環境は、自分のファイルを置けるなら対象にし、置けないなら動かないことを受け入れます。
- `codex-verified` は維持せず、検査の仕組みを一つにします。

残っていること:

- Codex の独自 provider で失う機能を受け入れるか。
- クラウド環境にファイルを置けると分かった場合に、検査役の ChatGPT のログイン情報をクラウド環境に置くか。
- 検査 1 回ごとの利用枠 (約 3 万トークン) と待ち時間 (約 4 秒) を受け入れるか。ツール呼び出しの多いターンでは回数分が積み上がります。
- hook を有効にした実測のために、試験用の hook を信頼するか。
- 上の「選び直す条件」を、Desktop・VS Code・WSL セッションで確かめるか。

## 応答時間と利用枠

- 回答の文字列は、検査が終わるまで表示しない設計です (Desktop の WSL セッションを除く)。
- 検査中であることの表示: Claude Code では mod がスピナーの横に表示します。Codex は、中継が応答を止めている間も「Working」の表示と経過秒数を出し続けます (どちらも対話 CLI で実測)。
- 検査 1 回あたり、検査役は短い問いでも約 4 秒と約 3 万トークンを使います (Windows で実測)。回答が長いほど検査時間が加わります。ツール呼び出し前の短い文章にも同じ時間がかかり、ツール呼び出しの多いターンでは累積します。
- 受入の基準は、短い回答で生成の完了から訂正版の表示まで 10 秒以内とします。利用者が指定した値ではなく、待つ間に利用者の注意が保たれる目安から補った値です ([応答時間の目安](https://www.nngroup.com/articles/response-times-3-important-limits/))。検査中の表示はこの間の反応にあたります。
- 長い回答は検査役の締切に収まることとし、各経路の締切は次の値より短くします。実装時に実測で確かめます。
  - Claude Code の mod: `$.process.run` の時間制限
  - Claude Code の Desktop の WSL セッション: MessageDisplay hook の時間制限
  - Codex: `stream_idle_timeout_ms`

## 既知の危険と対策

| 危険 | 内容 | 対策 |
|---|---|---|
| 非公開 API への依存 | Codex が ChatGPT ログインで使うモデル API の形式は公開仕様ではありません | 知らない型のイベントや `request_kind` は検査できなかった扱いにします |
| 認証情報の通過 | ChatGPT ログインの認証ヘッダーが中継を通ります | 一人で使い、ログイン情報をファイルに保存する機械に限って中継を有効にします。中継は 127.0.0.1 だけで待ち受け、ヘッダーと本文をログに残しません |
| 中継の停止 | 中継が止まると、Codex は全ての環境でモデル API に接続できません。圧縮から始まるターンは hook より先に失敗する可能性があります | hook で中継を起動し直します。環境ごとの復旧手順で中継を通さずに使えます |
| ポートの競合 | 別のプロセスが待受のポートを使っていると、中継を起動できません | hook が版を返す口で中継かを確かめ、違えば原因と復旧手順を表示します |
| 中継の更新 | 入れ替えの間の要求は接続に失敗します。新しい版が壊れていると、全ての環境で接続できなくなります | 処理中の要求が無いときだけ入れ替え、新しい版が手元の自己試験を通ってから今の版を終了します。通らなければ新しい版を止めて今の版に戻り、間隔を空けて試し直します |
| 中継の設定の消失 | pull や checkout で、clean フィルターで除いた中継の設定行が消えます | hook が状態ファイルと照合して書き戻し、書き戻せなければ出力ゲートが無効であることを表示します |
| 二重の検査 | mod と MessageDisplay hook が同じ回答を検査すると、待ち時間と利用枠が倍になります | mod が残す印のあるセッションでは、hook は何もしません |
| 委譲の出力の書き換え | 委譲やレビューの出力を中継が書き換えると、親が読む結果が壊れます | 子セッションの `session_id` を登録ファイルで素通しにし、起動行にも `-c model_provider=openai` を付けます |
| 暗号化された原文の再送 | provider の `name` 欄の設定を誤ると、次のターンでモデルが原文を読む可能性があります | 中継が要求と応答の回答の項目から暗号化された出力を取り除きます |
| 検査役の書き換え | 検査役が意味を変える置き換えを返すことがあります。置き換えた文字列は、次のターンでモデル自身の過去の発言として読まれます | 違反した規則を示さない組・意味を変える組・コードや引用にかかる組を適用しません。検査役にツールの出力を渡しません。見落としは残ります |
| mod の失敗 | turn.step の hook が時間制限を超えると、ターンが失敗しました (実測) | 検査の失敗は hook 自身が受けて原文に理由を添えて流し、`.catch` の処理でも同じ扱いを返します。`.catch` の処理まで失敗すると、扱いを保証できません |
| MessageDisplay の失敗 | Desktop の WSL セッションで hook が失敗すると、原文がそのまま残ります | 防げません。満たせない範囲として扱います |

## 採らなかった方式

| 方式 | 採らなかった理由 |
|---|---|
| Claude Code を MessageDisplay hook だけで覆う | Claude Code は SDK を介する環境では回答の完成後に hook を 1 回だけ呼ぶため、部分メッセージを流す画面では原文が先に流れます (Desktop・VS Code は見込み)。会話記録と文脈も原文のままです |
| `ANTHROPIC_BASE_URL` を向ける両 CLI 共通の中継 | Desktop では第三者推論の設定とゲートウェイ用の認証情報が要り、claude.ai のログインの利用枠を使えなくなる見込みです |
| Codex の app-server と CLI の間の JSON-RPC 中継 | `--no-daemon` の対話 CLI と `codex exec` は外部の app-server を介さずに動きます |
| 両 CLI の Stop hook・通知 | 回答を表示した後に動くため、表示前の差し替えができません |
| 検査付きの非対話ラッパー (既存の `codex-verified.sh`) | 非対話の実行だけが対象で、対話 CLI・Desktop アプリ・IDE 拡張の表示を変えられません。撤去します |
| 委譲の起動を共通の処理 1 か所にまとめる | 包むと sandbox の除外と許可規則の照合から外れるためです |
| 許可規則やコマンドの文字列で `-c` の書き忘れを止める | auto モードでは許可規則に無いコマンドも分類器が実行を認めるため止まりません。コマンドの文字列の照合は書き方の違いで外れるため、エージェントの動作を縛る仕組みに使いません |
| 中継の待受を TLS にし、独自の CA を Codex に配る | CA の配布と更新、OS ごとのルート証明書の扱いが必要になります。上の前提 (一人で使い、ログイン情報をファイルに保存する機械) では同じ利用者のプロセスがログイン情報を直接読めるため、得るものがありません |
| 応答の全体を止める | 推論の間に Codex へイベントが届かず、上流が止まったときの検出が遅れます。回答の項目から止める形でも差し替えられました (実測) |

# 工程 1: 目的・設計を固める

[kata](../kata/SKILL.md) の工程 1 を進める手順です。次へ進む条件は kata の工程表にあります。

## 手順

1. 元の依頼・訂正・参照資料を読み、成果物・全対象・維持する既存保証・完了を示す観測結果を書き出します。あわせて、目的 (なぜ必要か)、やらないこと、技術的には動いても失敗とみなす条件を、依頼と実物から分かる範囲で書き出します。
2. 既存の入口・処理・設定・テスト・関連文書と Git 状態を、関連部分が今どう動き、変更がどこに及ぶかを説明できるまで調べます。repo に ADR があれば、関連する決定を [adr](../adr/SKILL.md) の読み方で確かめ、守る制約として扱います。目的の結果が今の利用経路でいつ得られるかを確かめ、新設の前に既存の変更・統合・置換で満たせるかを判断します。依頼の内容や作り方を変える制約・衝突・より安い経路が見つかったら、方式を決める前に利用者へ伝えます。
3. 利用者の操作・結果・所要時間に影響する実装なら、ここで [user-acceptance](../user-acceptance/SKILL.md) の受入担当を割り当てます。
4. 作業の規模を決めます。互いに独立した複数の仕事が含まれていれば、分けて順序を決め、一つずつこの工程を進めます。途中で規模が大きくなったら、その時点で利用者に伝えて大きい側の扱いへ移ります。

   | 規模 | 設計の記録 | builder check |
   |---|---|---|
   | 小さな変更 | 下の「設計の記録」の各項目を 1〜2 行で書きます | 行いません |
   | プロジェクト相当 (複数の部品・工程にまたがり、別に計画を立てる仕事) | 「設計の記録」の全項目を書きます | 行います |

5. 方式の候補を、既存の設定値や最初に見つけたものに限らず洗い出します。各候補が必須条件を満たすかと要件上の優劣を、一次資料・実装・実測で確かめます。成立を左右する仕組みが未確認の候補は、推奨や選択肢として示しません。目的に反する候補と既存の実物が排除する候補を落とし、残る 2〜3 案を、何を得て何を失うかが分かる具体さで比べ、1 案を理由とともに推奨します。妥当な方式が一つしかなければ、他の案が合わない理由を示します。
6. 方式を決め、下の「設計の記録」を書きます。プロジェクト相当なら、記録を書いた後に builder check を行い、その結果を記録へ反映してから次の工程へ渡します。

## 設計の記録

計画を立てる担当が、利用者に聞き直さずに計画できる内容を書きます。

- 目的と、それが必要な理由
- 目標・やらないこと・失敗とみなす条件
- 制約と維持する既存保証 (関連する ADR の決定を含みます。反する方式を選ぶなら、置き換えの ADR が要ることも書きます)
- 検討した方式、それぞれの得失、選んだ方式とその理由
- 作り方のうち利用者が決めたこと (決めた通りに書きます)
- 自分が決めたこと (利用者の合意と区別し、理由を添えます)
- 実装担当に任せること
- 成功を確かめる観測結果

設計の記録は会話か Git 管理外のメモに残し、builder check を行う設計では新しい agent が読めるよう Git 管理外のファイルに残します。正式な設計書を求められた場合だけ、既存の正式な保存先へ置きます。決定が ADR に値し、依頼か repo の方針が記録を求める場合は、設計の記録を写さず、[adr](../adr/SKILL.md) に沿って今後の読み手向けの ADR を書きます。

## builder check

プロジェクト相当の設計で、計画に必要な情報の不足を回収する確認です。

1. [review-gate](../review-gate/SKILL.md) に、確認の目的 (計画に不足する質問の回収)、入力 (設計の記録)、返す結果 (重要度順の質問と、その答えで計画が変わる理由) を渡します。会話の経緯を知らない新しい agent に、[builder-check-prompt.md](builder-check-prompt.md) の依頼文で読ませます。
2. 返った質問を次の 3 つに分けます。

   | 分類 | 扱い |
   |---|---|
   | 会話・実物で答えが出ている | 答えを記録へ書き足します |
   | 妥当な実装者が決めても作るものが変わらない | 自分で決め、自分の判断として記録へ書きます |
   | 本人しか答えられず、答えで作るものが変わる | 重要な順に一つのメッセージにまとめて尋ねます |

3. 回答を記録へ反映し、自分で決めた判断の一覧を添えて次の工程へ渡します。

## 質問と承認

- 依頼・既存資料・実物で決まることは自分で決め、質問しません。ざっくりした依頼でも、目的と既存の実物から妥当な案を選んで進めます。利用者が既に決めたことを問い直しません。
- 本人にしか決められない選択と、依頼・repo の手順が求める承認だけを、確認結果と選択肢を添えて尋ねます。その判断に依存しない調査・準備は先に進めます。
- 目的が分からず、その答えで作るものが変わる場合は、選択肢を付けない開いた質問で尋ねます。選択肢を示すと回答がその枠に寄るためです。目的が分かった後の判断は、各案の得失と推奨を具体的に示して尋ねます。
- 質問は一度に一つにし、作るものを最も大きく変えるものから尋ねます。答えで何が変わるかを添えます。直前の回答や調べた事実を踏まえ、相手が見落としていそうな帰結や場合を確かめる問いにします。工程や skill の説明で質問を代用せず、相手の用語で書きます。
- 自分で決めた既定値や方式は、理由を添えて訂正できる形で利用者に示します。示していない既定値は利用者が退けられないためです。理解した内容を返すときも、利用者が述べたことと自分が補ったことを区別します。
- 画面・配置・手順の流れなど、見た目で判断するものは、数行のテキストの図で示します。
- 動くものを見ないと判断できないときは、捨てる前提の試作を提案できます。試作の結果は設計の判断に戻し、試作の成果物を残す場合は新しい依頼としてこの工程から進めます。
- 承認は示した内容にだけ及びます。案への同意を、まだ書いていない設計の承認として扱いません。依頼・repo の手順が求めていない設計の記録への承認待ちを、新しい承認条件にしません。
- 小さく明確な依頼に、新しい設計書を一律に追加しません。

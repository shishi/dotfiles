# 工程 1: 目的・設計を固める

[kata](../kata/SKILL.md) の工程 1 を進める手順です。次へ進む条件は kata の工程表にあります。superpowers の対応 skill は手順 0 で読み込みます。superpowers が無い環境でも、以下の手順だけで工程を終えられます。上流とこの手順が食い違う場合は、この手順と共通 AGENTS.md に従います。

## 手順

0. skill 一覧に `superpowers:brainstorming` があれば、手順 1 の前に、Skill ツールがあればそれで開き、無ければ skill 一覧にある SKILL.md を読んで、現在版の本文を取得します。この工程の詳しい進め方として以下の手順に組み込み、質問・承認待ちの扱いは下の「質問と承認」に従います。一覧に無ければ、以下の手順だけで進めます。
1. 元の依頼・訂正・参照資料を読み、成果物・全対象・維持する既存保証・完了を示す観測結果を書き出します。
2. 既存の入口・処理・設定・テスト・関連文書と Git 状態を調べ、目的の結果が今の利用経路でいつ得られるかを確かめます。新設の前に、既存の変更・統合・置換で満たせるかを判断します。
3. 利用者の操作・結果・所要時間に影響する実装なら、ここで [user-acceptance](../user-acceptance/SKILL.md) の受入担当を割り当てます。
4. 方式の候補を、既存の設定値や最初に見つけたものに限らず洗い出します。各候補が必須条件を満たすかと要件上の優劣を、一次資料・実装・実測で確かめます。成立を左右する仕組みが未確認の候補は、推奨や選択肢として示しません。
5. 主要な方式と根拠を決め、何を変え、何を保ち、何で成功を確かめるかを作業メモか会話に残します。

## 質問と承認

- 依頼・既存資料・実物で決まることは自分で決め、質問しません。ざっくりした依頼でも、目的と既存の実物から妥当な案を選んで進めます。
- 本人にしか決められない選択と、依頼・repo の手順が求める承認だけを、確認結果と選択肢を添えて尋ねます。その判断に依存しない調査・準備は先に進めます。
- 上流の設計書の承認待ちを新しい承認条件にしません。正式な設計書を求められた場合だけ既存の正式な保存先へ置き、それ以外は会話か Git 管理外のメモに残します。
- 小さく明確な依頼に、新しい設計書を一律に追加しません。

# 観点レーンの障害から復旧する

[review-gate](../SKILL.md) の一部です。レーンの結果が届かないとき、失敗したとき、代替のモデル・エンジンを選ぶときに読みます。

結果が届かないレーンごとに、次を順に進める。**明示的な失敗(エラー応答・非ゼロ終了)は待たずに
次の段階へ移る。** 待つのは無応答のときだけで、待ちは**その試行の dispatch が受理された時点から
30 分**を上限とする。上限を固定するのは、待ち時間を都度の判断に任せるとゲートの厳しさが実行のたびに
変わるからである。値は、記録された成功レビューの最長 (約 7 分) に余裕を持たせて決めた。短い上限は
進んでいるレビューまで打ち切るため使わず、代わりに上限までの間、監視の確認のたびに reviewer の会話記録・
イベント出力の内容を読み (Claude Code では監視 hook が停滞を検知して起こした時点、Codex では wait_agent から戻るたび。どちらも前回の確認から 10 分、次に 20 分で、30 分の上限に重なる)、対象の読解や指摘の作成が進んでいるかを確かめる。Claude Code では進んでいる間は起こされないため、上限を過ぎて届いた結果や、上限後に起こされた時点で続いている試行は上限超過として扱う。認証・入力待ち、同じ操作の
反復、対象外の作業など、内容から進捗が無いと判断できた時点で上限を待たずに中止する。プロセスの存在や
出力の大きさの増加だけでは進捗と扱わない。中止した試行と上限を超えた試行は、以後届く結果を採用せず
次の許容候補へ進む。

1. `agent-delegation` のモデル代替規則で、この観点に許容するモデルを決めて初回を dispatch する。
   既定の外部レビューは Codex の Astra / high → Sol / high、Claude の Opus / high → Fable / high。
   狭い機械的照合だけなら Sonnet / high も許容する。各候補は原則 1 回、受理後の待ちは上の上限と内容の確認に従う。
2. 失敗原因を確認する。モデル単位の障害なら、同じエンジンの次の許容候補を新しく起動する。
   認証・通信・権限・サービス全体の枠不足なら、その原因を共有する候補を連打しない。
   一過性の障害の再試行も司令塔が判断し、adapter は独自に再試行しない。
   上限前の短い観測 timeout だけで失敗とせず、同じ実行の状態を確認する。
3. 許容候補が利用不能なら未実行の代替エンジンへ進む。外部 CLI からは司令塔側の新規観点 agent、
   native agent からは利用可能な他方の CLI を使い、モデル候補は同じ下限で選ぶ。
   各新規試行も同じ上限と内容の確認に従う。失敗済みのエンジン・モデルへ戻らず、最上位だけが起動する。
4. 許容する独立 reviewer が使えなければ、司令塔自身がその観点の本文を読み、元の要件と全対象を
   照合して指摘・根拠・検証結果を揃える。実際に確認できれば「通過(自己代替あり)」とできるが、
   独立レビューとは呼ばず、自己代替したレーンと理由を報告する。個別の依頼で独立性が必須と指定された場合は、その条件を維持する。
5. 入力・権限・能力の不足や判定不能が残れば、自己代替でも未通過とする。secrets 検査、逐語の
   タスク記述、全対象の照合を省かない。実行可能な作業を進め、不足と再開条件を具体化する。

観点と採否の基準は、モデル・エンジン・自己代替のいずれでも変えない。

gitleaks が不在なら利用可能な導入・実行経路を調べます。実行不能なら secrets 検査を省略せず未通過とし、理由と再開条件を報告します。

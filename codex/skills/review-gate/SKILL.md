# 独立レビューの実行

発動・省略条件、変更の採否、全範囲の完遂は AGENTS.md に従います。この skill は入力組成、レーン編成、エンジン選択、結果の回収と通過判定を担います。

観点の正本は `~/.claude/agents/*-reviewer.md` です。Codex では同名の `~/.codex/agents/*-reviewer.toml` が同じ本文を持ち、`tests/reviewer-agents-sync.sh` で同期を検査します。

## 対象と入力を組成する

レビュー対象を次の全体から組成します。

- `git diff HEAD` と全 untracked ファイルの本文。`git status --short --untracked-files=all` で列挙します。
- Git 外の成果物の本文。issue・外部文書は投稿・更新予定の全文と、更新時は取得した変更前の本文を含めます。
- 会話で渡す調査結果・文書、差分だけでは判定できない成果物の現在状態、要件に対応する検証結果。

Git 差分が空でも、Git 外の成果物があれば対象なしとは判定しません。分割する場合は全対象を割り当て、境界と依存関係も確認します。

各 reviewer に元の依頼・後続の訂正・参照された仕様や計画を渡します。タスク記述は既存テキストの逐語コピーとし、要約で代用しません。入力の詳細は spec-scope-review の「入力組成」に従います。既存の逐語ソースを探しても取得できない場合だけユーザーに求めます。

設計・移行手順・計測記録・関連記憶など、判断の前提となる資料の存在を確認します。差分だけでは前提を判定できない場合は該当本文を含めます。次の観点を入力に添えます。

- 障害が構造上起こり得ることと、実際の発火条件が存在することを区別して重大度を判断します。文書化された運用前提がその条件を排除するか確認します。
- 古いコメントより現在の設計・計測を検討します。ただし資料間に固定の優先順位を当てず、現在の実物と矛盾を照合してから断定します。
- 削除された処理が保証を提供していたとは限りません。削除理由と測定結果を確認し、元から壊れていた処理の復活を要求しません。
- 指摘が依頼範囲から広がったら、対象範囲をレビュー入力に明示して採否を判断します。レビュー運営用のメモを正式成果物へ追加しません。読者に必要な仕様・手順の不足だけを成果物へ反映します。

実装者の自己評価や判断の合理化は証拠に含めません。

文書を含む場合は、対象読者・用途・既存の正本と、writing-prose から適用する読者・用途・置き場・公開可否・Git 管理の**規則本文**を同梱します。リンクだけで済ませず、その内容を当該文書へ置く妥当性と言語の統一も確認させます。

## ゲートとレーンを選ぶ

| ゲート | 対象 | レーン |
|---|---|---|
| spec gate | 仕様・計画・設計の文書や issue | 0: secrets → adversarial |
| defect gate | 実装・設定・一般文書・その他の issue | 0: secrets → spec-scope と correctness を並行実行 |

設計と一般文書の両方を含む場合は、対応する対象に両方の観点を適用します。分類をユーザーへの質問や対象の除外理由にしません。外部へ送る本文は送信前にレビューします。

## エンジンを選ぶ

**Codex**: 各観点を `~/.codex/agents/` の spec-scope-reviewer / correctness-reviewer / adversarial-reviewer に対応する新規 agent で実行します。codex-review と曜日判定は使いません。secrets は gitleaks です。

**Claude Code**:

- spec-scope は Claude subagent、correctness / adversarial は平日に codex CLI、土日に Claude subagent を使います。codex CLI が利用不能なら Claude subagent へ切り替えます。
- 曜日は JST(UTC+9)で判定します。tzdata の有無に依存する `TZ=Asia/Tokyo date` は使わず、利用可能な Python 3(`python3` または `python`)の `datetime.now(timezone(timedelta(hours=9))).isoweekday()` など固定オフセットで取得します。6・7 が土日です。
- 3 観点とも codex CLI に置換できます。spec-scope への置換では、codex-review の専用入力を逐語タスク記述とともに組めることが条件です。
- 新規 agent には対応する観点 agent を Task tool で起動します。codex CLI は codex-review に観点名と focus を渡して 1 パス実行します。secrets は曜日に関係なく gitleaks です。

新規 agent には組成済み本文を渡します。大きな入力は呼び出し側が組成したファイルで渡せますが、reviewer が利用できる読取手段を指定し、全本文の読了を確認します。対象の選別を reviewer に委ねず、切り詰めや読取失敗があれば回収します。codex CLI には Git 差分・untracked の取得を指示し、Git 外の成果物本文を codex-review の全モード共通の追加入力へ含めます。

## 実行と通過判定

1. 対象が空なら「レビュー対象なし」で終了します。対象があればゲートとエンジンを決めます。
2. **secrets-scan を先行・直列で実行し、検出ゼロを確認します。** Git 外の成果物もローカルの一時ファイルに保存して per-file 検査へ含めます。Git repo がなければ成果物を直接検査します。検出内容を外部 API へ送りません。
3. 必要な観点を新規 reviewer へ dispatch し、各 1 パスの結果を回収します。文書・issue は要件だけでなく事実・参照先・手順・記述間の整合性も確認させます。反復の管理はゲートが担います。
4. 指摘の引用を照合します。欠陥の指摘は少なくとも一つの引用がレビュー対象に存在するかを確認します。未変更コードからの補助引用は実物と照合します。要件未達・判定不能の指摘は要件ソースと照合し、不一致は指摘 ID と理由を記録して棄却します。
5. AGENTS.md の判断基準で採否を決めます。採用した blocker / should を修正して直接検証し、対象を再組成して 2 に戻ります。同じ箇所で correctness と spec-scope の指摘が衝突した場合は、欠陥を解消する案を要件と照合し、spec-scope の再レビューで確認します。要件を黙って変更しません。
6. 変更ごとに secrets を再検査し、未見の差分と変更が影響する観点を独立レビューへ渡します。同じ対象・前提・証拠に対する独立レビュー結果は再利用できます。関連する修正を再確認せず、古い結果だけで通しません。反復の総回数に固定上限は設けず、AGENTS.md の収束規約に従います。
7. **必要な全レーン・全対象の結果があり、採用した blocker / should が解消し、元の全要件が証拠付きで満たされた場合だけ通過します。** spec gate は adversarial が「safe」相当であることも必要です。未レビュー・未確認・判定不能が残れば通過しません。note は元の要件未達を含まない任意改善に限り、棄却には根拠を残します。

判定不能は不足する元の要件・実物・検証結果を取得して再判定します。権限・外部障害・本人の判断、または収束規約によって止まる場合は、依存しない作業を終え、残件・試行結果・再開条件を報告します。停止を通過と扱いません。

## 観点レーンの障害から復旧する

subagent の死亡・無応答・結果の未着、codex CLI の 401・hang・timeout は、レーンごとに以下で処理します。

1. 明示的なエラーや非ゼロ終了なら待たずに原因を確認します。無応答だけの場合は、dispatch 受理から **5 分**をその試行の待ち上限にします。観測ツールのタイムアウトだけで失敗とせず、同じ handle の状態を確認します。
2. 一過性の障害など、原因の根拠がある場合は新しく dispatch します。新しい試行も受理から最大 5 分です。新情報のない同じ再試行は AGENTS.md の収束規約に従います。
3. Claude Code ではもう一方のエンジンへ切り替えて新しく dispatch し、受理から最大 5 分待ちます。観点の正本は変えません。逐語タスク記述など必要な入力を組めない置換は行いません。Codex は別エンジンへの切り替えを行わず、新規 agent のみを使います。
4. 結果がなければ未レビューのまま保持し、ゲートを未通過とします。独立レビューを自己レビューで代替しません。

codex-review 内部の原因確認付きリトライは、上の 2 とは別にその CLI 試行の一部として数えます。試行の待ち上限は内部リトライを含めて 5 分です。

この復旧手順は観点レーン限定です。gitleaks が不在なら利用可能な導入・実行経路を調べます。実行不能なら検査を省略せず、未通過として理由と再開条件を報告します。

独立した変更が多数ある場合は focus で分割できます。同じパターンの反復だけなら分割不要です。全分割と境界の結果を揃えてから通過を判定します。

## 結果を報告する

- ゲートと使用エンジン。省略・代替したレーンは理由も示します。
- 通過 / 未通過と、全対象・全要件の確認結果と根拠。
- 修正・棄却・未対応 note の指摘 ID と内容。棄却は理由を添えます。
- 未確認・判定不能・未レビューの対象、残件と再開条件。

レビューの窓口はこの skill に集約し、別 plugin の stop 時レビューは使いません。他の手順で得た独立レビューも、対象・観点・前提・証拠が一致する範囲では再利用できます。記憶 repo への commit は AGENTS.md に従い対象外です。

# 独立レビューの実行

発動・省略条件、変更の採否、全範囲の完遂は AGENTS.md に従います。この skill は入力組成、レーン編成、エンジン選択、結果の回収と通過判定を担います。

観点の正本は `~/.claude/agents/*-reviewer.md` です。Codex では同名の `~/.codex/agents/*-reviewer.toml` が同じ本文を持ち、`tests/reviewer-agents-sync.sh` で同期を検査します。

## 対象と入力を組成する

レビュー対象を次の全体から組成します。

- `git diff HEAD` と全 untracked ファイルの本文。`git status --short --untracked-files=all` で列挙します。
- Git 外の成果物の本文。issue・外部文書は投稿・更新予定の全文と、更新時は取得した変更前の本文を含めます。
- 会話で渡す調査結果・文書、差分だけでは判定できない成果物の現在状態、要件に対応する検証結果。

Git 差分が空でも、Git 外の成果物があれば対象なしとは判定しません。分割する場合は全対象を割り当て、境界と依存関係も確認します。

各 reviewer に元の依頼・後続の訂正・参照された仕様や計画を渡します。タスク記述は既存テキストの逐語コピーとし、要約で代用しません。入力の詳細は spec-scope-review の「入力組成」に従います。既存の逐語ソースを探しても取得できない場合だけユーザーに求めます。

設計・移行手順・計測記録・関連記憶など、判断の前提となる資料の存在を確認します。差分だけでは前提を判定できない場合は該当本文を含めます。次の観点を入力に添えます。

- 障害が構造上起こり得ることと、実際の発火条件が存在することを区別して重大度を判断します。文書化された運用前提がその条件を排除するか確認します。
- 古いコメントより現在の設計・計測を検討します。ただし資料間に固定の優先順位を当てず、現在の実物と矛盾を照合してから断定します。
- 削除された処理が保証を提供していたとは限りません。削除理由と測定結果を確認し、元から壊れていた処理の復活を要求しません。
- 指摘が依頼範囲から広がったら、対象範囲をレビュー入力に明示して採否を判断します。レビュー運営用のメモを正式成果物へ追加しません。読者に必要な仕様・手順の不足だけを成果物へ反映します。

操作に影響する実装では、逐語要件と補完条件を区別した受入記録と、対象版に対応する実操作・計測の証拠を全レーンへ渡します。実装前は条件・根拠・検証可能性を確認し、まだない実装の実操作を要求しません。実装者の自己評価や判断の合理化は証拠に含めません。

文書を含む場合は、対象読者・用途・既存の正本と、writing-prose から適用する読者・用途・置き場・公開可否・Git 管理の**規則本文**を同梱します。リンクだけで済ませず、その内容を当該文書へ置く妥当性と言語の統一も確認させます。

## 利用者としての受入

利用者の操作・結果・所要時間に影響する実装では、着手時に受入準備を始める。
対象は変更が影響する利用経路と、目的達成に必要な既存の保証とする。差分内だけに限定せず、
無関係な製品全体へも広げない。文書のみの変更など、操作を変えない作業に UI の時間基準や
実操作を課さない。その成果物に必要な内容・根拠・手順を確認する。

### 着手時の担当と条件

1. 司令塔は既存の worker / default agent を、実装者と別コンテキストの受入担当に割り当てる。
   会話全体を継承せず、必要な入力だけ渡す。新しい role は作らない。元の依頼・訂正の
   逐語テキストと、既存の実物・正常な類似操作を渡す。
   実装計画・実装者の成功説明を読む前に、必要な操作・結果・時間基準と根拠を導かせる。
   後で実装と照合し、実装に合わせて期待を逆算しない。
2. ユーザーの逐語要件と、受入担当が補完した条件を分けて記録する。ボタンを押せば結果を
   利用できるなど、依頼・実物・正常な類似操作に根拠のある条件を補完する。通常の補完に
   再承認は求めない。業務上の選択や新機能の追加へ広げず、根拠では決まらない本人の選択だけ
   司令塔へ返す。補完をユーザーの発言や既存仕様の事実として引用しない。
3. 司令塔は受入担当が通常の入口を操作できる安全な環境・データ・実行手段を準備する。
   reviewer の読み取り専用権限は変えない。受入担当が実操作と証拠取得を担い、reviewer は
   その記録と実物を独立に照合する。環境や権限が不足する場合は利用可能な経路を調べる。
   必要な操作を確認できない間は未完了とする。

### 時間基準と計測

- UI の押下に対する反応は 100 ms 程度、単純な操作の結果を利用できるまでは 1 秒以内を
  初期基準とする。[NNGroup の応答時間の目安](https://www.nngroup.com/articles/response-times-3-important-limits/)
  を出発点に、反応と結果を別に判定する。正常な既存操作がより速ければ、その速さを維持する。
  既存の壊れた・遅い挙動を正解にしない。連続操作や生成・大量出力などは、操作種別・
  データ量・正常な類似操作を根拠に別の時間予算を事前に定める。一律に 1 秒へ押し込めない。
- 新実装の計測前に、具体的な閾値と根拠、対象版、環境、データ量、キャッシュ状態、開始点・
  終点、試行数と検証全体の時間予算を確定する。初回利用が対象なら初回も含める。
  遅い実測だけを理由に、失敗後の閾値を緩めて合格させない。新しい根拠で補完条件を訂正する
  場合は変更理由を残し、司令塔が採否を決める。ユーザーの要求や既存の保証を変える場合は
  本人の判断へ戻す。
- 計測するのは製品内の操作開始から反応・必要な結果までとする。エージェントの思考時間や
  ツール往復は含めない。[Interaction to Next Paint(INP)](https://web.dev/articles/inp) は、
  操作から次の描画までの遅延を集約した応答性指標である。INP、スピナーの表示、API 単体の
  速度だけで結果の速度を合格にしない。タイムアウトや失敗を含む全試行の値と結果を残し、
  速い試行だけを採らない。

### 実装後の操作と記録

受入担当は通常の UI / CLI / API の入口から操作し、必要な結果と、その次の利用・永続化など
目的達成に必要な保証まで確認する。UI が対象なら handler や API の直叩きで接続確認を
代用しない。確認対象の接続や結果を mock した成功は、実接続の証拠にしない。
既存の受入テスト・CI を再利用し、重要な反復操作は結果と時間の assertion に残す。

記録は既存のタスク・テスト欄等へ、次の内容をコンパクトにまとめる。追加の仕様書は作らない。
公開する記録は writing-prose の公開境界に従い、私的なパス等を持ち込まない。

`操作 | 逐語要件 / 補完した期待と根拠 | 結果・時間基準 | 対象版・環境・計測条件 | 全試行の実測・結果 | 証拠参照`

この記録を両レビューの必須入力にする。spec-scope は補完の妥当性、要件・性能条件と実測の
一致を確認し、correctness は内部欠陥と実測結果の実装上の原因を確認する。条件や実物の
証拠不足を「指摘なし」と混ぜない。修正後は影響する操作の証拠を対象版に合わせて再取得し、
受入条件とレビュー入力を更新する。実装後の受入通過には、結果と時間の両方の証拠が必要となる。

## ゲートとレーンを選ぶ

| ゲート | 対象 | レーン |
|---|---|---|
| spec gate | 仕様・計画・設計の文書や issue | 0: secrets → 同系統と他系統の adversarial |
| defect gate | 実装・設定・一般文書・その他の issue | 0: secrets → spec-scope、同系統 correctness、他系統 correctness を並行実行 |

設計と一般文書の両方を含む場合は、対応する対象に両方の観点を適用します。分類をユーザーへの質問や対象の除外理由にしません。外部へ送る本文は送信前にレビューします。

## エンジンを選ぶ

仕様・スコープは元の依頼との照合、正しさ・設計は実装や前提への反証を担当する。
後者は同系統の新規 reviewer に加え、他方のモデルにも同じ対象を渡す。
モデルが違うだけで検出率が上がるとは扱わず、指摘は実物の引用・再現条件で採否を決める。
他レーンの結論や作成側の自己評価を先に渡さず、要件・対象・検証結果から独立に判断させる。

| 司令塔 | spec-scope | 同系統 correctness / adversarial | 他系統 correctness / adversarial |
|---|---|---|---|
| Claude Code | Claude の新規観点 agent | 司令塔と同じモデルの新規観点 agent / high | Codex CLI(`codex-review`、Astra / high) |
| Codex | Codex の新規観点 agent | 司令塔と同じモデルの新規観点 agent / high | Claude CLI(`claude-review`、Fable / high。ユーザー指定なら Opus / high) |

- 曜日による利用制限は両方とも設けない。secrets は常時 gitleaks。
- 同系統の確認も実装した会話の自己点検とは別に行う。両系統に同じ原要求・既存保証・
  対象本文・検証結果を渡し、初回は相手の結論を渡さない。観点を別々に分担しただけでは
  同じ対象の二系統レビューと数えない。対象の基準 commit と全差分・新規本文を固定する。
- CLI の存在だけで利用可能と判定せず、認証・モデル利用可否・権限・結果の受領まで確認する。
  モデル単位の利用不能は AGENTS.md の許容候補で代替する。CLI やサービス全体が利用不能なら
  同じ原因のモデルを試し続けず下の代替手順へ進む。起動後の障害も同じ手順で扱う。
- 個別の依頼が両系統・同一モデル・独立性を必須とする場合、欠けた結果を別系統や自己点検で
  満たしたことにしない。その条件の指定が無い場合は AGENTS.md の許容候補と自己代替規則を使い、
  失った独立性と実際のモデルを報告する。枠切れでも依存しない実装・検証は進めてよいが、
  必須のレビューが揃うまで通過・マージ可能とは扱わない。
- どの観点も同じ観点のままエンジンを差し替えられる。spec-scope には、どのエンジンでも
  `spec-scope-review` の入力組成に従う逐語のタスク記述が必要。入力不足をエンジン変更で解消した扱いにしない。
- 新規 agent エンジンでの実行 = 対応する観点 agent
  (spec-scope-reviewer / correctness-reviewer / adversarial-reviewer)を Claude Code では Agent tool、
  Codex では spawn agent で dispatch し、組成済みレビュー対象と focus をプロンプトで渡す(1 パス)
- 外部 CLI は最上位の司令塔が直接起動する。Codex CLI は `codex-review`、Claude CLI は
  `claude-review` に観点名・組成済み入力・focus を渡して 1 パス実行する。
  受託 reviewer はレビューを返すだけで、別 CLI へ再委譲もゲートの再起動もしない。

新規 agent には組成済み本文を渡します。大きな入力は呼び出し側が組成したファイルで渡せますが、reviewer が利用できる読取手段を指定し、全本文の読了を確認します。対象の選別を reviewer に委ねず、切り詰めや読取失敗があれば回収します。Claude CLI には Bash を与えず、全対象と必要な周辺文脈を入力に含めます。

## 実行と通過判定

1. 対象が空なら「レビュー対象なし」で終了します。対象があればゲートとエンジンを決めます。
2. **secrets-scan を先行・直列で実行し、検出ゼロを確認します。** Git 外の成果物もローカルの一時ファイルに保存して per-file 検査へ含めます。Git repo がなければ成果物を直接検査します。検出内容を外部 API へ送りません。
3. 必要な観点を新規 reviewer と他方の CLI へ dispatch し、各 1 パスの結果を回収します。文書・issue は要件だけでなく事実・参照先・手順・記述間の整合性も確認させます。反復の管理はゲートが担います。
4. 指摘の引用を照合します。欠陥の指摘は少なくとも一つの引用がレビュー対象に存在するかを確認します。未変更コードからの補助引用は実物と照合します。要件未達・判定不能の指摘は要件ソースと照合し、不一致は指摘 ID と理由を記録して棄却します。
5. AGENTS.md の判断基準で採否を決めます。採用した blocker / should を修正して直接検証し、影響する受入の証拠も再取得して、対象を再組成して 2 に戻ります。同じ箇所で correctness と spec-scope の指摘が衝突した場合は、欠陥を解消する案を要件と照合し、spec-scope の再レビューで確認します。要件を黙って変更しません。
6. 変更ごとに secrets を再検査し、未見の差分と変更が影響する観点を独立レビューへ渡します。同じ対象・前提・証拠に対する独立レビュー結果は再利用できます。関連する修正を再確認せず、古い結果だけで通しません。反復の総回数に固定上限は設けず、AGENTS.md の収束規約に従います。
7. **個別依頼の必須条件を維持し、下記の代替手順も含め必要な全レーン・全対象の結果があり、採用した blocker / should が解消し、元の全要件が証拠付きで満たされた場合だけ通過します。** spec gate は adversarial が「safe」相当であることも必要です。未レビュー・未確認・判定不能が残れば通過しません。note は元の要件未達を含まない任意改善に限り、棄却には根拠を残します。

判定不能は不足する元の要件・実物・検証結果を取得して再判定します。権限・外部障害・本人の判断、または収束規約によって止まる場合は、依存しない作業を終え、残件・試行結果・再開条件を報告します。停止を通過と扱いません。

## 実績への追記

各 adapter が返した `RUN_RECORD` を司令塔が更新する。`verification` は実検証の
`passed` / `failed` / 未確認の null、`adopted_findings` は採用した指摘数、
`rework_count` はその担当の受入・レビュー後に修正を戻した回数とする。
未確認の件数を 0 と書かない。追加の修正・再レビュー実行も各 adapter で別記録を残す。

割当前後に取得した枠は `QUOTA_OBSERVATIONS` という一時 JSON ファイルへ組成する。
形は `{"codex":{"before":null,"after":null},"claude":null}` とし、取得できた箇所だけ
helper の観測時刻・status・ウィンドウ・リセット日時を含む結果で置き換える。
Claude は正式に受領した値と観測時刻がある場合だけ同じ before / after 構造へ入れる。
観測が一方だけならもう一方は null のままにし、追加取得のためだけにモデルを呼ばない。
これを `rate_limits` に保存し、単一仕事の正確な消費へ換算しない。

次は数値と判定を確認済みの場合の追記例。変数を実結果で設定し、記録と同じ許可経路で
実行する。未確認値は JSON の null を渡す。元の数値 metadata は保持する。

```sh
RECORD_UPDATE=$(mktemp "${RUN_RECORD}.XXXXXX") || exit 1
jq -c --slurpfile quota "$QUOTA_OBSERVATIONS" --argjson verification "$VERIFICATION_JSON" --argjson adopted "$ADOPTED_FINDINGS" --argjson rework "$REWORK_COUNT" '.verification = $verification | .adopted_findings = $adopted | .rework_count = $rework | .rate_limits = $quota[0]' "$RUN_RECORD" > "$RECORD_UPDATE" || { rm -f "$RECORD_UPDATE"; exit 1; }
mv "$RECORD_UPDATE" "$RUN_RECORD"
```

## 観点レーンの障害から復旧する

結果が届かないレーンごとに、次を順に進める。**明示的な失敗(エラー応答・非ゼロ終了)は待たずに
次の段階へ移る。** 待つのは無応答のときだけで、待ちは**その試行の dispatch が受理された時点から
5 分**を上限とする。上限を置くのは、待ち時間を都度の判断に任せるとゲートの厳しさが実行のたびに
変わるからである。5 分を超えて結果がない試行は中止し、以後届く結果を採用せず次の許容候補へ進む。

1. AGENTS.md の代替規則で、この観点に許容するモデルを決めて初回を dispatch する。
   既定の外部レビューは Codex の Astra / high → Sol / high、Claude の Fable / high → Opus / high。
   狭い機械的照合だけなら Sonnet / high も許容する。各候補は原則 1 回、受理後の待ちは最大 5 分。
2. 失敗原因を確認する。モデル単位の障害なら、同じエンジンの次の許容候補を新しく起動する。
   認証・通信・権限・サービス全体の枠不足なら、その原因を共有する候補を連打しない。
   一過性の障害の再試行も司令塔が判断し、adapter は独自に再試行しない。
   上限前の短い観測 timeout だけで失敗とせず、同じ実行の状態を確認する。
3. 許容候補が利用不能なら未実行の代替エンジンへ進む。外部 CLI からは司令塔側の新規観点 agent、
   native agent からは利用可能な他方の CLI を使い、モデル候補は同じ下限で選ぶ。
   各新規試行も受理後最大 5 分。失敗済みのエンジン・モデルへ戻らず、最上位だけが起動する。
4. 許容する独立 reviewer が使えなければ、司令塔自身がその観点の本文を読み、元の要件と全対象を
   照合して指摘・根拠・検証結果を揃える。実際に確認できれば「通過(自己代替あり)」とできるが、
   独立レビューとは呼ばず、自己代替したレーンと理由を報告する。個別の依頼で独立性が必須と指定された場合は、その条件を維持する。
5. 入力・権限・能力の不足や判定不能が残れば、自己代替でも未通過とする。secrets 検査、逐語の
   タスク記述、全対象の照合を省かない。実行可能な作業を進め、不足と再開条件を具体化する。

観点と採否の基準は、モデル・エンジン・自己代替のいずれでも変えない。

gitleaks が不在なら利用可能な導入・実行経路を調べます。実行不能なら secrets 検査を省略せず未通過とし、理由と再開条件を報告します。

## 結果を報告する

- ゲートと実際のエンジン・モデル。省略・代替したレーンは試した候補と利用不能の理由、自己代替と失われた独立性も示します。
- 適用した受入条件・実操作・時間の結果と証拠参照。適用外ならその理由を示します。

- 未確認・判定不能・未レビューの対象、残件と再開条件。

レビューの窓口はこの skill に集約し、別 plugin の stop 時レビューは使いません。他の手順で得た独立レビューも、対象・観点・前提・証拠が一致する範囲では再利用できます。記憶 repo への commit は AGENTS.md に従い対象外です。

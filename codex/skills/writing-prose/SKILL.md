# 人間向け文章の執筆規約

## 概要

読者が一度で読める文を書く。共通原則と文書種別ごとの方針は全言語に適用する。言語ごとの規約は、その言語の文章に適用する。

## 併用する skill

文章を書く・直すときは、書き始める前に、この skill と一緒に次の表で該当する skill をすべて開く。一つで済ませない。草稿を書き終えたら、レビュー・commit・投稿の前に、下の「推敲」を適用する。文書・README・skill・コメント・commit の本文も対象で、言語を問わない。

| 書くもの | 併用する skill |
|---|---|
| コードコメント | code-comments |
| commit メッセージ | git-commit |
| issue | writing-issues |
| GitHub の PR・コメント・レビューの投稿 | github-writing |
| ADR | adr |
| 用語集 (GLOSSARY.md)・ドメインの ADR | domain-modeling |

## 共通原則(全言語)

- 対象読者とユーザー指定から文書の主言語を決める。見出し、定型欄、ラベル、本文を
  その言語に統一する。標準テンプレートの初期表記は、言語を混在させる理由にしない
- 読者に必要な事実と判断だけを、意味を損なわない最短の文章で書く。一文一義とし、長い文は分割する
- 相手への配慮は、求められた答えや実際の是正で示す。被害や不満を軽く扱う相づちや同意、自己評価で応答を代用しない。
- 主語と述語を近づける。二通りに読める文は書き直す
- システムの動作説明は能動態で書く(「保存されます」→「保存します」)
- 結論を先に置き、根拠と具体的な内容を因果が分かる文章でつなぐ。補足・例外は後に添える
- 未確認の挙動を既成事実として書かない。通常の利用に必要な受入条件は依頼・実物を根拠に
  補完し、明示仕様と区別して記す。事実の不明点は一次資料と実物で確認し、
  自力で確認できる内容を「不明」「要確認」と書き残して完成にしない
- 外部へ投稿する前に宛先・本文・実行環境を確認し、投稿後に同じ対象の実物と照合する。
  readback の取得通知だけでは本文の一致を確認したことにならない。コメントは親本文と区別する

## 対象読者と書いてよい情報(全言語)

- 公開文書は、不特定多数が読んでも差し支えない内容にする。特定の人だけに向けた指示や、
  限られた人しか知らない情報は書かない。著者やエージェントの思考・検討経緯、作業ログ、備忘、
  引き継ぎは掲載しない。現在の仕様・操作・制約と、理解に必要な技術的根拠を簡潔に書く。
- private 記憶には実機名・私的なパス等を保持してよい。バージョン管理から除外した
  ファイルは、公開 repo 内にあっても単なる作業メモでよく、成果物向けの構成を求めない。
- 書く前に、依頼された成果物と対象読者に必要な内容を選ぶ。個人マシン名、私的なパス・
  接続先、端末固有の状態・試行経緯は公開文書へ持ち込まない。技術説明に必要なのは
  OS・製品・バージョン・再現条件などの一般化した条件であり、実機の識別情報ではない。
  不要な私的情報は自分で除き、一件ずつ禁止指定や公開可否の確認をユーザーへ求めない。
- 保存価値、公開可否、Git 管理は別の判断。private 記憶を読めることや、同じ値が既存の
  コード・履歴にあることを公開文書への転記許可としない。内容を選んでから置き場を決める。
  スキル・テンプレート・添付資料・メタデータも同じ基準で選び、保存先の実パスと Git 管理を
  確認する。ホーム配下でも公開 repo の追跡対象へのリンクなら private の保存先として使わない。

| 用途 | 置き場と管理 |
|---|---|
| 利用者向けのごく短い概要と、解説文書へのリンク | README。機能や条件の説明・設定・手順は全てリンク先に置く |
| 依頼された設計・手順、プロジェクトの読者に必要な仕様・開発・運用文書 | 既存の正式 docs 等。共有範囲に合う内容を Git 管理する |
| エージェントの実行計画・調査メモ・引き継ぎ | 会話内、repo 内のバージョン管理から除外したファイル、または Git 管理外の一時領域 |
| ユーザーの方針・再利用する判断・個人環境の知識 | private の個人記憶。必要な実機名・パスもここに保持できる |

- 置き場を訂正するときは、元の依頼で残すべき内容を移動先へ保持し、内容と Git 管理状態を確認する。
  「設計」「計画」という名前だけで成果物を一時メモへ分類しない。
- 個人名は、特に必要がある場合または指示された場合に限り、「誰の名前をどこに
  書くか」をユーザーへ先に宣言してから書く
- 機微な情報(所属・評価・健康・私的な事情・社外秘の事実)も公開しない。
  依頼された成果物が非公開情報そのものを必要とする場合だけ、共有先と権限を確認する。
  credential は private 記憶にも保存しない。
- これらに反する記述を既存文書に見つけたら、放置せず修正または削除する。
  公開 repo では最優先で対処する

## 文書種別ごとの方針(全言語)

どの文書でも、記述ごとに「これはこの文書に書く内容か」を判定する。属さない
記述は正しい置き場へ移すか削り、追記のときも同じ判定を通す。置き場の一般則:
その文書の読者がその場で必要とする情報だけを残す。依頼範囲の将来計画は issue、
変更理由は commit log に記す場合も同じ公開基準で選別し、私的メモの移動先にしない。
正本ファイルにある値は複製せず参照にする。
仕組みの説明文書は作業メモにせず、読者が使う・判断する・直すときに必要なこと (何をするか、なぜか、
利用者の操作) だけを書く。内部の状態ファイル・退避先・環境変数・分岐ごとの挙動・検討の経緯など、
コードとコメントで分かる実装の詳細は並べない。

- **意思決定文書**: WHY(なぜ選んだか)と WHY NOT(なぜ他案を退けたか)を書く。現在形の要件と事実で書き、「本改訂では」のような経緯は書かない(経緯は commit log へ)
- **運用手順**: 回避策を足す前に構造で解消できるかを確認する。経緯を省いても動作前提・既知の制限・事実と推定の区別は残す
- **コミットメッセージ**: git-commit skill に従う(WHY 重視の body)
- **エラーメッセージ**: 原因と次の行動を 1 文ずつ

## 日本語の表記規約

| 項目 | 規約 |
|---|---|
| カタカナ語の末尾長音 | 付ける(サーバー、ユーザー、コンピューター) |
| 送り仮名 | 「行う」(「行なう」は不可) |
| 和文と半角英数の間 | 半角スペースを入れる(例: S3 バケットに 3 回) |
| 数字・英字 | 半角。全角英数は使わない |
| 文体 | 地の文は です・ます。箇条書きは体言止め可。一つの文書内で混在させない。製品・ツールの表示文も、会話の口調とは区別し、丁寧で親しみやすく書く |
| 読点 | 一文に読点が 3 つ以上付いたら文を分ける |

## 日本語の冗長表現の置換

| 冗長 | 簡潔 |
|---|---|
| することができます | できます |
| 〜という形になっています | 〜です |
| 〜を行う | 動詞にする(リトライを行う → リトライする) |
| 〜においては / 〜につきましては | 〜では |
| 〜というもの | (削除) |
| 注意が必要です | 何をすべきかを具体的に書く |

## 英語の規約

| 項目 | 規約 |
|---|---|
| 態 | 能動態で書き、動作の主体を主語にする |
| 語 | 平易な語を選ぶ (utilize → use、facilitate → help) |
| 名詞化 | 動詞に戻す (make a decision → decide、perform an update → update) |
| 冗長表現 | 削る (in order to → to、due to the fact that → because、it is possible to → can、at this point in time → now) |
| 文 | 一文一義。長い文は分割し、修飾節を重ねない |

## 推敲

説明の意味を明らかにしてから、読者に必要な内容へ短くする。言語を問わず適用する。

1. 依頼と草稿、その前後と表・図・注記を読み、読者に何を理解してほしいかを定める。概念の説明に、不要な行動指示や採用判断を加えない。
2. 長さを気にせず説明を組み立てる。何がどう動き、なぜそうなり、どの条件で成り立つのかを具体的にする。抽象語や唐突な否定で済ませない。比較や誤解の訂正が目的なら、その対比を残す。技術的な事実は一次資料と実物で確かめ、推測で補わない。
3. 仕組み・条件・例外を分け、その場所で必要な内容を選ぶ。条件は対応する文や表の項目に添え、重要な制約を注記に追いやらない。
4. 重複と回りくどい言い方を削る。主体・動作・因果・比較対象・適用条件と正式な用語は残し、必要な用語は初出で説明する。独自の略語や短い標語に置き換えない。
5. 完成文だけを続けて読み、元の長い説明なしで理解できるか確かめる。意味が欠けたら言葉を戻す。指定の長さで条件を保てなければ、必要な長さや構成を示す。
6. 編集した正本を読み直し、本文・表・図・注記の意味と既存の変更が保たれていることを確かめる。

誤字だけの修正や原文の表示・書き出しだけの依頼には適用しない。構成の大きな変更が要る場合は依頼範囲と照合し、無関係な文書・設定へ広げない。引用・逐語訳・識別子は書き換えない。相談には書き換え案を、編集の依頼には正本への反映で答え、長い下書きや検討過程は並べない。手順は [「AI の謎な説明文を直すスキル」](https://zenn.dev/microsoft/articles/explain-before-shorten) を参考にしている。

## チェック

- 草稿が揃ったら「推敲」を適用し、その後に以下の最終確認を行う。同じ本文を既に推敲済みで変更がなければ繰り返さない
- 元の依頼・訂正・参照資料を完成した文書と照合する。要求された全項目、比較の各対象と
  条件、結論を支える根拠が反映されているか確認する。自作の見出し一覧だけで充足を判定しない
- 必須の内容を「補足」「別の観点」として落とさない。構成を変えた場合も移動元の必要な
  内容が移動先にあることを確認する。不足は本文と根拠を補い、全体を再照合してから完成とする

- 日本語: 見出し、定型欄、ラベル、本文に英語だけの文章や不要な英単語が残っていないか確認する。製品名、識別子、コマンド、引用は維持する
- 日本語: 表記ゆれを grep で確認する(長音なしの「ユーザ」「サーバ」、「行なう」)。音読して詰まる文は書き直す
- 独立レビューを依頼する場合は、主言語の統一を明示的な確認項目に含める
- 英語: 英語の規約で見直し、不要語を削る(omit needless words)

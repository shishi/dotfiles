# kata の作業ワークフロー

変更作業は、以下の順序と通過条件に従って進めます。共通 AGENTS.md とこの skill を入口に、各工程は表の担当と工程 skill (kata-design・kata-workspace・kata-plan・kata-build・review-gate・kata-verify・kata-finish) で進めます。工程 skill は、この工程表と共通指示の条件の下で、工程内の詳しい実施方法を持ちます。

## 読込と担当範囲

- 工程の開始前に、その工程の skill の本文を読みます。同じ版をこのコンテキストで既に読んでいれば再利用します。一覧の説明や別 skill 内の参照だけでは本文の読了にしません。担当が取得できない場合は、確認した経路と不足を司令塔へ返し、司令塔は必要な本文を入力として渡します。作業に関係しない skill まで一括読込せず、選択を入力の固定文字列の一致で代替しません。
- 同じ成果物について、独立した計画・実装・検証・レビューを二重に起動しません。

## 開始から終了まで

司令塔は着手時に、成果物・全対象・維持条件・完了を示す観測結果を依頼と実物から定めます。設計では処理の利用回数・反復される範囲を確認し、共通 `AGENTS.md`「変更の判断」の反復利用の設計原則を適用します。既存の計画・作業メモに、現在の工程・読んだ工程 skill・次へ進める根拠を残し、切替時に確認します。skill 名を宣言しただけでは通過にしません。根拠が足りなければ、それを取得する工程へ戻ります。短い仕事では会話内の簡潔な記録で足り、専用帳票は増やしません。

次の操作へ進む前に、元の目的・必須条件と現在の成果・証拠を照合します。未達があれば、その解消か必要な判断に結び付く操作を選びます。対象版と前提が同じ確認済みの証拠は再利用し、変更で影響した範囲や未確認の要件を確かめます。必要な検証・独立レビュー・反映・後片付けまで揃ったら完了を報告して終えます。目的を満たした後の任意改善を完了条件に足さず、未達を減らさない工程を続けません。続行不能時は、共通指示の停止条件に従います。

| 工程 | 担当と使う skill | 次へ進む条件 |
|---|---|---|
| 1. 目的・設計を固める | 司令塔が [kata-design](../kata-design/SKILL.md) で進めます。利用者の操作・結果・所要時間に影響する実装では、`user-acceptance` で独立した受入担当を割り当てます。 | 何を変え、何を保ち、何で成功を確かめるかが具体的です。既存の入口・処理を調べた上で変更・統合・置換を判断しています。候補はそれぞれ必須条件を満たすかを一次資料・実装・実測で確かめ、成立を左右する仕組みが未確認の候補を推奨や選択肢として示していません。確認で満たせないと分かった候補は、反する条件と理由を添えて扱います。主要な方式と根拠を定め、kata-design の規模の判断でプロジェクト相当になった設計では、builder check で計画に必要な不足質問を回収しています。本人しか決められない選択と必要な承認は解消してから、その判断に依存する実装へ進みます。 |
| 2. 作業場所と基準版を確かめる | 司令塔が [kata-workspace](../kata-workspace/SKILL.md) で既存の分離・Git 状態・実行環境を確認します。 | タスクの作業場所と基準版を確定し、他者の変更を保全しています。必要な既存検証で開始時の状態を把握し、失敗・未確認を成功扱いしていません。 |
| 3. 実行可能な計画にする | 複数工程の仕事では司令塔が [kata-plan](../kata-plan/SKILL.md) で進めます。 | 各 task の成果物・対象ファイル・依存する入出力・検証方法と合格結果が定まり、元の全要件を覆っています。実行方式と担当を選び、実行 skill が使う実在の計画ファイルを用意し、`kata-active codex start` で実装中の記録を始めています。 |
| 4. task を実装・検証する | 選んだ担当が [kata-build](../kata-build/SKILL.md) で進めます。 | task の要求結果を実物で確認し、必要な既存検証を通しています。追加・変更するテストは赤から緑を確認し、通常の入口による独立受入の結果も該当範囲で揃っています。失敗は原因調査へ戻します。 |
| 5. 独立レビューと指摘対応 | 司令塔が [review-gate](../review-gate/SKILL.md) で編成します。指摘受領者は review-gate の「指摘の価値から採否を決める」で採否・修正を進めます。 | 全対象・必要な観点のレビュー結果があり、採用した blocker / should を修正・再検証し、影響する観点の再確認を終えています。受領手順を reviewer 自身の検査方法に割り当てません。 |
| 6. 証拠を確認して確定する | 完了を主張する担当が [kata-verify](../kata-verify/SKILL.md) で証拠を取得し、司令塔が親として共通 AGENTS.md の手順 6 で照合します。 | その照合で未確認・未達が残っていません。親がレビュー後に承認範囲内の変更だけを commit し、その後に `progress.md` の完了行を書き、実装中の記録が残っていれば `kata-active codex done` で消します。この記録は計画全体のものなので、計画の全 task を終えたときだけ消し、途中の task の確認では消しません。 |
| 7. 統合・保全・後片付け | 司令塔が [kata-finish](../kata-finish/SKILL.md) で終え方を決め、push・PR 作成もこの skill で行います。merge・pull・rebase・cherry-pick と、統合済みの branch・worktree の整理は `git-lossless-integrate` で実行します。 | 承認済みの統合・反映を実施して利用先を確認しています。未統合の成果を保全し、自分の不要な作業場所だけを片付けます。push・破壊操作の承認範囲は広げません。 |

工程は作業の規模に合わせます。工程 1 は kata-design を開いて進めます。kata-design を不要と判断した場合は、省く前に、その判断と根拠を示して利用者に省いてよいかを質問します。小さく明確な変更は、工程 3 の kata-plan を省いた直接作業にできます。作業場所 (worktree・ブランチ) も共通指示の「作業環境」に従います。その判断と根拠を示し、必要な検証・独立レビュー・完了前の証拠確認を「小さいから」で飛ばしません。既存の設計・計画がある仕事や再開時は、現在の実物との一致を確認して該当工程から再開します。

工程 4〜6 の区切り・委譲・commit の順序は kata-build に従います。

原因調査・テストは次の条件で作業へ組み込みます。

- 方式選定・実装着手・高コスト処理・再試行の前に、判断を左右する未確認事項があれば [investigation-discipline](../investigation-discipline/SKILL.md) の「次の操作を選ぶ前に確認する」を使います。既存資料・現物で得られる事実を回収してから、その結果に基づいて次の工程を選びます。
- 不具合・想定外の挙動では、修正案の前に [investigation-discipline](../investigation-discipline/SKILL.md) で観測・原因・既存保証を確認し、原因に対応する設計・計画へ戻します。調査だけの依頼を実装へ広げません。
- テストの作成・変更は [test-red-first](../test-red-first/SKILL.md) に従います。
- 工程 1 で始めた受入は、別の実装・レビューを重ねず、同じ対象・目的・前提・証拠が一致する結果を組み込みます。

## レビュー・修正と完了

- 工程 skill がレビューを求めたら、対象だけでなく、その段階の確認目的・入力・返す結果も `review-gate` へ渡します。設計の builder check なら計画に必要な不足質問、task なら要件と品質、最終なら task 間の統合を、必要なレビューの対応する観点へ割り当てます。操作に影響する実装の独立受入は着手時から準備します。指摘の採否・修正・再レビューと通過の条件は `review-gate` に従います。

## skill 作成

- skill・指示文の作成と改訂は [create-rule](../create-rule/SKILL.md) の配置・検証手順で行います。実行者の判断・手順・出力を変える改訂では、[empirical-prompt-tuning](../empirical-prompt-tuning/SKILL.md) の実行・修正・再評価を使います。利用環境に `skill-creator` などの作成支援 skill が付属する場合は、その配布版の適用範囲・形式にも従います。全変更への固定回数の実験、先行して書いた文書の機械的削除、自動 push は要求しません。

# Writing Issues

## Overview

issue は「開いた人が前提知識ゼロで、**問題 → やること → なんのため** まで読み切ってそのまま作業に入れる」自己完結文書。参照の丸投げと選択肢の羅列は、読者に判断コストと中途半端な着地を渡す。

## 本文の構成(この順で全部入れる)

1. **問題** — 冒頭 1 文で「何が起きる/起きているか」を言い切る。可能なら「現在はこう/放置・リリース後はこうなる」の対比を付ける
2. **用語定義** — 本文で使う固有名詞・プログラム名は冒頭で 1 回定義し、以後その語だけを使う(「実装」「コード」「タスク」のような曖昧語で同じものを呼び分けない)
3. **原因・仕組み** — 前提知識ゼロで追える粒度で。コード言及はファイルパス付き
4. **やること(確定形で書く)**
   - 複数案が全部必要なら「両方やる(役割分担: A が正規の動き、B が安全網)」と書く
   - 採らない案は **「やらないこと」節** に置き、不要な理由を明記する
   - 読者に選ばせてよいのは、判断材料と判断基準まで明文化できた場合だけ
5. **実行物はベタ書き** — SQL・コマンドは全文貼る。「別ドキュメントが正」なら「正は doc、本文は転記」と注記して両立させる。**貼る前に実行して確認する**(確認した環境と日付を注記)。未確認のまま貼るなら「未実行」と明示する。番号・対応表をうろ覚えで書かない(元を確認できない状況なら「要転記」と書いて作業項目に変える)。各実行項目に「期待値」と「結果別の次アクション(非 0 なら X、0 なら記録のみ、等)」を付ける
6. **完了条件** — チェックボックスで done の定義を固定する
7. **参考** — 補足だけを置く。本文の理解・実行に必須な情報を参考に逃がさない

## Quick reference(書きがちな形 → 直した形)

| 書きがちな形 | 直した形 |
|---|---|
| 「対応候補: a / b / c。方針を決める」 | 「a と b を両方やる。c はやらない(理由: …)」 |
| 「SQL は doc の Q11 参照」「再掲しない」 | SQL 全文 + 「正は doc Q11。2026-08-06 にローカル DB(MySQL 8.0.32)で実行確認済み」 |
| 「非 0 なら対処方針を検討」 | 「非 0 なら当日までに rename する。0 なら §6 に記録して終わり」 |
| 「実装」「コード」「タスク」の混在 | 冒頭で「移行タスク = ○○(何をするプログラムか)」と定義して統一 |
| 「緊急度は状況次第」 | 「計測 X がヒットしたら必須対応に格上げ」と判定条件を明文化 |

## Common mistakes

- **未実行の SQL/コマンドを貼る** — 構文エラーや環境差(例: MySQL の `[[:space:]]` は全角スペースを含まない)で動かない。実行してから貼る
- **参照だけを頼りに番号・対応表を書く** — うろ覚えの Q 番号やマッピングは捏造になる。元を開いて転記する
- **本文とコード・別文書の判定条件がズレる** — 転記元が更新されたら issue も追随する。可能なら「正はどちらか」を明記

## 適用範囲

issue 本文が対象。ただし構成 1〜7 の考え方は、PR 説明・障害報告・引き継ぎメモなど「読者が文脈ゼロで作業に入る文書」全般に流用してよい。

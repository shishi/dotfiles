# GitHub 本文の投稿と更新

投稿先と本文を確定し、送信した本文を同じ対象から取得して照合します。この skill の選択自体は投稿の承認になりません。文章の推敲は `writing-prose` に従います。

issue の本文を書く・直す・レビューするときは、投稿しない草案でも [issue の構成](references/issue.md) を読みます。

## 送信前

1. GitHub ホスト、repository、issue / PR 番号、本文かコメントかを特定します。更新では対象 ID と現在の本文も取得します。
2. コメント・返信・レビューの各本文について、内容を誰が決めたかに応じて AI 表記を判断します。
   ユーザーが主張や判断内容を決め、エージェントが意味を変えずに整文・翻訳・投稿するだけなら、AI 表記は不要です。
   エージェント自身の調査・判断で作成した内容には、AI エージェントによる投稿であることと実際のエージェント名を、読者に見える本文で明記します（例: `AI エージェント（Codex）によるコメントです。`）。
   投稿の許可や草稿への了承だけを、ユーザーが内容を決めた根拠にはしません。両者の内容が混在する場合は、エージェントが作成した部分が分かるように明記します。
   同じ本文内に既に明記されていれば重ねません。アカウント表示や HTML コメントだけでは代替しません。
3. Codex による自動一次 PR レビューと、その判定を伝えるコメントでは、冒頭を `CodexによるAI自動一次レビューです。人間による最終レビューではありません。` とし、直後に `判定：修正必要` / `判定：修正不要` / `判定：判断保留` の一つと、実装の妥当性の結論を書きます。ユーザーが別形式を明示した場合はそれを優先します。エージェントが作成した委譲指示だけでは、この必須形式を変更しません。この形式要件もレビュー入力に含め、AI 明記だけで形式を満たしたと扱いません。判定は元の要件と証拠に基づくコード修正要否とし、ゲート通過・本番実証・人間の承認とは区別します。
4. 依頼で許可された操作とアカウントを確認します。ユーザー指定の connector・API・CLI を優先し、宛先と投稿する全文を `review-gate` でレビューします。既にある承認は取り直しません。
5. 複数行本文は構造化引数で渡します。CLI を使う場合は以下の方法で本文を標準入力から渡します。本文は引用付きのヒアドキュメント (`<<'EOF'`) か PowerShell の here-string (`@'…'@`) にだけ書き、コマンドの引数や二重引用符の中へ埋め込みません。ヒアドキュメントの区切り語は本文に単独の行として現れない語にします (区切り語の行で本文が切れ、残りがコマンドとして実行されるため)。here-string の終端は `'@` に固定なので、本文に `'@` で始まる行があるときは、その行だけを単一引用の文字列 (中の `'` は `''`) にし、前後の here-string と `` (@'…'@, '…', @'…'@) -join "`n" `` のように連結してから標準入力へ流します。

## gh CLI の本文受け渡し

| 操作 | 本文の渡し方 |
|---|---|
| `gh issue/pr create`・`edit`・`comment` | 確定本文をコマンドの中のヒアドキュメント (PowerShell では here-string) で標準入力へ流し、`--body-file -` を指定します |
| REST の本文更新 | 本文を標準入力から JSON serializer に渡して `{"body": 本文}` を作り (例: `jq -Rs '{body: .}' <<'EOF'` … `EOF`。PowerShell では here-string から `ConvertTo-Json`)、パイプで `gh api --method PATCH <endpoint> --input -` に渡します |
| GraphQL | `query` と `variables` を同じ方法で JSON にし、パイプで `gh api graphql --input -` に渡します |

実行前からあるファイルを本文や payload にしません。sandbox の有無で一時ディレクトリが変わり、同じパスで別の残骸ファイルが読まれても gh は失敗しないためです。文字コードと改行が保持されることを確認します。Windows PowerShell 5.1 はネイティブコマンドへのパイプで非 ASCII 文字を失うため、本文を流す同じコマンドの先頭で `$OutputEncoding = [Text.UTF8Encoding]::new($false);` を設定します (別のコマンドで設定しても引き継がれません)。

`gh api -f body=@-` は禁止です。`-f` はリテラル文字列なので、本文を `@-` に置き換えます。`-F` は別の型変換規則です。本文を含む複雑な payload には JSON と `--input` を使います。[gh api の仕様](https://cli.github.com/manual/gh_api)

## pending review を扱う場合

- 作成・追加・修正・submit の操作前に、[pending review と suggestion](references/pending-review.md) を読みます。
  API の入力と適用行、既存の未送信レビュー、投稿範囲をそこで照合します。

各 mutation の入力は [GitHub の PR GraphQL 仕様](https://docs.github.com/en/graphql/reference/pulls) で確認します。

## 送信後

同じ本文・コメント ID から本文を再取得し、送信した原文と比較します。親 issue / PR 本文の取得をコメントの確認に代用しません。AI 明記が必要なコメント・レビューでは、その表記が読者に見えることも確認します。改行を正規化する場合は観測された輸送上の差だけに限定し、本文全体への `trim` で欠落を隠しません。

タイムアウトや 422、submit のエラーでは、再送前に現在の本文・review state を取得します。初回が成功していれば重複投稿や再 submit をしません。不一致があれば元の依頼の範囲で修正し、再取得して確認します。URL と終了コードだけでは完了にしません。

# 調査と変更の手順

全範囲の完遂と変更判断は AGENTS.md に従います。この skill は、対象の列挙から原因の切り分け、成果との照合までを扱います。

## 対象と証拠を揃える

1. 元の依頼・訂正・参照資料から対象と要件を列挙します。ディレクトリ、設定の参照先、呼び出し元、配備先と照合し、列挙が全体を覆う根拠を確認します。検索の除外、非表示項目、ページ分割、権限による欠落を調べます。
2. 各対象の内容を読み、要件・成果・直接の確認結果・残件を対応づけます。索引や抜粋だけを全文確認と数えず、切り詰め・取得失敗による未読部分を回収します。対応は会話や既存の計画に置き、専用の管理機構は増やしません。
3. 抽出・変換では、入力のうち採用しなかった部分を補集合として確認します。除外した部分が採用部分の前提になっていないかを調べ、残す内容・移す内容・不要な内容を区別します。
4. 比較前に両側の取得成功と対象件数を確認します。正常な空集合、取得失敗、差分なしを別々に扱います。例外で取得できなかった対象を成功件数へ混ぜません。
5. 参照先や利用経路に達成を左右する前提があれば辿ります。対象外にするものは元の依頼との関係から判断します。
6. 元の依頼から成果への対応と、実物から要件への対応を両方向で照合します。漏れと不要な追加を確認し、不足があれば共通原因のある箇所と変更の影響先まで戻ります。対象と前提が変わっていない証拠は再利用できます。

## 原因と制約を切り分ける

- 症状、観測条件、原因仮説、その仮説を区別できる観測を揃えます。同じ問題を解く先行実装、公式資料の保証範囲、既知の issue を確認し、環境固有という推測だけで調査範囲を狭めません。
- 実装上の制約は、要件や外部仕様による制約と分けます。導入時の履歴・意思決定を確認し、現在も必要な理由を調べます。実装都合なら外す案も比較します。

```bash
git log --oneline -S '<制約の文字列>' -- <path>
git show -s --format=%B <sha>
```

- 回避策を適用する前に、観測した原因、対策が変える状態、維持する保証、影響範囲を対応づけます。因果が説明できない場合は仮説を区別する観測へ戻ります。
- ツールの互換性は OS 名から推定せず、実際のコマンドと必要な機能で確認します。プローブは、確認したい操作が実際に起きたことを検証します。何もしない成功を権限や到達性の証拠にしません。

## 観測経路と介入を検証する

- 消失・件数減少などの異常は別の取得経路でも測ります。対象の欠陥と判定する前に、同じ入力で起動元・権限・接続などの条件を一つ変えた対比を取ります。対比できない条件は原因未確定として保持し、利用可能な別の観測で切り分けます。
- 監視や停止処理を加える前に、誤判定時に壊れる状態と復旧方法を確認します。進捗指標が実作業と同じ層を見ているか、親プロセスが子の処理を待っているだけではないかを確かめます。
- 観測が消費する CPU・I/O・接続数と観測頻度も測定条件に含めます。観測自身がログの順序や最新値を変える場合は、本来の処理の記録を識別します。
- 設定へ反映する前に、観測が初回・通常運用・復旧などのどの局面に属するかを確認します。一局面の回避策を、前提の異なる局面の既定値へ一般化しません。
- 引き継ぎや履歴の状態値は観測時点のものとして扱います。次の操作を決める状態だけを現在の実物から再取得し、キャッシュされた値と現在値を区別します。

## 保持・削除と影響先を確かめる

1. 残すものが提供する機能や保証を実測し、削除する場合に失うものと比較します。隠す・skip する案では、処理後に残る状態と、その状態を後続処理がどう扱うかを確かめます。
2. 常時失敗する検証や警告は原因を調べます。検証を廃止する場合は保証が不要になった根拠を確認し、必要な保証を消して成功にしません。
3. 前提を変更したら、コード・テスト・文書・運用手順の参照箇所と利用先を列挙し、新しい前提で成立するか確認します。
4. その設計を根拠にした過去の判断も列挙し、根拠が残るか再評価します。ファイル内の語句検索だけで判断の依存関係まで確認したことにしません。
5. 元の要件・全対象・直接の証拠を再照合します。再試行と停止は AGENTS.md の収束規約に従い、未達を残した停止を完了と扱いません。

# 調査と変更の手順

全範囲の完遂と変更判断は AGENTS.md に従います。この skill は、失敗の因果の特定から修正・直接検証・反映までを扱います。

エージェントの shell / sandbox によるファイル・認証・通信の食い違いは、
[実行環境の観測](references/agent-runtime.md) を読みます。
Windows の文字コード・shell 間の入力や実レジストリは `windows-script-diagnostics` が担当します。

## 原因から修正を収束させる

網羅・列挙による穴埋めをしません。観測した失敗がどの状態の欠落・取り違えによって生じたかを説明し、要求された結果と守るべき性質を、その状態を管理する既存の責務へ結び付けます。判別に必要な情報を失っているなら、症状の文字列から推測する条件を足す前に、情報を保持する責務を直します。

修正前に原因仮説を区別する最小の観測を行い、元の失敗を再現します。同じ原因が別の操作で再発したら、前の修正が成立すると考えた前提を見直します。理解が変わらないまま条件・テスト・レビューを積み増しません。変更の必要性と、元の失敗を防ぎながら既存保証を保つ理由が説明できてから編集します。

検証を始める前に対象版を固定します。検証中のコード編集・ビルド切替は行わず、修正が必要になったら検証を区切り、修正後に影響する証拠だけを取り直します。前提も対象も変わらない結果は再利用します。

レビューには判定に必要な呼出元・状態の出所・既存保証・直接検証を一緒に渡します。入力の分割で文脈を欠かせ、推測の指摘と追加調査を往復させません。指摘は実物で因果と到達性を判断し、観測済みの問題か要件に結び付かないものを新しい作業へ変えません。

依頼の要件が実物と直接検証で満たされ、具体的な未確認リスクがなければ調査と検査を終え、必要な反映と後片付けへ進みます。管理用の一覧や追加文書を成果の代わりにせず、固定回数で未達を打ち切ることもしません。

## 原因と制約を切り分ける

- ローカルの調査・修正・ユーザーへの操作依頼より先に、既知の issue(対象の Issue トラッカー。解決済みを含む)、公式資料の保証範囲、同じ問題を解く先行実装を確認します。既知なら原因・回避策・修正状況から答えます。そのうえで症状、観測条件、原因仮説、その仮説を区別できる観測を揃え、環境固有という推測だけで調査範囲を狭めません。
- 実装上の制約は、要件や外部仕様による制約と分けます。導入時の履歴・意思決定を確認し、現在も必要な理由を調べます。実装都合なら外す案も比較します。

```bash
git log --oneline -S '<制約の文字列>' -- <path>
git show -s --format=%B <sha>
```

- 回避策を適用する前に、観測した原因、対策が変える状態、維持する保証、影響範囲を対応づけます。因果が説明できない場合は仮説を区別する観測へ戻ります。
- ツールの互換性は OS 名から推定せず、実際のコマンドと必要な機能で確認します。プローブは、確認したい操作が実際に起きたことを検証します。何もしない成功を権限や到達性の証拠にしません。

## 観測経路と介入を検証する

- 消失・件数減少などの異常は別の取得経路でも測ります。対象の欠陥と判定する前に、同じ入力で起動元・権限・接続などの条件を一つ変えた対比を取ります。対比できない条件は原因未確定として保持し、利用可能な別の観測で切り分けます。
- 監視や停止処理を加える前に、誤判定時に壊れる状態と復旧方法を確認します。進捗指標が実作業と同じ層を見ているか、親プロセスが子の処理を待っているだけではないかを確かめます。
- 観測が消費する CPU・I/O・接続数と観測頻度も測定条件に含めます。観測自身がログの順序や最新値を変える場合は、本来の処理の記録を識別します。
- 設定へ反映する前に、観測が初回・通常運用・復旧などのどの局面に属するかを確認します。一局面の回避策を、前提の異なる局面の既定値へ一般化しません。
- 引き継ぎや履歴の状態値は観測時点のものとして扱います。次の操作を決める状態だけを現在の実物から再取得し、キャッシュされた値と現在値を区別します。

## 保持・削除と影響先を確かめる

1. 残すものが提供する機能や保証を実測し、削除する場合に失うものと比較します。隠す・skip する案では、処理後に残る状態と、その状態を後続処理がどう扱うかを確かめます。
2. 常時失敗する検証や警告は原因を調べます。検証を廃止する場合は保証が不要になった根拠を確認し、必要な保証を消して成功にしません。
3. 前提を変更したら、その前提を使う責務と利用経路へ戻り、新しい前提で成立するか確認します。
4. その設計を根拠にした判断は、根拠が残るか再評価します。ファイル内の語句検索だけで判断の依存関係まで確認したことにしません。
5. 元の要件・全対象・直接の証拠を再照合します。再試行と停止は AGENTS.md「変更の判断」の再試行規則に従い、未達を残した停止を完了と扱いません。

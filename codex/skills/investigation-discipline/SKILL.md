# 原因調査の追加条件

不具合・想定外の挙動を調べるときは、利用中の配布版の `superpowers:systematic-debugging` を読み、根因調査から修正・検証までの主手順に使います。同じ版の既読本文は再読しません。配布版が未取得・読取不能なら、確認済みとせず、取得状況と未確認の範囲を司令塔へ返します。

この skill は上流の調査手順に、対象・証拠・既存保証を扱う条件を加えます。全範囲の完遂と変更判断は共通 `AGENTS.md` に従います。

AdGuard の通信ログ、DNS フィルタやモバイル広告の残存を調べる場合は、[ad-filter-investigation](../ad-filter-investigation/SKILL.md) を併用します。

エージェントの shell / sandbox によるファイル・認証・通信の食い違いは、[実行環境の観測](references/agent-runtime.md) を読みます。Windows の文字コード・shell 間の入力や実レジストリは `windows-script-diagnostics` が担当します。

## 対象と証拠を照合する

- 全件調査や抽出・比較では、元の依頼・訂正・参照資料から対象と要件を特定します。ディレクトリ、設定の参照先、呼び出し元、配備先と照合し、全体を覆う根拠を確認します。検索の除外、非表示項目、ページ分割、権限による欠落も調べます。
- 各対象の内容と、要件・成果・直接の確認結果・残件を対応づけます。索引や抜粋を全文確認と数えず、切り詰め・取得失敗による未読部分を回収します。対応は会話や既存の計画に置き、専用の管理機構は増やしません。
- 抽出・変換では、入力のうち採用しなかった部分も確認します。除外部分が採用部分の前提になっていないかを調べ、残す内容・移す内容・不要な内容を区別します。
- 比較前に両側の取得成功と対象件数を確認します。正常な空集合、取得失敗、差分なしを区別し、取得できなかった対象を成功件数へ混ぜません。
- 参照先や利用経路に達成を左右する前提があれば辿ります。対象外にするものは元の依頼との関係から判断します。

## 原因と制約を切り分ける

- ローカルの調査・修正・ユーザーへの操作依頼より先に、既知の issue、公式資料の保証範囲、同じ問題を解く先行実装を確認します。Issue トラッカーは解決済みも含めます。既知なら原因・回避策・修正状況を踏まえ、環境固有という推測だけで調査範囲を狭めません。
- 実装上の制約は、要件や外部仕様による制約と分けます。導入時の履歴・意思決定から現在も必要な理由を調べ、実装都合なら外す案も比較します。
- 原因が状態の欠落・取り違えなら、要求された結果と守る性質を、その状態を管理する既存の責務へ結び付けます。判別情報を失っている場合は、症状の文字列を推測する条件を足す前に、情報を保持する責務を直します。
- 同じ原因が別の操作で再発したら、前の修正が成立すると考えた前提を見直します。理解が変わらないまま条件・テスト・レビューを積み増しません。
- 回避策を適用する前に、観測した原因、対策が変える状態、維持する保証、影響範囲を対応づけます。因果が説明できない場合は仮説を区別する観測へ戻ります。
- ツールの互換性は OS 名から推定せず、実際のコマンドと必要な機能で確認します。確認したい操作が起きたことを検証し、何もしない成功を権限や到達性の証拠にしません。

## 観測経路と介入を検証する

- 消失・件数減少などの異常は別の取得経路でも測ります。対象の欠陥と判定する前に、同じ入力で起動元・権限・接続などの条件を一つ変えた対比を取ります。対比できない条件は原因未確定として保持し、別の観測で切り分けます。
- 監視や停止処理を加える前に、誤判定時に壊れる状態と復旧方法を確認します。進捗指標が実作業と同じ層を見ているか、親プロセスが子の処理を待っているだけではないかを確かめます。
- 観測が消費する CPU・I/O・接続数と観測頻度も測定条件に含めます。観測自身がログの順序や最新値を変える場合は、本来の処理の記録を識別します。
- 設定へ反映する前に、観測が初回・通常運用・復旧などのどの局面に属するかを確認します。一局面の回避策を、前提の異なる局面の既定値へ一般化しません。
- 引き継ぎや履歴の状態値は観測時点のものとして扱います。次の操作を決める状態だけを現在の実物から再取得し、キャッシュされた値と区別します。

## 保持・削除と影響先を確かめる

- 残すものが提供する機能や保証を実測し、削除する場合に失うものと比較します。隠す・skip する案では、処理後に残る状態と、後続処理がその状態をどう扱うかを確かめます。
- 常時失敗する検証や警告は原因を調べます。廃止する場合は保証が不要になった根拠を確認し、必要な保証を消して成功にしません。
- 前提を変更したら、その前提を使う責務と利用経路を確認します。コード・テスト・文書・運用手順と、その設計を根拠にした過去の判断も新しい前提で再評価します。語句検索だけで判断の依存関係まで確認したことにしません。

## 検証と収束の条件

- 検証前に対象版を固定します。検証中にコード編集・ビルド切替が必要になったら、その検証を区切ります。修正後は影響する証拠だけを再取得し、対象と前提が変わらない結果は再利用します。
- 上流の失敗テスト作成は、共通 `AGENTS.md` で必要と判断したテストへ適用し、`test-red-first` の追加条件に従います。元の失敗の再現と、修正結果を実際の利用経路で確認する作業は省略しません。
- レビューには判定に必要な呼び出し元・状態の出所・既存保証・直接検証を渡します。文脈を欠いた分割で推測と追加調査を往復させず、指摘の因果と到達性を実物で判断します。
- 上流の「3 回の修正で人間へ相談」は固定の打切り条件にしません。再試行・当該経路の停止・別経路の継続は、共通 `AGENTS.md`「変更の判断」の再試行規則に従います。
- 元の依頼から成果への対応と、実物から要件への対応を両方向で照合します。漏れがあれば共通原因と影響先へ戻ります。全要件が実物と直接検証で満たされ、具体的な未確認リスクがなければ調査と検査を終え、必要な反映と後片付けへ進みます。

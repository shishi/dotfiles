# 工程 2: 作業場所と基準版を確かめる

[kata](../kata/SKILL.md) の工程 2 を進める手順です。次へ進む条件は kata の工程表にあります。worktree を作るかどうかは共通指示と repo の指示で決まるため、利用者に毎回は尋ねません。

## 手順

1. 今いる場所を、見た目で判断せずコマンドで確かめます。`git rev-parse --git-dir` と `--git-common-dir` は相対パスで返ることがあるため、それぞれ `cd` して `pwd -P` で物理パスにそろえてから比べます。違えば既に worktree の中なので、新しく作らず手順 4 へ進みます。ただし `git rev-parse --show-superproject-working-tree` が値を返す submodule の中なら、通常の checkout として扱います。既に worktree の中で detached HEAD の場合は、外部の仕組みが管理する場所として扱い、工程 7 でブランチを作る必要があることを作業メモに残します。既存のタスク用 worktree・ブランチがあれば再利用し、新しく作りません。
2. 作業場所を決めます。共通指示の「作業環境」に従い、コードを変えるなら worktree を基本にし、アプリケーションの性質で合わなければブランチにします。repo の指示が master 1 本など別の運用を定めていれば、それに従います。CLI に worktree を作る専用ツールがあれば、`git worktree add` より先にそれを使います。専用ツールは置き場所・ブランチ・片付けを管理するため、迂回すると CLI が把握も片付けもできない worktree が残ります。専用ツールが無いときだけ `git worktree add <パス> -b <ブランチ>` で作ります。置き場所は、指示があればそれに従います。無ければ repo に既にある `.worktrees/`、次に `worktrees/` を使い、どちらも無ければ `.worktrees/` を作ります。
3. worktree を repo の中に置く場合は、その場所が `git check-ignore -q <場所>` で無視されていることを、作る前に確かめます。無視されていなければ worktree の中身がそのまま commit に混ざるため、無視の設定を先に整えます。
4. 基準版を記録します。分岐元のブランチと commit を確かめ、計画や作業メモに残します。分岐元が会話・計画・upstream から決まらなければ、推測で統合先を決めず確かめます。
5. 他者の未コミット変更を確かめ、自分の作業と混ぜずに残します。
6. 実行環境を用意します。依存の導入は、package.json などのファイルの有無から package manager を起動するのでなく、プロジェクトが用意する手順 (Nix → Docker → その他) に従います。flake.nix のあるプロジェクトは `nix-environment` に従い、読解・編集だけなら環境を起動しません。
7. 変更と直接関係する既存の検証を、作業を始める前に一度実行し、開始時の成功・失敗を記録します。開始時の状態が分からないと、後の失敗が自分の変更によるものか判別できません。開始前から失敗しているものは、自分の変更による失敗と区別できるよう名前で残し、成功扱いにしません。
8. 作業場所のパス・ブランチ・基準版・開始時の検証結果を報告します。自分で作った worktree・ブランチは、作成手段 (専用ツールか `git worktree add` か) とともに作業メモに記録します。工程 7 の片付けは、この記録で自分が作ったと示せる場所だけが対象です。

## 注意

- sandbox などで worktree を作れない場合は、作れなかった理由と代わりに使う場所を示し、その場所で手順 6・7 を進めます。

# 実行結果に基づく指示文の改善

対象指示を実行し、要求と結果の差を根拠に指示文を修正して、改善と既存保証を再評価します。skill・共通指示・タスク用プロンプトなどに単独で使えます。ルールの配置判断や通常の作業実行を、指示文改善の実験へ置き換えません。

1. **評価対象と合否を先に決める。** 依頼と失敗の観測から、成果物・必須条件・維持する正常動作を定めます。既知の失敗条件を現行版と変更候補で比較し、別の現実的な条件でも維持を確認します。対象の条件を覆うシナリオを選び、採点しやすさのために要件を減らしません。既存指示のない新規作成では、指示を外した条件 (下の「指示を外した条件を作る」) や既存の代替経路を比較の基準にします。比較対象を確保できなければ機能の確認と改善の因果判定を分けます。description の用途と本文が一致するかは実行前に確認します。
2. **比較条件と予算を固定する。** 指示の版、入力、モデル・推論量、共通指示、ツール・権限、環境を記録します。取得できる範囲で初回・再利用時の状態も揃えます。比較に必要な試行と時間・使用枠の予算を開始前に決め、揃わない条件は差として残します。モデルを起動する前に、依頼された判断主体・入力・利用経路と、試験コードが実際に送る内容・呼び出す処理を照合します。食い違いがあれば修正してから試行します。変更候補と違う条件の成功を、指示変更の改善とは断定しません。
3. **通常入力と内部採点を分ける。** 各試行は作者や前回試行の会話履歴を持たない新規コンテキストで行います。対象が起動時に読み込まれる指示 (skill・共通指示) なら、子エージェントは親の開始時点の指示と一覧を使うので、比べる条件ごとに新しいプロセスを起動します。作業場所の状態・生成物・記録も前提として揃えます。前試行の成果物を持ち込む場合は通常利用に必要なものか確認し、残る状態や条件差を記録します。実行者には対象指示と、通常の利用者が渡す依頼・必要な資料を渡します。利用者の要求は隠さず、特定 skill の呼出など評価者だけが使う検査項目は渡しません。追加の質問や自己申告を求める診断試行は、通常入力による試行と区別します。作者が対象指示を説明し直して成功させた結果を、元の指示だけの成功と扱いません。判断が評価対象なら、判断を担う実行者や仕組みに、選択が分かれる通常の入力を同じ入口から渡します。入力や試験コードで選択を指定した実行は、その経路の診断に使います。
4. **成果と観測で判定する。** 出力・実物の差分・ツール記録・終了結果などを、事前の必須条件と照合します。採点は下の「版を伏せて判定する」で行います。事前に決めた採点項目はすべて合否に残し、項目ごとに「両方成功・両方失敗・比べる側だけ成功・基準側だけ成功」を記録します。差がばらつきの範囲に収まるなら、効果は確かめられないとします。実行者の不明瞭点、補完した判断、原因説明は改善の手掛かりであり、実行や原因の観測事実と区別します。呼出回数・時間・再試行などは、取得した記録と自己申告を分け、取れない値は未取得にします。判断を評価した場合は、誰が何を選び、その後どの処理が走ったかを記録から確かめます。依頼された判断の経路で得た結果だけを、その方式の採否や負担の比較に使います。達成項目の割合や速さで、必須条件の未達を相殺しません。
5. **対象の指示文を修正する。** 原因を指示文に帰属する前に、対象本文と実行経路を照合します。本文が未取得なら指示の不足は未判定とし、権限・環境による実行不能と指示の欠陥を分けます。失敗した箇所と原因仮説、変更する指示、確認する要求を対応させます。同じ目的の既存記述があるなら、適用されなかった経路を先に調べます。関連する修正を一つの仮説にまとめます。修正まで依頼されている場合は、承認された対象ファイルやプロンプト本文へ反映し、提案だけで終了しません。
6. **修正の確認と合格を分ける。** 手順 3 と同じ条件の新規コンテキストで影響する条件を再評価し、改善に使っていない条件でも要求を確認します。失敗を見て調整に使った条件は、以後は未使用条件に数えません。ばらつきが判断を妨げる場合は、予算内で比較を追加します。下の記録を揃え、必須条件と維持条件が満たされた証拠を合格の根拠にします。未取得の条件が判定へ影響する場合は、その範囲を未判定とします。改善の頭打ちや予算終了は評価を止める判断であり、未達を合格・作業完了にしません。未達を記録し、承認範囲内の再計画・予算の見直し・別経路の利用は司令塔が判断します。追加の承認が必要な操作だけ本人へ確認し、残件への対応と停止は共通指示に従います。

## 指示を外した条件を作る

タスク用プロンプトは、その指示を渡さない通常の依頼を、外した条件にします。共通指示の規則は起動時に読み込まれるので、依頼から省いても両方の条件に届きます。試行専用の読み込み元 (隔離した設定ディレクトリに置いた共通指示の写しなど) から対象の規則だけを外し、実行者に届いた共通指示を両方の条件の記録で照合します。対象が skill で、skill なしの条件と比べるときは、そのプロセスだけで skill を外し、本文を読めない状態にします。一覧から外すだけでは足りません。記憶や共通指示が skill の名前を挙げていると、エージェントは本文のファイルを自分で探して読みにいきます。同じ本文の写しが別の場所 (`claude/skills/` と `codex/skills/` など) にもあります。skill のディレクトリを動かしたり名前を変えたりしません。同じ checkout を使うほかのセッションからも skill が消えるためです。

- Claude Code: `claude -p '<依頼>' --settings '{"skillOverrides":{"<名前>":"off"},"permissions":{"deny":["Read(//**/skills/<名前>/**)"]}}'`。`skillOverrides` が一覧から外し、`deny` が手元のどの写しの本文も `Read` で読めなくします。シェルの `cat` などはこの拒否を通らないので、依頼がシェルを要しないなら両方の条件で `--disallowedTools Bash` を付けます。依頼がシェルを要するなら両方で Bash を使えるままにして、流した後に確かめます。
- Codex: `codex exec --skip-git-repo-check -c 'default_permissions="cmp"' -c 'permissions.cmp.filesystem={"/"="read","<写しのディレクトリ>"="deny",...}' -c 'skills.config=[{name="<名前>",enabled=false}]' '<依頼>' < /dev/null`。`permissions` の profile が、手元のすべての写しのディレクトリの読み取りを拒否します (Codex のベータの機能)。skill ありの側も、拒否の行を除いた同じ profile で流します。依頼がファイルの書き換えを要するなら、両方の profile で作業ディレクトリ (と書き込みが要るパス) を `"write"` にします。`--sandbox` を渡すと profile が使われないので付けません。`--skip-git-repo-check` は、Git の repo の外 (一時ディレクトリなど) で流すときに要ります。`codex exec` は、パイプなど閉じない標準入力を引き継ぐと、引数のプロンプトがあっても入力の終わりを待ち続けるので、`< /dev/null` を付けます。

どちらも毎回、外した skill がそのプロセスの一覧に載っていないことと、「なし」側の記録に本文が届いていないことを、試行の記録で確かめます。記録の読み方 (一覧の残り方、本文が届いたことの見分け方) は [assessing-skills の references/usage.md](../assessing-skills/references/usage.md) の手順 3 と手順 4 の 1 にあります。本文が届いた試行は比較から外し、その件数を報告に添えます。共通指示がその skill を開くよう求めていると、「なし」側のエージェントは本文を読めないことを理由に作業を止めて聞き返すことがあります。止まった試行も比較から外し、件数を添えます。

## 版を伏せて判定する

解釈が要る採点項目は、試行の実行者とも指示の作者とも別の、新規コンテキストの判定役が採点します。判定役は子エージェントでもかまいません。ただし、起動時に読み込まれる指示 (skill・共通指示) を比べる試験で、採点項目がその指示の解釈を要する場合は別です。判定役が読み込んだ版が採点の基準になり、版の見分けにも使えてしまうためです。この場合は、対象の規則を外した読み込み元 (上の「指示を外した条件を作る」) から、新しいプロセスで判定役を起動します。外した規則が判定役に届いていないことも、試行と同じ方法で確かめます。終了コードや差分のように機械的に決まる項目は、記録から直接判定します。判定役には、事前に決めた採点項目と、各試行の出力・差分・記録の抜粋を渡します。どの試行がどの版 (旧版・新版、指示あり・なし) かは、A・B などの記号に置き換え、並び順も混ぜて伏せます。版や skill の名前、条件を示すパスや文言が抜粋に残る場合は除きます。除くと採点項目を判定できない場合は除かず、その項目は版が分かる状態で判定したと記録します。判定役は項目ごとに合否と、根拠にした抜粋の引用を返します。記号と版の対応は、すべての判定がそろってから開きます。

## 記録

記録は既存の Git 管理外の作業記録を使い、以下の各項目に値か「未取得」を必ず残します。

- 対象指示の版と、通常入力・期待する成果
- 実モデル・推論量・共通指示、ツール・権限、環境・残留状態と条件差
- 事前の試行・時間・使用枠の予算、取得した回数・時間・使用量
- 必須条件と維持条件ごとの合否、観測根拠の場所、比較から外した試行の件数と理由
- 採用した修正、未確認、比較から言えること・言えないこと

文書の整合確認、進行判断の回答、実際の操作による評価は区別して報告します。評価用の成功を、未確認の通常利用や別モデルへ広げません。

方法の参考は [empirical-prompt-tuning](https://github.com/mizchi/skills/blob/main/empirical-prompt-tuning/SKILL-ja.md) です。通常入力の維持、観測に基づく判定、合格と評価停止の区別は共通指示に合わせています。

## 他の作業から使う場合

呼出元の対象・成果物・承認範囲・正常動作の保証を引き継ぎます。`create-rule` から使う場合も一つの改善ループとし、別の実験を二重に起動しません。変更が実行者の判断・行動・生成物を変えるなら、影響する条件を実行して確認します。意味や挙動を変えない表記整理は、既存の証拠と必要な通常経路の確認を使います。全変更に一定回数の実験を課しません。skill が役に立っているか (skill なしと比べて残す・外すを決める) は [assessing-skills](../assessing-skills/SKILL.md) が判定し、この skill の手順で試行を流します。

指示文の修正・再評価を終えたら、呼出元の最終確認・独立レビュー・保存の手順へ戻ります。独立レビューや commit・投稿の許可をこの skill で省略・拡張しません。

# TDD の追加条件

テストを書くと決めたら、利用中の配布版の `superpowers:test-driven-development` を読み、RED → GREEN → REFACTOR の主手順に使います。同じ版の既読本文は再読しません。配布版が未取得・読取不能なら、確認済みとせず、取得状況と未確認の範囲を司令塔へ返します。

この skill は上流の TDD 手順に、テストの適用範囲と偽陽性を防ぐ条件を加えます。

## 適用範囲と既存作業の保全

- テストを書く必要性と件数は、先に共通 `AGENTS.md` の「要求された挙動を証明する最小限」で決めます。既存テストを優先し、上流の全変更・全関数へのテスト要求を、新規テストの一律追加に使いません。
- 既存の振る舞いを固定する characterization test は test-after を認めます。新しい振る舞いの証明に、この例外を使いません。
- 実装を先に書いた場合も、既存コードや未コミット変更を機械的に削除しません。作業内容を保全し、編集前の複製か `git show <対象版>:<path>` で変更前の内容を別の一時領域へ用意します。他者変更と混在する作業 tree をその内容で上書きしません。新しい振る舞いが存在しない版で RED を確認し、退避した実装へテストの期待を合わせません。
- 上流の例外ごとの人間への確認は、共通 `AGENTS.md` と現在の承認範囲に従って判断します。承認済みの判断を再承認へ戻さず、必要なテストと実際の操作による確認を行います。
- 検証範囲は共通 `AGENTS.md` と repo の必須チェックで決めます。変更と直接関係する既存テストを実行し、新しい変更・失敗・未確認リスクがあれば広げます。上流の全 suite 一律実行よりこの範囲を優先し、repo が必須とする全 suite は実行します。

## 静的テストとミューテーション確認

- 観測できる振る舞いは、振る舞いテストで確認します。ソース文字列の照合は、その足場を用意する負担が高いと確認した場合に使います。
- 静的テストは RED → GREEN だけでは妥当性を証明できません。機能追加前は文字列がないため、無関係な正規表現でも赤から緑になります。正規表現が一致したまま約束した動作を壊せる条件を具体化し、そこからミューテーションを選びます。
- 守りたいのが呼び出し側の複数箇所なら、その箇所の欠落を確かめます。定義本体の 1 箇所だけを消して落ちても、呼び出し側を守った証拠にはなりません。文字列の存在だけでは、解放 API をファイル削除後に呼ぶような順序の不具合を確認できません。
- 静的な照合対象は、行番号で範囲を切り出し、期待件数も固定します。範囲を絞らない `(?s)` と遅延量指定子は、ブロックを飛び越えて後方へ一致するため避けます。
- ミューテーション確認は RED の代わりにしません。自分が選んだ壊し方への反応しか確認できず、実装後の緑が要求された振る舞いを証明しているかは区別できないためです。
- ミューテーション確認で退避した作業を復元するときは `git checkout` を使いません。未コミットの作業を失わないよう、先に承認範囲内で commit するか、対象ファイルを別名で退避してそこから戻します。

## LLM の判定を含む部品

- 入出力の組成・パース・分岐など、決定的な配管をスタブでテストします。非決定的で正解が主観に依存する判定品質を assertion で固定しません。
- 判定品質は実運用の誤判定を観測してからプロンプトを直します。テストの成功を求めて、停止条件のないプロンプト調整を続けません。
- 対象の hook・gate を配線したまま、その hook 自身が block する種類の作業でテストを開発しません。開発側の停止や検証を、被験体が妨げない状態で行います。

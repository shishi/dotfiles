# 赤から始めるテスト

テストは、本番コードより先に書いて失敗を見届けます。失敗を見ていないテストは、狙った誤りを捕まえられるか分かりません。

RSpec のテストを書く・直すときは、この手順と一緒に [writing-rspec](../writing-rspec/SKILL.md) を開き、その書き方に従います。

## 赤 → 緑 → 整理

1. **何が壊れたら落ちるテストかを決めます。** テストが捕まえる誤り (誤った分岐、抜けた副作用、誤った引数、境界、壊れた契約など) を先に言葉にします。言えないテストは、観測できる振る舞いを軸に設計し直します。
2. **赤:** 一つの振る舞いを確かめる最小のテストを書きます。名前で振る舞いを表し、名前に「と」で複数の振る舞いが並ぶなら分けます。モックは避けられない場合だけにして、本物のコードを通します。書き方は下の「期待値とモック」に従います。
3. **赤を確かめる:** 実行して、エラーでなく期待した理由で失敗することを確かめます。失敗の理由を説明できない、または綴りの誤りや読込失敗で落ちている場合は、テストを直して再実行します。最初から通るなら既存の振る舞いを試しているので、テストを直します (既存の振る舞いを固定する characterization test は下の例外に従います)。手動で動作を確かめたことを、赤の確認の代わりにしません。
4. **緑:** テストを通す最小のコードを書きます。テストに無い機能や、ついでの整理を足しません。
5. **緑を確かめる:** そのテストと、変更に関係する既存のテストを実行し、すべて通り、余計なエラーや警告が出ないことを確かめます。書いたテストが落ちたら、テストでなくコードを直します。依頼で意図して変える旧挙動を固定した既存テストは、その変更に合わせて直します。自分が原因でない失敗も名前を挙げて報告します。
6. **整理:** 緑のまま、重複や名前を整えます。振る舞いは足しません。
7. 次の振る舞いへ進み、1 から繰り返します。不具合の修正では、その不具合を再現する失敗テストから始めます。

テストが書きにくいときは、設計の問題として扱います。すべてをモックしないと書けないなら結合が強すぎるので依存を外から渡せる形にし、準備が膨らむなら補助を切り出し、それでも複雑ならインターフェースを単純にします。

## 期待値とモック

- 期待値は、テスト対象のコードやその補助関数を使わず、手で確かめたリテラルや固定データで書きます。同じ組み立て関数で期待値と実際の値を作ると、コードが何をしても一致します。入力と期待値をリテラルで並べる表形式を優先します。
- 意図して決めた定数・文言・内部構造が変わっただけで落ちるテストは書きません。その決定に依存する振る舞いを確かめます。たとえば上限回数の定数値ではなく、上限回数まで再試行してそれ以上は試さないことを確かめます。
- 自分のコードが境界で約束する内容 (登録する経路、発行するクエリ、組み立てる送信内容) を確かめます。フレームワークやライブラリの仕組みそのものは確かめません。予想外の挙動に依存したときだけ、その前提を名前にした狭いテストを一つ置きます。コンストラクター・getter・定数・単純な転送は、検証・正規化・既定値・導出・副作用を持つ場合だけテストし、それ以外は最初に利用者から見える結果で確かめます。
- モックそのものを assertion で確かめません。モックの有無でだけ結果が変わる assertion は、本物の部品について何も示しません。
- モックする前に本物のメソッドの副作用を調べ、テストが依存する副作用は本物のまま残し、遅い処理や外部との通信だけをその下の層で置き換えます。迷ったら一度本物で実行し、実際に何が起きる必要があるかを観測します。
- 引数・呼出し回数・順序が契約に含まれるなら、テストダブルでそれを確かめます。成功・失敗・不正な応答の分岐ごとに別の固定データやスパイを用意し、誤った分岐でも期待を満たせる状態にしません。
- モックの応答には、テストが読む項目だけでなく、実際のデータ構造の全項目を持たせます。項目が欠けたモックでは、後続の処理がその項目を読んだときに統合で壊れても、テストは通ります。
- テストだけが使う後片付けや補助は、本番のクラスへ入れずテスト用の補助に置きます。
- モックの準備がテスト本体より大きくなる、本物にあるメソッドがモックに無い、モックを変えるたびにテストが壊れる場合は、本物の部品を使う統合テストに切り替えます。

## 適用範囲と既存作業の保全

- テストを書く必要性と件数は、先に共通 `AGENTS.md` の「要求された挙動を証明する最小限」で決めます。既存テストを優先し、全変更・全関数へ新規テストを一律に追加しません。単純なコードや人間向けの文章にテストを足しません。
- 既存の振る舞いを固定する characterization test は test-after を認めます。新しい振る舞いの証明に、この例外を使いません。
- 実装を先に書いた場合も、既存コードや未コミット変更を機械的に削除しません。作業 tree の新実装を保ち、編集前の複製や `git show <対象版>:<path>` で変更前の実行可能な構成を別の一時領域へ用意します。新規テストと必要な依存をその領域へ揃え、そこで旧版に対してテストを実行します。読み込まれた実装が旧版であることと、新挙動の欠如による RED を確認します。作業 tree を旧版で上書きせず、新実装へテストの期待を合わせません。
- テストを省くかどうかの人間への確認は、共通 `AGENTS.md` と現在の承認範囲に従って判断します。承認済みの判断を再承認へ戻さず、必要なテストと実際の操作による確認を行います。
- 検証範囲は共通 `AGENTS.md` と repo の必須チェックで決めます。変更と直接関係する既存テストを実行し、新しい変更・失敗・未確認リスクがあれば広げます。全 suite を一律には実行せず、repo が必須とする全 suite は実行します。

## 静的テストとミューテーション確認

- 観測できる振る舞いは、振る舞いテストで確認します。スクリプトは制御した入力で実行し、出力・副作用・終了コードを確かめます。ソース文字列の照合は、その足場を用意する負担が高いと確認した場合に使います。
- 静的テストは RED → GREEN だけでは妥当性を証明できません。機能追加前は文字列がないため、無関係な正規表現でも赤から緑になります。正規表現が一致したまま約束した動作を壊せる条件を具体化し、そこからミューテーションを選びます。
- 守りたいのが呼び出し側の複数箇所なら、その箇所の欠落を確かめます。定義本体の 1 箇所だけを消して落ちても、呼び出し側を守った証拠にはなりません。文字列の存在だけでは、解放 API をファイル削除後に呼ぶような順序の不具合を確認できません。
- 静的な照合対象は、行番号で範囲を切り出し、期待件数も固定します。範囲を絞らない `(?s)` と遅延量指定子は、ブロックを飛び越えて後方へ一致するため避けます。
- テストを書き終えたら、本番コードを頭の中で壊し、現実に起こりうる壊し方それぞれで少なくとも一つのテストが落ちるかを確かめます。壊し方には、定数や引数の誤り、分岐先の誤り、状態変更や副作用の抜け、空や既定値を返す、ゼロ・空・nil・権限なし・不正な入力の検証漏れを含めます。どのテストも落ちない壊し方があれば、その振る舞いは守られていないか、テストが常に真になっています。
- ミューテーション確認は RED の代わりにしません。自分が選んだ壊し方への反応しか確認できず、実装後の緑が要求された振る舞いを証明しているかは区別できないためです。
- ミューテーション確認で退避した作業を復元するときは `git checkout` を使いません。未コミットの作業を失わないよう、先に承認範囲内で commit するか、対象ファイルを別名で退避してそこから戻します。

## LLM の判定を含む部品

- 入出力の組成・パース・分岐など、決定的な配管をスタブでテストします。非決定的で正解が主観に依存する判定品質を assertion で固定しません。
- 判定品質は実運用の誤判定を観測してからプロンプトを直します。テストの成功を求めて、停止条件のないプロンプト調整を続けません。
- 対象の hook・gate を配線したまま、その hook 自身が block する種類の作業でテストを開発しません。開発側の停止や検証を、被験体が妨げない状態で行います。

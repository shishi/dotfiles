# skill を直す

skill への変更は、足したい文をどこに書くかではなく、変更後の skill 全体が一つの責務を矛盾なく伝えるかで決めます。文を足すたびに例外・重複・食い違いが増えると、読むエージェントは規則どうしの優先を推測で埋めるようになり、同じ skill でも結果がぶれます。そのため、編集の方法は削除・置き換え・分離を先に検討し、追記は最も適切な場合だけ選びます。

## 1. 対象と周辺を読む

1. 実際に使われている版を特定します。skill を管理する repo の規約で、対象の由来と編集先を確かめます。この dotfiles では、由来の一覧 `agent-shared/skill-sources.tsv` と `docs/agents.md` の「skill の由来と編集先」に従います。plugin・system skill を直すときと、外部の skill を導入・更新するときは、[skill-source-overrides](../skill-source-overrides/SKILL.md) で修復版の有無と使う版を先に決めます。
2. その版の description と、SKILL.md・references/ の全文を読みます。一部の節だけを読んで直しません。
3. 対象の名前で検索し、対象を参照する skill・共通指示と、対象が参照する skill を読みます。重複と矛盾は skill の外にも及ぶためです。
4. 変更の動機 (依頼、指摘、観測された失敗) を確かめます。エージェントの挙動への指摘が動機なら、[create-rule](../create-rule/SKILL.md) の手順で前提と適用されなかった経路を先に調べます。この skill は本文を直す段階で使います。

## 2. 要件の一覧を作る

変更前の skill が求めている要件を、文ではなく要件ごとに作業メモへ書き出します。要件とは、適用する条件と求める行動・例外とその条件・必須の確認です。今回の新しい要求も加えます。この一覧は、再構成で要件が落ちていないかを確かめる基準です (手順 5)。

## 3. 問題を見つける

要件の一覧と本文を突き合わせ、次の問題を探します。対象の skill の中で見つけた問題は、依頼された箇所の外でも同じ編集で直します。対象の外 (ほかの skill、共通指示) に原因や重複があれば、承認された範囲に入る箇所だけを直します。範囲の外にしか直す先が無ければ、その箇所と理由を利用者に示します。

| 問題 | 見分け方 | 直し方 |
|---|---|---|
| 矛盾 | 同じ条件に別の行動を求める文がある (「必ず確認する」と「急ぐなら省略してよい」など) | 正しい側を決め、もう一方を消します。決める根拠は利用者の指示、skill の目的、上位の規則です。目的を打ち消す側 (「必ず」を条件なしで無効にする文など) は消す側です。どちらも目的と両立する方針の選択で、決める根拠が無いときだけ、両案と推奨を示して利用者に選んでもらいます。優先順位の注記を足して両方を残しません |
| 重複 | 同じ要件を複数の箇所で述べている | その要件が必要になる時点で読まれる一か所に残し、ほかは削るか参照に替えます。言い回しが違う重複は、片方だけが持つ条件を要件の一覧で確かめてから一つにまとめます |
| 事例の列挙 | 同じ理由から出た個別の事例・例外が並んでいる (「README だけなら不要」「docs/ だけなら不要」など) | 事例に共通する理由を言葉にし、一つの判断基準に置き換えます。事例は基準の理解を助ける範囲で例として残します。事例を足す依頼も、その事例が基準に入るかで扱います。入るなら基準を書き、外れるなら基準そのものを見直します |
| 責務の混在 | 一つの単位が、別の場面で使う独立した仕事を抱えている。description に無関係なきっかけが並ぶ、片方だけを使う作業でもう片方の本文まで読まれる、片方を変えてももう片方に影響しない | きっかけが別なら別の skill に分けます。同じ skill の中で一部の場面だけ必要なら references/ に分けます。分けた単位は、相手の担当範囲を一文で示して互いに参照し、内容は写しません。references/ は SKILL.md から直接参照し、references/ のファイルから別の references/ を参照させません |
| 不要な本文 | 役目を終えた経緯、時間が経つと古くなる値、skill が無くてもエージェントが正しく行うと試して確かめた手順 | 削ります。最後の種類は、試さずに「書かなくても守れる」と判断して消しません |
| description と本文のずれ | description にない場面を本文が扱う、または逆 | 本文の責務に合わせて description を書き直すか、本文を分けます |

## 4. 編集の方法を選ぶ

変更ごとに、削除・置き換え (統合を含む)・分離や移動・追記を比べ、その変更を最も適切に表す方法を選びます。比べる順はこの並びのとおりで、追記は最後に検討します。

- 追記を選ぶのは、新しい要件が既存のどの文の判断基準にも含まれず、ほかの skill や references/ の責務でもない場合です。既存の文を書き換えて表せる場合は、書き換えのほうが規則の数を増やさずに済むため、書き換えを選びます。
- 追記するときも、その要件が属する節の流れの中に書き、末尾に「ただし」を付け足しません。例外は、観測できる条件を持つ独立した分岐として書きます。
- 節を書き換えるときは、差分を小さくすることを目的にせず、要件の一覧から節全体を書き直します。

文章は [writing-prose](../writing-prose/SKILL.md) の規約で書き、用語は skill の中で一つに揃えます。

## 5. 確かめる

1. 要件の一覧の各要件について、変更後の扱いを確かめます。維持・移動・統合した要件は、反映先と適用条件が本文にあることを確かめます。消した要件 (矛盾の解消で消した側など) は、消した根拠を作業メモに残します。
2. 変更後の本文に、新しい矛盾・重複・事例の列挙が無いことを確かめます。
3. 参照先が存在することを確かめます。skill を管理する repo の検査も通します。この dotfiles では、`claude/skills/` と `codex/skills/` の両方にある skill を同じ内容に直して `tests/skills-sync.sh` で確かめます。分割・統合で skill を作ったり消したりしたら、同じ変更で由来の一覧も直します。作ったファイルは `git add`、消したファイルは `git rm` で Git に反映してから `tests/skill-sources.sh` で確かめます。この検査は、一覧に載っている各 skill の種類に応じて SKILL.md の Git 登録の有無も確かめるためです。
4. 確かめ方は、実行者が読む本文・読む時機・求める行動のどれかを改訂が変えるかで決めます。どれも変えない改訂は、上の 1 の照合で確かめます。同じ本文の中の言い回しの統一や、判断に使われない経緯の削除がこれに当たります。どれかを変える改訂は、[empirical-prompt-tuning](../empirical-prompt-tuning/SKILL.md) で変更前の版と比べます。矛盾の解消・基準への置き換え・手順の削除と、要件を別のファイルへ移す分離・移動・参照への置き換えがこれに当たります。要件を別のファイルへ移した場合は、通常の依頼でその要件が必要になる時点までに移動先が読まれたことと、読んだ後の判断が要件を満たしたことを分けて確かめます。

方法は、Anthropic の [skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md) と [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)、superpowers の [writing-skills](https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md) を参考にしています。例外を独立した分岐として書く規則は writing-skills から取り込みました。writing-skills の文言比較では、結果の安定していた指示に例外条項を一つ足しただけで結果がぶれました。

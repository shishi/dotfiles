# ルールを実行に結び付ける

依頼されたルールは、実行前ガード、skill、AGENTS.md の順に配置を検討し、実際の実行に結び付けます。作業固有の判断・手順は skill を優先します。記憶保存、同意、今後の宣言だけで完了にしません。

## 挙動について指示・修正を受けたとき

エージェントの判断・操作・応答をどう行うかという指示と、実際の挙動への修正要求を対象にします。
既存の失敗の指摘がなくても適用します。「ルールを直して」「覚えて」「skill に反映して」という追加依頼や、同じ範囲の再承認を待たず、そのターンで関連 skill の反映と検証まで進めます。
疑問形や短い指摘も、元の依頼と実際の行動に照らして意味を判断します。
通常の成果物だけの依頼、引用、ユーザー自身の訂正と混同せず、固定語句の検知にはしません。

1. **元の依頼から次の行動を決めます。** 指示の対象・適用条件・求める結果と現在の実物を照合し、修正要求には元の成果物・未達・承認範囲を引き継ぎます。
   元の目的が未達で実行可能な是正が残るなら、その操作と結果確認まで進めます。指摘への説明を返しても、元の実行要求を満たしたことにはしません。
   利用者が説明のみ・変更禁止を明示した場合はその範囲を守ります。完了か続行かは指摘の表現でなく、元の依頼の達成状況と共通指示の停止条件で判断します。
   以下の恒久対策も同じターンで進め、規則や記憶の更新を元の依頼の是正の代わりにしません。
2. **既存の規則と適用経路を調べます。** 共通指示・関連 skill・hook・記憶の本文と、
   実際の読込・呼出・判断を照合します。既存にあれば「既に書いてある」で終えず、
   なぜ適用されなかったかを調べます。未読、入口や適用条件の不足、規則間の矛盾、
   実行時の判断や環境の問題を証拠で切り分け、未取得の原因を断定しません。
   過去の内因を復元できなくても、観測された行動と既存規則が食い違う判断点を特定し、
   その判断点で規則を使うための入力・手順・検証を既存箇所へ結び付けて改善します。
   原因が未確定であることだけを「反映不要」の根拠にせず、再現と対策後の実行で仮説を確かめます。
3. **原因を担う正本へ反映します。** 反映先は、失敗した場面の名称ではなく、適用されなかった判断・手順の責務から選びます。複数の作業に共通する規則は既存の共通入口へ統合します。個別 skill ごとに同じ規則や呼出条件を追記しません。作業固有の手順は対応する既存 skill を更新し、対応先がなければ下の配置判断に従います。
   指示は守るべき性質と判断基準として既存の手順へ統合します。改訂は対策候補の保存として扱い、挙動の改善は次の手順で実証します。AGENTS.md や記憶への保存、今後守るという返答だけで代替しません。操作を止める既存ガードと、常時必要な原則・呼出条件の維持も同じ配置判断に従います。
   同じ要件が既に正しく反映され、新しい要求も観測された逸脱もなければ重複編集しません。既存に書かれているのに挙動が外れた場合は、本文だけでなく適用経路を改善します。
   記憶に置く個人方針・知識は [capturing-memory](../capturing-memory/SKILL.md) で統合します。
   規則と保存手順は記憶に複製しません。
4. **挙動の変化を実証します。** 指摘された失敗を判断点まで切り出して再現し、対策後の通常の利用経路で守るべき性質が保たれた証拠を得てから改善を判定します。規則の保存や読込確認だけでは、挙動の是正は未完了です。
   再発は既存対策が不成立だった証拠として扱い、同じ指示文の追記へ戻らず、判断を実行へ結び付ける責務を見直します。強制できる性質は既存の機構で強制し、その経路で結果を確認します。実証できなければ未達として扱い、改善・遵守を達成したと報告しません。
   Git 管理外の作業メモに、望まれた行動との差、適用されなかった原因と根拠、反映先と変更、
   検証結果を短く残します。反映しないと判断した内容にも理由を残します。
   この記録はユーザー向けの返答へ転記しません。返答自体への訂正には、訂正後の答えを返します。

毎回行うのは、指示と関連 skill の照合、必要な反映、通常の利用経路での検証です。
以後も適用する価値観・判断基準・行動方針が示された場合は、共通指示に従って
同じターンで適切な永続化手段を必ず使います。その場限りの条件は恒久化しません。
ただし、その指摘から再利用できる判断・適用経路の欠陥が分かれば、原因を担う箇所を直します。
新しい規則や記憶が不要でも、元の依頼の是正と確認は省きません。
改善が必要なのに実施・検証できない場合は、未解決のまま「不要」や「完了」としません。
エージェントの行動を制御する指示・skill・hook の正本は、この是正の関連対象です。
元の作業 repo が別でも正本を特定し、そこへ反映します。作業 repo への複製で代替しません。
編集・反映時は共通指示の作業場所・独立レビュー・稼働設定の保全に従います。
この手順はエージェント自身の行動を直す範囲に適用し、無関係な repo の改変、外部への投稿、
認証・権限・変更禁止の境界を広げません。必要な承認や実行不能な範囲は共通指示に従います。

## 依頼と配置

- 元の依頼と訂正から、禁止する判断・行動、求める結果、適用範囲、維持する保証を定めます。
  例に登場した単語だけを禁止せず、文脈上の意図を外した判断を対象にします。
- 配置は次の順に検討します。これは実装先の検討順であり、指示の権限や優先関係を変えるものではありません。
  1. **既存の実行前ガード。** push、破壊的な Git 操作、削除など、操作前に拒否すべきものを既存の判定 hook・承認審査・権限の deny へ統合します。通常の承認済み操作を維持できるか確認します。機構があることだけを理由に、作業の判断や手順までガードへ移しません。
  2. **既存 skill への統合、必要なら skill の新設。** 作業固有の判断・手順はここを第一候補にします。適用場面を description に書き、本文を作業直前に取得できる入口を確保します。同じ目的の skill を先に探し、新設は既存の責務へ収まらない場合に限ります。
  3. **AGENTS.md。** 常時必要な共通原則・承認境界と、skill を呼ぶ条件だけを残します。作業別の詳細を追記する前に、上の配置では満たせない理由を確認します。
- 既存の AGENTS.md や記憶に詳細手順がある場合も、上の順に移行します。移動先を先に用意し、元の条件・例外・必須要件が保たれ、通常の入口から参照できることを確認してから、移動元を短い呼出条件や参照へ置き換えます。同じ詳細は両方へ残しません。
  個人の価値観・好み・環境事実・版を限定した観測は private 記憶に保持します。手順と混在していれば分け、個人マシン名・私的なパス・接続先を公開 skill へ転記しません。
- 規則は入力のたびに hook で注入しません。回答の事後採点・差し戻しや失敗後の命令再注入は、ユーザーがその仕組みを明示的に依頼した場合だけ扱います。ルール改修や遵守改善の依頼だけを事後検査の承認にしません。
  明示依頼がある場合は、既存の出力ゲートと `docs/ADR/20261103-213806-output-gate-post-check.md` を確認し、下の手順を使います。
- リポジトリの指示ファイルを作成・変更する前に、エージェントの実行版・設定、対象と祖先の既存指示ファイル、公式の読込仕様を確認します。
  既存の読込経路で必要な規則が届く場合は、その経路を使います。
  Claude Code が対象の `AGENTS.md` を直接読む環境では、読込のためだけの `CLAUDE.md`・import・symlink・hook を追加しません。
  直接読めない環境では、既存の読込経路の不足を確認してから、必要な入口だけを補います。
- hook やガードを使う場合は、現在の本文、登録イベント、配備先と symlink、共通指示との関係を読みます。
  危険操作の拒否は、既存の実行前ガードへ統合します。
  Claude Code と Codex の両方に同じ共有 hook を登録しているため、既存登録を再利用します。
  作業別の詳細手順は skill に置き、hook から必要なときに参照させます。

## 明示依頼がある場合の事後検査

- 各規則は `{id, text}` で、`text` を「対象」「違反」「違反にしない」の順に書きます。
- 検査役が見られるのは、有効な依頼・制約、今回の回答、供給された会話やツール結果の原文、規則一覧です。各主張と依頼の充足に必要な証拠を原文の参照に対応付け、それだけで判定できる形にします。原文を保存したことと、検査役が取得して確認したことを区別します。
- 違反は、回答の書き直しか、差し戻しの後に同じセッションで続ける作業で解消できる形にします。過去の操作そのものを違反にすると、証拠から消せないため差し戻しが終わりません。そうした操作は「回答が報告していない」ことを違反にし、操作自体は実行前ガードで止めます。
- 既定の判定 (確認していない主張、依頼の抜け、ごまかし) と重なる規則は足しません。同じ違反が二重に指摘されます。
- 禁止語と謝罪・自己評価は、共通ルールの「応答」の節にあり、置き換えで直します。

## 実装と検証

- モデルによる意味の判断を、ユーザー入力や回答の固定文字列の一致・不一致で代替しません。
- 既存の同じ規則を置換・統合し、同じ詳細を記憶や複数の配置に複製しません。
  共通指示との矛盾があれば、現在のユーザー指示と上位の権限制約に合わせて解消します。
  vendor cache は変更せず、正本と有効な配布先を更新します。
- 採用した配置の通常の読込・呼出経路で、規則が必要な時点に使われることを確認します。
  両エージェントの登録と実際の参照先、既存 hook の契約、関連する既存テストも確認します。
  新しい hook の登録や定義変更で trust の更新が必要なら、通常の承認経路で扱います。
- skill へ移した場合は、呼び出されて本文が取得されたことと、その後の判断・操作が要件を満たしたことを分けて確認します。配置を変えただけで遵守が改善したとは扱いません。移行元に残す入口も検証対象に含めます。
- 事後検査の規則は、`tests/output-gate-rules-live.py` に違反する回答と守る回答の事例を足して実行し、違反する回答でだけその規則の違反が返ることを確かめます。検査役を実際に呼ぶ手動の試験です。
- 元の失敗例と維持条件を使い、規則に沿う判断と結果を確認します。
  規則が渡ったことやガードの出力の確認と、モデルの実際の応答・操作の確認を区別し、未確認の挙動を確認済みとしません。
  応答の抑止を依頼された場合は、通常の入力経路で元の失敗が抑止された実回答を確認するまで未完了です。
  誤った前提の訂正や、明示的に求められた別案の説明など、維持すべき応答も確認します。
  配備成功や独立レビューの指摘なしを、抑止できた証拠の代わりにしません。
  必要な独立レビューと commit は共通指示に従います。
- skill・共通指示・再利用するプロンプトを新規作成する場合や、実行者の判断・手順・出力を変える指示の改訂では、
  [empirical-prompt-tuning](../empirical-prompt-tuning/SKILL.md) で実行・修正・再評価を行います。
  上の通常経路の確認と同じ評価として組み込み、全ルール変更へ一律に実験を追加しません。

ルールの作成・変更を明示的に依頼された場合の完了報告には、選んだ配置とその理由、反映したルール、確認した利用経路、未確認事項を記します。
行動の訂正への最終回答は、訂正後の答え・成果物から始めます。規則・記憶を実際に変更した場合は、その末尾に変更した正本と検証結果を示す一文を添えます。
分析・作業経緯は転記せず、本人の判断や操作に必要な未達は明示します。
将来の応答をすべて保証したという表現で、実装・検証結果を置き換えません。

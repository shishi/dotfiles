# 工程 3: 実行可能な計画にする

[kata](../kata/SKILL.md) の工程 3 を進める手順です。次へ進む条件は kata の工程表にあります。

計画の読み手は、この repo と設計を見ていない実装担当です。担当は、正確なインターフェースとテストが分かれば、その言語の慣用的なコードを書けます。計画が選択を残した箇所も妥当に決められます。担当が自分では知り得ないのは、計画側で決めた事項です。対象ファイル、名前とシグネチャ、仕様が定めた値、各 task を証明するテストがそれに当たります。計画にはこれらを書きます。

## 手順

1. 工程 1 で決めた目的・方式・維持条件と、工程 2 で確かめた作業場所・基準版を前提にします。設計が互いに独立した複数の仕組みにまたがる場合は、仕組みごとに計画を分けます。分けた計画は、それぞれ単独で動作・検証できる成果を出すようにします。
2. task を切る前に、作成・変更するファイルと各ファイルの責務を一覧にします。分割の判断はここで固まります。
   - 一つのファイルには一つの明確な責務とインターフェースを持たせます。一度に把握できる小さなファイルのほうが、編集の誤りが減ります。
   - 一緒に変わるファイルは同じ場所に置き、技術的な層でなく責務で分けます。
   - 既存の repo では既存の構成に従います。勝手に再構成しません。変更するファイルが扱いきれない大きさになっている場合だけ、分割を計画に含めます。
3. 仕事を task に分けます。task は、自分のテスト・検証で完結し、独立レビューで単独に可否を判断できる最小の単位です。準備・設定・足場・文書の作業は、それを必要とする成果物の task に含めます。分けるのは、レビューで片方を差し戻し、隣を通す意味がある境界だけです。各 task は下の「計画ファイルの形」で書きます。
4. 各ステップは、確認できる結果を一つ持つ一つの操作にします。例は「失敗するテストを書く」「実行して失敗を確かめる」「最小の実装を書く」「実行して通過を確かめる」です。ステップは、担当がそこから書けるものが一つに決まれば足ります。種類ごとに次を書きます。
   - テスト: テスト名と、仕様の値をそのまま使ったアサーション (コードで書きます)
   - コード: シグネチャ (名前・引数・戻り値)、置くファイル、仕様が定める値。本体は担当が書きます。本体を計画に書くのは、シグネチャとテストで決まらないアルゴリズムと、仕様が文言を固定している場合だけです。
   - 検証: 実行するコマンドと、合格を示す出力
   - 他の task の参照: その task のインターフェース欄を参照し、コードを繰り返しません。

   何も決めない行は、担当が判断できない穴です。「TBD」「エッジケースを処理する」「適切な検証を加える」「上記のテストを書く」や、どの task も定義しない型・関数がこれに当たります。
5. 書き終えた計画を設計・元の依頼と見比べて点検し、見つけた問題はその場で直します。
   - 要件の網羅: 元の要件ごとに、それを実装する task を指せるかを確かめます。漏れた要件は task に足すか、満たせない理由を明示します。
   - ステップ: 各ステップから書けるものが一つに決まるかを確かめます。何も決めない行と、シグネチャとテストで決まる本体の書き写しの両方を直します。
   - 名前と型: 後の task で使う関数名・シグネチャ・プロパティ名が、定義した task と一致するかを確かめます。Task 3 の `clearLayers()` が Task 7 で `clearFullLayers()` になっていれば不具合です。
   - レビューの重点: 下の「レビューの重点」の各項目に、テストを足した task か、テストにせずレビューへ渡す理由があるかを確かめます。
   - 分量: 計画が説明するコードより長い計画は、コードを書き写しています。コードブロックが大半を占める場合は、本体をシグネチャ・テスト名・アサーションに置き換え、各ステップが一つに決まることを確かめ直します。
6. 実行方式 (司令塔が直接実行するか、子へ task を渡すか) と担当を、[agent-delegation](../agent-delegation/SKILL.md) で選びます。
7. 計画を実在のファイルに保存します。正式な計画を求められた場合は既存の正式な保存先へ、それ以外は Git 管理外の場所に、この計画専用のディレクトリを作って置きます (両 CLI の sandbox から書ける `/tmp/claude-<uid>/` の下など)。進捗の `progress.md`、実装担当の報告、長い出力の保存も同じディレクトリに置くため、別の計画とディレクトリを共有しません。
8. 実装に入る前に、実装中であることを記録します。

   ```sh
   ~/.agent-shared/bin/kata-active codex start <計画ファイル>
   ```

   記録があるセッションでは、計画を終えないまま止まろうとすると Stop hook が差し戻します。hook の判定役は、計画ファイルと同じディレクトリの `progress.md` も読みます。計画を終えたとき、または利用者の指示で中止したときは `~/.agent-shared/bin/kata-active codex done` で記録を消します。記録があっても止まれるのは、全 task を検証の証拠つきで終えたときと、次のときです。

   - 本人の認証・判断・承認が必要で、その理由と最小の操作を具体的に報告するとき
   - 利用可能な別の手段を試しても進めず、試した内容と再開の条件を報告するとき
   - 利用者が一時停止を求めたとき、または質問・説明だけを求めて、それに答えたとき

   これらの場合は記録が残り、利用者の返答の後も計画を続けます。

## 計画ファイルの形

task の見出しは、本文の言語にかかわらず `### Task 1: <部品名>` のように英字の `Task` と番号で書きます。実装担当へ task の範囲を渡すとき、この見出しで区切ります。commit はステップに書きません。task の独立レビューの後に司令塔が行います ([kata-build](../kata-build/SKILL.md))。

````markdown
# <作業名> 実行計画

**目的:** <何を作るかを一文で>
**方式:** <採用した方式を 2〜3 文で>
**設計:** <工程 1 の設計・依頼の参照先。計画は設計を根拠にするため、実装担当は両方を読みます>

## 全体の制約

<仕様が全体に課す要件 (版の下限、依存の制限、命名・文言の規則、対象環境) を 1 行ずつ。値は仕様から逐語で写します。全 task の要件に暗黙に含まれます。>

## レビューの重点

<仕様から想定されるのに、どの task のテストも扱わない入力・失敗条件のうち、通常の利用で届き、利用者に影響しやすいものを 1 行ずつ、起きやすい順に書きます。仕様に書かれていない入力でも、それでプログラムが壊れてよいことにはなりません。各行には条件と、利用者が期待する挙動を書きます。テストで固定する項目は、そのコードを持つ task のステップにテストを足します。共通指示のテスト基準に合わない項目はテストにせず、ここに残して独立レビューへ渡します。確認して該当がなければ「なし」と書きます。>

### Task 1: <部品名>

**対象ファイル:**
- 作成: `exact/path/to/file`
- 変更: `exact/path/to/existing:123-145`
- テスト: `tests/exact/path/to/test`

**インターフェース:**
- 使う: <前の task から使うもの。正確なシグネチャ>
- 提供する: <後の task が頼るもの。正確な関数名、引数と戻り値の型。実装担当は自分の task しか読まないため、隣の task の名前と型はこの欄で知ります>

1. 失敗するテストを書く: `test_specific_behavior` (アサーションをコードで示す)
2. 実行して失敗を確かめる
   実行: `<コマンド>`
   期待する結果: FAIL (<期待する失敗の理由>)
3. `exact/path/to/file` に `function(input: InputType) -> ResultType` を実装する
   (シグネチャとテストで選択が残る場合だけ、使うライブラリやデータ構造を 1 行で)
4. 実行して通過を確かめる
   実行: `<コマンド>`
   期待する結果: PASS
````

## 注意

- 計画書の承認待ちや実行方式の選択メニューを、新しい承認条件にしません。本人にしか決められない選択と、依頼・repo の手順が求める承認は維持します。
- 計画は会話だけで済ませず、実行時に読み直せるファイルにします。短く明確な仕事で計画が不要なら、工程 3 を省いた判断と根拠を示して工程 4 へ進みます。
- 「レビューの重点」は、共通指示のテスト基準 (現実性・損害・明示スコープの根拠がない仮定上のケースを増やさない) を緩めません。

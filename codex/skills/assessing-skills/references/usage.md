# 担う場面で skill が開かれたかを記録で確かめる

過去のセッション記録は、skill の担う場面が実際の作業で起きたときに、その skill が開かれ、期待する行動が起きたかを確かめるために使います。開かれた回数の合計は、場面がどれだけ起きたかと、開かれるべきでない場面で開かれた回数が混ざるので、判定に使いません。

## 1. 担う場面が起きたセッションを探す

skill の担う場面を表す語 (症状、エラーの文言、対象の名前) で記録を検索し、場面が起きたセッションを選びます。期間は、評価する行動を決めているファイル (SKILL.md と references/) が今の内容になってからにします。それより前の記録には、名前の違う前身や、廃止した skill が混ざります。版を決める材料は、Git で管理する skill なら Git の履歴 (`git log -1 --format=%cs -- claude/skills/<名前>/` など)、管理しない skill なら取得元の配布版と、適用した overlay の履歴です。この材料で記録を絞り、採用する記録ごとに、評価する版と同じかを照合します。本文を開いた記録は、届いた本文で照合します。本文を開かなかった記録は、その時点で使えた版を、この材料と記録に残る一覧 (description や、一覧に出る配布版のパス) で照合します。どちらでも決まらない記録は、版不明として分けます。未コミットの編集で動いていた期間は、Git の日付だけでは分からないためです。

- Claude Code: `~/.claude/projects/` の下に、作業ディレクトリごとのディレクトリと `<session>.jsonl` があります。ディレクトリ名は記号を `-` に置き換えた形なので、名前を組み立てずに、記録の中の `cwd` で作業ディレクトリを確かめます。子エージェントの記録は `<session>/subagents/` の下にあります。
- Codex: `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`。古い記録は `*.jsonl.zst` に zstd で圧縮されているので、`zstdcat` で展開してから検索します。展開に失敗した記録は、読めなかった件数として分けて数えます。

## 2. セッションの種類を分ける

利用者が直接依頼した作業だけを、skill の判定に使います。

次は分類の手がかりです。手がかりだけで決めず、冒頭の依頼と、委譲元・試行元の記録で区別します。

- Claude Code: 記録の `entrypoint` が `sdk-cli` のものは `claude -p` などプログラムからの起動 (委譲・判定役・試行、または利用者が自分で流したもの) です。`subagents/` の下は子エージェントです。
- Codex: 先頭の `session_meta` の `originator` が `codex_exec` のものは `codex exec` からの起動、`source` に `subagent` があるものは子エージェントやレビューです。
- どちらも、作業ディレクトリが一時ディレクトリ (`/tmp` の下など) なら試行のことが多いですが、利用者が一時ディレクトリで直接作業することもあります。skill を置いている repo (dotfiles) で skill 自体を作る・直すセッションは、skill のファイルを読むのが作業そのものなので分けます。分け方が決まらない記録は、分類できなかったものとして残します。

## 3. そのセッションで skill が開かれたかを見る

- Claude Code: skill が開かれると、Skill ツールで呼ばれた場合も、利用者が `/<名前>` で呼んだ場合も、記録に `Base directory for this skill: <パス>/skills/<名前>` の行が入ります。`Read` で `SKILL.md` を読んだ場合もあります。記録は JSON で、改行は `\n` の 2 文字になっているので、名前の後ろに `\n` か `"` が続く形で探します。例: `grep -lE 'Base directory for this skill: [^"\\]*/skills/<名前>(\\n|")' <記録>`。この検索は候補の記録を絞るだけです。利用者が過去のログを貼った発言にも同じ行が入るので、一致した行が skill の読み込み (`isMeta` が true の user イベント。Skill ツールで呼ばれた場合は `sourceToolUseID` がその呼び出しを指す) であることを、その行を含むイベントの種類で確かめます。`Read` や Bash (`cat` など) で本文を読むこともあるので、ツールの種類を問わず、対象の SKILL.md の本文が返った成功結果も「開かれた」に数えます。
- Codex: skill の本文はシェルのコマンドで読まれます。ツール呼び出しのうち、`SKILL.md` を読むコマンド (`cat`・`sed -n` など) と、その出力に本文があることを確かめます。パスに触れただけのコマンド (検索・一覧) は、開いたことに数えません。

どちらも、本文が届いたのが、skill が変えるはずの判断・操作より前かを、イベントの順序で確かめます。依頼を受けてから開いた場合も、その判断に間に合っていれば開かれたものとします。

## 4. 開かれていなかったときに確かめること

開かれていなかった場面ごとに、次を順に確かめてから原因を決めます。

1. その時点の skill の一覧に、対象の description が載っていたか。Codex は記録の冒頭に、Claude Code は記録の `skill_listing` に一覧が残ります。Claude Code は一覧の文字数が上限を超えると description が短くなります。description が載っていなかった、または短くなって場面が読み取れなかったなら、description の文言より先に、一覧に載る条件を調べます。
2. 同じセッションの前のほうで本文を既に読んでいて、文脈に残っていたか。
3. 本文が文脈に無かったときに、期待する行動 (SKILL.md の手順 1 で書いたもの) が起きていたか。本文が文脈に残っていた場合は、本文がある条件として扱い、ここに数えません。起きていれば、その場面と、実際に確かめた行動については、本文を読まなくても同じ行動がとれた材料になります。その場面でも一覧の description や、skill の名前を挙げた記憶は文脈に残っていたので、skill が無い状態の証拠にはなりません。確かめていない行動や、別の場面についての結論にもしません。
4. description が一覧に載っていて、本文が文脈に無く、期待する行動も起きていなければ、description が場面と合っていない可能性があります。同じ場面の依頼を新しいプロセスで流し、呼ばれないことを再現しても、文言は原因の候補にとどめ、直した後に呼ばれることを確かめます。

記録はこのマシンのものだけで、ほかのマシンでの作業は含みません。

# 子へ task を渡す手順

[kata-build](../SKILL.md) の「子へ task を渡す方式」で実装担当を起動する前に読みます。依頼文、担当に求めること、報告の扱い、レビューと修正の回し方を扱います。

依頼文は一つの task だけを説明し、session の経緯を含めません。前の task の要約を積み重ねて貼りません。依頼文には次を入れます。

1. この task が全体のどこに当たるかを 1 行
2. 計画ファイルのパスと、その task の行範囲と「全体の制約」の行範囲。task の範囲は `grep -n '^#\{1,6\} Task ' <計画ファイル>` で求め、コードブロックの中に当たった行は境界から除きます。「最初に読む要件で、値はここから逐語で使う」と示し、計画全体は読ませません。正確な値・シグネチャ・テストケースは依頼文に書き写さず、計画の本文だけに置きます。
3. 前の task から引き継ぐインターフェースと判断の記録。前の task が同じ範囲で見送った指摘があれば、その記録の場所
4. task の本文で親が気づいた曖昧さと、その解き方
5. 報告ファイルのパス (計画のディレクトリの `task-N-report.md`) と、下の報告の形

依頼文で担当に求めること:

- 着手前と作業中に、要件・受入条件・方式・前提に不明な点があれば質問します。推測で進めません。親は質問に答え、必要な文脈を足し、急がせません。
- task の指定どおりに実装し、テストと検証をします。繰り返す間は変更箇所に絞ったテストを走らせ、報告の前に task のテストを通して実行します。
- 子をさらに起動しません (実装の分担にも、自分の作業のレビューにも使いません)。レビューは報告の後に親が `review-gate` で編成します。担当が起こした reviewer は同じ差分の重複であり、その承認は工程の通過に数えません。
- commit と `kata-active` の実行はしません。
- 計画のファイル構成に従います。作成中のファイルが計画の意図を超えて大きくなる場合は、自分で分割せず懸念として報告します。変更する既存ファイルが大きく絡み合っている場合も懸念として報告します。触れているコードは改善してよいですが、task の外を再構成しません。
- 手に余る場合は止まって報告します。該当するのは、複数の妥当な設計判断が要る場合、渡された範囲の外のコードを理解する必要があり見通しが立たない場合、方式が正しいか確信できない場合、計画が想定しない再構成が要る場合、ファイルを読み続けても進まない場合です。何に詰まり、何を試し、どんな助けが要るかを書きます。質の悪い成果は、成果が無いことより悪いためです。
- 報告の前に自分の差分を読み直し、見つけた問題を直します。要件をすべて実装したか、依頼外の機能を足していないか、名前が処理の中身でなく役割を表すか、既存の書き方に従ったか、テストがモックでなく実際の振る舞いを確かめるか、テスト出力に警告や雑音が無いかを確かめます。
- 報告ファイルには、実装した内容 (止まった場合は試した内容)、テストと結果、赤と緑の証拠 (実行したコマンドと出力、赤が期待どおりの理由)、変更ファイル、自己点検で見つけたこと、懸念を書きます。返答は 15 行以内とし、状態 (`DONE` / `DONE_WITH_CONCERNS` / `BLOCKED` / `NEEDS_CONTEXT`)、一行のテスト結果、懸念、報告ファイルのパスだけを返します。`BLOCKED` と `NEEDS_CONTEXT` では、詳細も返答に書きます。

報告の状態ごとに次のように扱います。

| 状態 | 親の対応 |
|---|---|
| `DONE` | 差分と証拠を実物で照合し、task の独立レビューへ進めます。 |
| `DONE_WITH_CONCERNS` | 懸念を読みます。正しさ・範囲の懸念はレビュー前に解消します。ファイルが大きいなどの観察は記録して、レビューへ進めます。 |
| `NEEDS_CONTEXT` | 足りない情報を足して、もう一度依頼します。 |
| `BLOCKED` | 文脈が足りなければ足して同じモデルで、推論が足りなければより能力の高いモデルで、task が大きすぎれば分けて、計画が誤っていれば判断を記録してから、もう一度依頼します。何も変えずに同じ担当へやり直させません。 |

task の独立レビューは `review-gate` で編成し、task の本文の範囲、「全体の制約」の逐語、報告ファイル、基準版からの全差分を渡します。担当の報告と、そこに書かれた設計の理由は、未検証の主張として扱います。reviewer への依頼に「この点は指摘しない」「重大度は低い」「計画がそう決めた」のような事前の判定を書きません。誤検知と思う指摘も、reviewer に挙げさせてから採否を判断します。reviewer が差分だけでは確かめられないと返した項目は、task 間の文脈を持つ親が確かめます。実際の不足なら採用した指摘と同じく修正へ回します。

採用した指摘の修正は、その task の担当を再開して頼み、指摘を逐語で渡します。担当の文脈に task・コード・自分の選択が残っているためです。担当は修正し、修正したコードを覆うテストを再実行し、変更内容・実行したテスト・コマンド・出力を報告ファイルに追記します。親は、その追記があることを確かめてから、`review-gate` の手順で影響範囲を再レビューします。修正しても同じ指摘が残る場合は、原因の見立てを更新したうえで、報告ファイルと未解決の指摘を新しい担当 (必要ならより能力の高いモデル) に渡し、「前の担当が N 回試した。報告ファイルで試した内容を読む」と伝えて切り替えます。担当を再開できない環境でも、報告ファイルと指摘を渡して新しい担当に頼みます。

- 小さく同じ形の変更 (同じ 1 行の修正、定数の変更、項目の追加など) が複数の task に並ぶ場合は、task ごとに担当を起動しません。ファイルごとの変更の一覧を一つの依頼にまとめ、一つの差分としてレビューします。並んだファイルのどれかに変更が無ければ要件の漏れです。
- 最終レビューで採用した指摘は、全件の一覧を一人の担当にまとめて渡します。指摘ごとに担当を分けると、担当ごとに文脈の構築とテストの実行が繰り返されます。担当は指摘を一つずつ直し、そのたびに修正を覆うテストを実行します。

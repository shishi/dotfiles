# MySQL のデータ・スキーマ移行を検証する

対象 DB の版、ストレージエンジン、実スキーマ、データ量、接続ロール、メンテナンス条件を確認します。
プロジェクト固有の移行フェーズや実行経路は、対象 repo の正式文書と関連記憶から取得します。

## DDL の成立条件

- 削除・変更する列の index、外部キー、生成列、CHECK と DDL の制約を確認します。
  対象版と同じスキーマで、許可された検証環境から実際の ALTER を確認します。
- メンテナンス時間に影響する場合、要求する `ALGORITHM` と `LOCK` を明示します。
  ORM の既定が低コストな方式を保証すると扱いません。
  INSTANT 不可なら、暗黙に表再構築へ落ちる挙動と明示失敗の違いを確認します。
- INSTANT の対応と row version の上限は版・操作で異なります。
  index の削除を伴う場合は、操作を分ける必要と既存制約への影響を実測します。
  過去のある版での失敗を、全 MySQL 版の仕様へ広げません。

## データ移行とゲート

- 複数テーブル UPDATE では単一テーブル UPDATE と同じ LIMIT が使えるとは限りません。
  バッチを分ける場合は ID 範囲などで対象集合を定め、境界の欠落・重複を確認します。
- TEMPORARY TABLE はセッションに属します。生成と利用を同じ接続で実行し、
  接続・プロセス終了で失う状態を、永続的な再開情報と混同しません。
- 書き込み直後のゲートは Writer で読みます。
  Reader の遅延指標が小さくても、SQL と観測時刻が違えば直後の整合性の証明になりません。
- ゲートの述語は、追加・維持する制約全体と一致させます。
  XOR の一方だけを検査するなど、部分的な異常検査を制約追加の成功保証にしません。
- 実行権限・接続先を確認し、許可された検証環境で移行前後の結果と制約追加を照合します。
  調査やレビューの依頼だけで本番の移行を実行しません。

使用版の [InnoDB online DDL](https://dev.mysql.com/doc/refman/8.0/en/innodb-online-ddl-operations.html)
と [UPDATE](https://dev.mysql.com/doc/refman/8.0/en/update.html) を確認します。

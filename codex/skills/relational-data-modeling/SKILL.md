# 集合と関連によるデータモデル

NULL は不定を示すマーカーであり、属性の定義域に属する通常の値ではありません。
「ない」「未発生」「非該当」を表す値とみなさず、設計時とレビュー時に原則排除します。
成立している事実を集合と関連で表し、各行の属性をその事実について定まる値にします。
イベント記録や必要な範囲のテーブル分離を先に検討し、NULL を残す側に強い根拠を求めます。
NULL の数だけで良否を判定せず、情報の意味・既存の保証・運用上の制約を維持します。

SQL の NULL を含む `=` や `<>` による比較は真偽が不定になります。
[MySQL の NULL の説明](https://dev.mysql.com/doc/refman/8.4/en/working-with-null.html)
も参照し、業務上の「ない」と SQL の不定を混同しません。

MySQL の DDL・データ移行を検証する場合は、[移行の成立条件とゲート](references/mysql-migration.md)
を読みます。通常の設計だけで移行作業を追加しません。

## 設計と照合

1. 各行が表す事実、識別するキー、関連の多重度を特定します。
   現在状態・起きた出来事・時刻から導ける状態を区別します。
2. nullable な属性が表そうとしている事実を特定します。
   未発生や任意の関連は、原則として対応する事実の行が存在しない形で表します。
   属性が一部の対象にのみ成立する場合は、その事実が成立する対象を別の関係で表します。
   値が不明でも既に成立している事実は記録し、判明している属性と必要な範囲で分離します。
   たとえば、使用済みで使用時刻だけ不明なら、使用した事実と時刻が判明している事実を分けます。
   ただし「ない」と「不明」の区別が必要なら、その区別も事実として表現し、行の不在だけにまとめません。
3. 一緒に成立する属性を同じ関係にまとめます。出来事が起きたときだけ必要な属性は、
   その出来事の関係へ移し、存在する行の属性を NOT NULL にします。
   値が未取得・不明なのに、0、空文字、ダミー日時などで既知の値に見せません。
   文字数が 0 であると確定している文字列には、空文字を正当な値として使えます。
   空文字や 0 が属性の定義域と業務上の意味に合うなら、NULL の排除に使えます。
   分離は、独立した事実や成立条件・多重度・制約の違いを表すために行います。
   NULL をなくすためだけの意味のない分割や、成立条件が同じ属性を一つずつ切り出す分割は認めません。
   不要なイベント履歴・汎用状態基盤も作りません。
4. NOT NULL、主キー・候補キー、UNIQUE、外部キーを必要な不変条件へ対応付けます。
   「関連を表す列がある」「関連先が実在することを DB が保証する」を区別します。
   UNIQUE は参照先の存在を保証しません。NULL を許す列の一意性は DB の仕様に照らして確認します。
   外部キーの追加・削除は、削除規則・履歴保持・移行リスクも含めて判断します。
   NULL 排除を理由に一律に外部キーを外しません。削除後も残す歴史上の ID と、
   現存する行への参照は意味を区別し、失う参照整合性の保証を明記します。
5. 使用可能・期限切れなどは、集合の差・存在判定・時刻の条件で導けるかを確認します。
   同じ事実をフラグ・nullable な日時・関連行へ重複して保持しません。
   事実の発生時刻と記録時刻が一致する仕様なら、created_at の兼用も選べます。
6. 具体案を既存の読み書き・削除・必要な原子性と照合します。
   テーブルごとの一意制約だけで、複数テーブル間の排他や処理全体の原子性を保証したとは扱いません。
   NULL を残すのは、イベント記録やテーブル分離では必須要件を満たせない強い根拠がある場合に限ります。
   互換性・性能・既存データ移行の制約は、対象の実装・実測・移行条件で分離案と比較します。
   NULL に「ない」などの意味を割り当てる場合も、その意味と適用範囲、分離案で満たせない必須要件、
   比較の証拠、失う保証を示します。慣例やテーブル数を減らしたい事情だけでは認めません。
   既存データのない設計に移行作業を要求するなど、対象外の保証は追加しません。

## 例：招待・使用・失効

一度の使用で消費され、手動失効を取り消さない招待を考えます。
使用時刻は使用の記録時に必ず判明する前提です。

| 関係 | 行が表す事実 | 主な制約 |
|---|---|---|
| invitations | 招待を発行した | id がキー、token が一意、expires_at が必須 |
| invitation_usages | 招待を使用した | invitation_id が一意、使用時刻などが必須 |
| invitation_revocations | 招待を手動失効させた | invitation_id が一意、失効時刻が必須 |

未使用・未失効は対応する行の不在で表せます。招待 ID の集合として、
`利用可能 = 期限内の招待 − 使用済みの招待 − 手動失効済みの招待` と導けます。
期限切れは expires_at と判定時刻の比較で導けるため、その判定だけの記録は不要です。
再有効化や履歴の要件が異なる場合は、この例をそのまま適用しません。

## レビューで返す内容

対象の具体的な列・関係・要件に結び付けて、記録すべき事実、NULL を排除する集合・関連の設計、
守る制約と失う保証を示します。NULL を残す案は、分離案を退ける強い根拠まで確認します。
全列 NOT NULL だけで合格にせず、仮値による不定の隠蔽や独立した事実の混在も見ます。
空文字などの正当な値を使う案と、事実を分ける案を区別し、意味のないテーブル分割を要求しません。実益のある指摘がなければ指摘なしとします。
既存の nullable 列の一括改修や将来機能の追加を要求しません。
必要な事実を記録しないことで NULL を減らす対応も認めません。
レビュー依頼を実装依頼へ広げず、判定は既存の review-gate に統合します。
